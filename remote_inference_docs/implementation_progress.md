Public options and defaults are resolved below. Alignment and blending are separate selectable behaviors and both are implemented. The legacy `0.3 * old + 0.7 * new` heuristic remains a reference, not an automatically selected new default.

Implementation decisions (2026-09-29): retain policy execution mode `chunk`, with client `chunk_merge=append|aligned`. Optional blending uses `blend_steps` (default 0, disabled, at most the configured execution slice), `blend_weight` (default 0.5, incoming fraction in `(0, 1]`), and explicit `blend_components`. The deployment separately declares permissible continuous canonical coordinates in `execution.blendable_components`; there is no implicit gripper selection. New clients require explicitly advertised `chunk_alignment_v1` / `chunk_blending_v1` capabilities and an exact settings acknowledgment. Protocol major 1 remains because old servers already reject unknown required capabilities; ordinary append and RTC retain their semantics. Observation anchors are captured on the control thread before the next policy endpoint is committed, and retain the cursor through delayed submission.

Same-host server/client processes remain an explicit target: users with a local GPU may want sustained bounded background replanning and smoother plain-policy motion without RTC. This uses the same executor/contract as LAN; no new in-process backend is required. The initial implementation requested as soon as the worker and a fresh advanced observation were available. **Superseded design decision:** the ACT follow-up adds the playback threshold to aligned scheduling, preserving one-in-flight and bounded future storage without importing append's successor-slot restriction. Asynchronous execution does not require maximal inference frequency.

Deferred by the user: expanded sensor-stall detection, per-camera timestamp propagation, independent hardware watchdogs and acquisition-error teardown redesign. Preserve current age and fault checks and record their limits; these deferred findings must not silently expand this batch. Also keep automatic motion recovery, automatic refill optimization and XVLA RTC out of scope. Legacy removal still waits for the existing real action/language acceptance gate.

## Inspection and decisions

- Scope comes only from `async_proposal.md`; older documents and draft branch are not requirements.
- Keep synchronous `select_action()` execution intact.
- Inspection found independently locked continuation getters and policy/processor reset on the control thread. These now use atomic snapshots and worker-owned resets.
- Plain chunks honor execution length independently of predicted horizon; RTC needs both canonical and model-space continuation. Plain append remains default; explicit aligned replacement trims actual committed progress and optionally blends eligible matching future targets.
- Fail closed for unsupported robot stop semantics, policy history/preparation, feature semantics, and explicitly requested modes.
- Do not remove legacy async/gRPC service before the proposal's real workflow validation gate passes; unrelated RL protobuf definitions and dependencies remain.
- Explicit semantic profile plus named feature conventions are required on the deployment/client; wire camera resolution is exact. SmolVLA and XVLA declare their existing internal resize/optional-camera behavior, and LaWAM declares processor resizing/unused-state behavior, through policy-owned validation hooks; policies without overrides retain exact checkpoint shapes. Rename mapping happens once client-side.
- Position hold is implemented for `SOFollower` and `OmxFollower` robots with only `.pos` actions. Unsupported/mixed control modes are rejected for async rollout. Physical hold validation is outstanding.
- Timing defaults are provisional lab starting points, not measured profiles. Local RTC gains additive age/action/startup/language bounds; synchronous action execution is unchanged.
- Server content identity hashes checkpoint/processor files, optional resolved adapter/base contents and effective settings. Warmup is server-only and is followed by a full reset before readiness.
- The server uses one serialized worker, capacity-one inference admission and bounded control/reply queues. A hung call cannot release model ownership to another session.
- Monotonic data sequence numbers supplement bounded request-ID history, preventing duplicate execution after ID-cache eviction.
- Zenoh binding is pinned to 1.9.0; the matching 1.9.0 router was tested. MessagePack is constrained to `>=1.1,<2`, with 1.2.2 selected in `uv.lock`. Direct callbacks only perform bounded handoff; query handles outlive callbacks until worker acknowledgments. Explicit subscriber readiness is required before data publication.
- Recording uses asynchronously written, bounded JSONL events keyed by session/control tick. Canonical targets, post-robot-processor commands and scalar measured state remain distinct.
- Planned holds preserve pending full resets and clear motion before acknowledging the hold. Language uses an isolated canonical processor pair. Autosteering requires an actual dispatched action after applying a subtask before requesting another, including with a zero interval.
- Startup/compilation and steady action deadlines are distinct. A deadline fault cannot restart warmup or restore dispatch. Local plain-chunk playback uses the declared execution slice; history-dependent configurations are rejected explicitly.
- No older draft code was reused. No future scheduling, recovery or multi-client framework was added. Legacy async/gRPC removal is deferred by the proposal's gate, not replaced with a compatibility shim.

## Post-LAN implementation — 2026-09-29

Completed the four approved engineering stages on the existing test branch:

1. **Session cleanup:** all OMX presets use a 30-second grace beginning at observed absence. Descriptor/status and BUSY diagnostics expose the owner, presence, remaining grace, pending inference/cleanup and blocker. Clean close still runs on the single worker; lost clients can be re-admitted after cleanup without restarting a healthy server. Grace does not cancel or take over unfinished inference. Presence restoration and a full command queue are handled without silently extending an already elapsed grace.
2. **Shared alignment and blending:** `ChunkRuntime` anchors observations to the next uncommitted endpoint, accounts for progress before submission and during inference, trims only the configured slice, and atomically replaces future actions. No usable suffix means rejection with the prior eligible buffer intact. Scheduling requires fresh captures and advanced policy steps, with a fresh-capture exception for a changed task version so startup retargeting cannot stall. Reset/resume reject older captures. Only one request runs at a time; aligned storage never grows beyond the execution slice.
3. **Explicit blend contract:** canonical float coordinates are selected by name on both deployment and client. Blending is limited to matching future steps in the configured window; non-selected coordinates use incoming targets. Relative-to-absolute postprocessing happens before blending. Old task/session/generation/artifact contexts and expired contributors are excluded. Per-target provenance stores incoming identity plus the oldest original source, contributor count and fixed-length digest, so repeated blends preserve the conservative age bound without growing a recursive history. Weight 1 gives replacement; default blending is disabled.
4. **Diagnostics and compatibility:** logs report configured/effective refill, scheduling rule, source/submission cursors, old playback, turnaround/margin, trim/overlap/blend counts, estimated and actual first-dispatch age, and canonical endpoint deltas. First-dispatch telemetry is bounded and drained by the worker, preserving its original time/generation/control tick. Build metadata is captured once at module/process startup, reports unknown Git revisions honestly, and is diagnostic only. Required alignment/blending capability checks plus exact settings/cursor echoes prevent old-server fallback before motion. The user guide now explains the freshness/continuity tradeoff, merge choices, nested CLI overrides and symptom-based tuning.

Review also found a pre-existing task-version read/accept race. Both remote and local RTC now hold the task lock through acceptance, so retargeting and admitting an old in-flight result have a definite order. Buffered actions accepted before a task change retain their original labels as specified; obsolete in-flight results are rejected. Synchronous inference is unchanged.

## Aligned request-timing correction — design and next steps, 2026-09-29

The follow-up inspection found a useful existing mechanism: legacy `async_inference` submits observations below `remaining_actions / chunk_size <= chunk_size_threshold` (default 0.5), then aligns/blends matching timestep targets. It may submit multiple observations below threshold and also filters similar joint states. `async_proposal1.md` recommends replacing the ratio with seconds; the inspected `origin/feat/remote_inference_draft` worker gates on `queue.qsize() * dt <= buffer_time_s`, with append for plain policies and replacement for RTC. These are references, not requirements or proof that the old implementation would solve this hardware failure.

**Decision:** retain the current transport, policy/processor contracts, atomic runtime, cursor/provenance and lifecycle infrastructure. Correct the later coupling of alignment to maximal replanning. Reuse `inference.refill_seconds` and `max(refill_seconds, recent_max_turnaround + action_interval)` for aligned steady-state requests. No new timing parameter, blend algorithm or protocol capability is needed for this client-local trigger. Keep append default and current numerical defaults; append, RTC and synchronous execution behavior are outside this change.
