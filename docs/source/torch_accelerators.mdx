# PyTorch accelerators

LeRobot supports multiple hardware acceleration options for both training and inference.

These options include:

- **CPU**: CPU executes all computations, no dedicated accelerator is used
- **CUDA**: acceleration with NVIDIA GPUs, and with AMD GPUs through ROCm (see [AMD GPUs](#amd-gpus-rocm))
- **MPS**: acceleration with Apple Silicon GPUs
- **XPU**: acceleration with Intel integrated and discrete GPUs

## Getting Started

To use particular accelerator, a suitable version of PyTorch should be installed.

For CPU, CUDA, and MPS backends follow instructions provided on [PyTorch installation page](https://pytorch.org/get-started/locally).
For XPU backend, follow instructions from [PyTorch documentation](https://docs.pytorch.org/docs/stable/notes/get_start_xpu.html).

### AMD GPUs (ROCm)

ROCm builds of PyTorch expose the HIP runtime through the `torch.cuda` namespace, so
`--policy.device=cuda` selects an AMD GPU and no LeRobot-side change is needed. `HIP_VISIBLE_DEVICES` is preferred over `CUDA_VISIBLE_DEVICES` when selecting specific cards.

Installing LeRobot on top of an existing ROCm PyTorch needs care: LeRobot's `torch`,
`torchvision` and `numpy` bounds may differ from what a ROCm image ships, and a normal
install takes torch from PyPI, whose Linux wheels are CUDA builds, so an
unconstrained install replaces the ROCm build and leaves the GPUs unusable. Pin those
packages with `uv pip install --override` so the rest of the tree resolves normally.
[`docker/Dockerfile.rocm`](https://github.com/huggingface/lerobot/blob/main/docker/Dockerfile.rocm)
does this and is the quickest way to a working environment; see
[docker/README.md](https://github.com/huggingface/lerobot/blob/main/docker/README.md)
for the run flags ROCm requires.

#### Known issues on ROCm

These came up while training LeRobot policies on AMD Instinct MI300X with ROCm 7.14 and PyTorch 2.12, using `docker/Dockerfile.rocm`:

- **`--group-add render` fails.** Some images do not define the `render` group by name. Pass the host's numeric group IDs instead, for example `--group-add $(getent group video | cut -d: -f3) --group-add $(getent group render | cut -d: -f3)`.
- **Multi-GPU training gets slower as GPUs are added.** Some HIP runtimes ([ROCm/rocm-systems#6134](https://github.com/ROCm/rocm-systems/pull/6134), reverted in [#6712](https://github.com/ROCm/rocm-systems/pull/6712)) narrow the CPU affinity of every process that initialises HIP to the CPUs nearest GPU 0. `accelerate launch` initialises HIP to count the GPUs, so all ranks and their DataLoader workers share those CPUs. On an 8x MI300X node with 160 CPUs this left 8 CPUs, and ACT ran at 706 samples/s on 8 GPUs, below its 1,056 on 2. Set `AMD_CPU_AFFINITY=0` (the runtime's default again upstream) before launching: the same run reached 4,122 samples/s on 8 GPUs (579 on one). `python -c "import os, torch; torch.cuda.device_count(); print(len(os.sched_getaffinity(0)))"` shows whether a runtime is affected.
- **The first training step is slow.** MIOpen compiles convolution kernels for each new shape on first use, which took about 8 minutes for ACT's ResNet backbone at batch 32. The compiled kernels go to the user's cache directories, which a `--rm` container loses. Mount a persistent directory and point `MIOPEN_USER_DB_PATH` and `MIOPEN_CUSTOM_CACHE_DIR` at it: the first step of the next run then took 28 s instead of 464 s. `MIOPEN_FIND_MODE=2` (fast find) is enough; normal find was not faster afterwards.
- **Evaluation in MuJoCo environments cannot render with EGL.** Instinct GPUs have no graphics context (`can't create a graphics context on a compute chip`). Render on the CPU instead: install `libosmesa6` and `libglu1-mesa`, and set `MUJOCO_GL=osmesa`.
- **LoRA (`--peft.*`) needs `torchao` newer than 0.16.** If the base image ships an older one, PEFT refuses to load. Run `uv pip install 'torchao>0.16'` in the image; the overrides in `Dockerfile.rocm` keep the ROCm build of PyTorch in place.
- **FlashAttention is not available.** Use the policy's PyTorch attention instead, for example `--policy.attn_mode=torch` for FLUX3.
- **The FLUX3 Video VAE needs NATTEN**, which has no ROCm wheels. Its source build only provides the Flex backend, which without compilation materialises a dense mask and runs out of memory at the VAE's sizes.

#### Policies trained on ROCm

Each of these completed training steps and saved a checkpoint on MI300X: ACT, Diffusion, Multi-task DiT, VQ-BeT, TD-MPC, SmolVLA, π0, π0.5, π0-FAST, EO1, X-VLA, WALL-OSS, Cosmos3, LaWAM, G05, FastWAM, LingBot-VLA, LingBot-VA, MolmoAct2, DM05, EVO1, VLA-JEPA, Long-WAM, FineART-VLA, GR00T N1.7 and NAT VLA, plus the SARM and reward-classifier reward models. Multi-GPU training (DDP, FSDP, HSDP) through `accelerate launch` behaves as on NVIDIA GPUs.

### Verifying the installation

After installation, accelerator availability can be verified by running

```python
import torch
print(torch.<backend_name>.is_available())  # <backend_name> is cuda, mps, or xpu
```

## How to run training or evaluation

To select the desired accelerator, use the `--policy.device` flag when running `lerobot-train` or `lerobot-eval`. For example, to use MPS on Apple Silicon, run:

```bash
lerobot-train \
    --policy.device=mps ...
```

```bash
lerobot-eval \
    --policy.device=mps ...
```

However, in most cases, presence of an accelerator is detected automatically and `policy.device` parameter can be omitted from CLI commands.

## Mixed precision

Training precision is owned by `--accelerator.mixed_precision`, which accepts `no` (default), `bf16` and `fp16`:

```bash
lerobot-train \
    --policy.type=act \
    --accelerator.mixed_precision=bf16 ...
```

`fp16` requires an accelerator: it is rejected on `--policy.device=cpu`, where accelerate builds no loss scaler and the run would silently fall back to full precision. `bf16` autocasts on CPU too, so it is not restricted.

`bf16` requires hardware support (Ampere or newer on NVIDIA GPUs). On older accelerators such as V100 or T4, use `fp16`.

### fp16 and the loss scaler

`fp16` has a much smaller exponent range than `bf16`, so gradients are scaled up before the backward pass and scaled back down before the optimizer step. LeRobot delegates this to accelerate's `GradScaler`, which also detects overflowing gradients and skips those optimizer updates. Under sharded training the gradients are `DTensor`s and PyTorch reduces the overflow flag across the device mesh, so an overflow on one rank skips the update on all of them.

Skipped updates are normal, especially in the first few steps while the scale calibrates down from its initial value. They are visible in the logs as the `scale` metric dropping. The scale is saved with every checkpoint (`training_state/scaler_state.json`) and restored on resume, so a resumed run does not have to recalibrate.

The scaler can be tuned if the defaults do not suit a policy:

```bash
lerobot-train \
    --policy.type=act \
    --accelerator.mixed_precision=fp16 \
    --accelerator.grad_scaler.init_scale=1024 \
    --accelerator.grad_scaler.growth_interval=2000 ...
```

### TF32

On Ampere and newer NVIDIA GPUs, LeRobot makes float32 matmuls and cuDNN convolutions use TF32 by default (`--tf32=true`). Use `--tf32=false` to keep them in full float32 precision, and `--tf32=null` leaves PyTorch's default settings.
