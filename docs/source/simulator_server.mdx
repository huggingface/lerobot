# Simulation: in-process or served

A simulated environment can be driven in two ways:

- as a **batched env** (`--env.*`): many worlds of one task, stepped together in lockstep. `lerobot-eval` and evaluation during training use it.
- through a **sim robot** (`--robot.type=sim`): one simulated robot and its cameras exposed through the `Robot` interface. `lerobot-rollout`, `lerobot-record`, `lerobot-teleoperate` and `lerobot-replay` use it.

Either runs **in-process**, in the policy's Python environment, or **served** by `lerobot-env-server`, usually in its own Docker image, so that the simulator's dependencies never meet the policy's. Setting an `endpoint` selects the execution location. Both use the same simulator session and backend for observations, task outcomes and episode boundaries. Local calls run synchronously on the caller's thread; served calls run on the server.

## Evaluate a checkpoint

In-process, with the simulator installed next to LeRobot (see [LIBERO](./libero)):

```bash
lerobot-eval \
  --policy.path=lerobot/smolvla_libero \
  --policy.pretrained_revision=a24f1f380461b665158d52acd140152c79e8b36d \
  --policy.device=cuda \
  --env.type=libero --env.task=libero_spatial --env.task_ids='[0]' \
  --rename_map='{"observation.images.image": "observation.images.camera1", "observation.images.image2": "observation.images.camera2"}' \
  --eval.n_episodes=1 --eval.batch_size=1 \
  --output_dir=outputs/eval_libero
```

Served: start the server with the same environment (see [Serve an environment](#serve-an-environment)), and add its endpoint:

```bash
lerobot-env-server --docker --config=docker/sims/configs/libero.yaml
lerobot-eval ... --env.endpoint=tcp/127.0.0.1:7448
```

The server must run the environment the command describes: the same type, task, control conventions and simulated body (`robot_type`), or the evaluation refuses to start and lists the differences. Other options that differ (resolution, episode length) are logged as warnings.

Observation names come from the environment (`observation.images.<camera>`, `observation.state`). When a checkpoint was trained with other camera names, map them with `--rename_map`, as for any robot, and preserve each camera's identity even when several have the same shape. Placeholder cameras (`empty_cameras`) are a policy setting saved with the checkpoint; override it with `--policy.empty_cameras` only when needed.

Before the first step, every checkpoint input must exist in the environment after renaming, with matching state and action dimensions and RGB channel count. Image height and width may differ: policy preprocessing owns resizing. Controller conventions (delta vs absolute actions, rotation format) are not checked; use a checkpoint trained on the environment's convention.

The worlds of a batch advance in lockstep. A world that ends keeps its terminal observation until the next reset; stepping the others never restarts it. With `--eval.use_async_envs=true` (the default), each world runs in its own process, in-process or on the server, and the batch steps in parallel. A server admits up to `max_envs` worlds per batch (32 by default). `--env.encoding=jpeg` (or `--robot.env.encoding=jpeg`, with `jpeg_quality`, 90 by default) sends served camera frames as JPEG: smaller replies for a remote server and larger batches, at the cost of encoding time and lossy frames. On localhost, raw frames are faster.

## Run a sim robot

```bash
lerobot-rollout \
  --robot.type=sim --robot.env.type=libero --robot.env.task=libero_spatial --robot.task_id=0 \
  --policy.path=lerobot/smolvla_libero \
  --policy.pretrained_revision=a24f1f380461b665158d52acd140152c79e8b36d \
  --rename_map='{"observation.images.image": "observation.images.camera1", "observation.images.image2": "observation.images.camera2"}' \
  --device=cuda --fps=20 --inference.type=sync \
  --display_data=true --display_mode=rerun \
  --return_to_initial_position=false --play_sounds=false
```

- `--robot.env.*` takes the same options as `--env.*` in evaluation. EnvHub environments are `--robot.env.type=envhub --robot.env.hub_path=<user/repo> --robot.env.trust_remote_code=true`.
- `--robot.env.endpoint=tcp/...` drives the world on an env server instead, as `--env.endpoint` does for a batched env. The robot checks that the server runs that environment.
- Both local and served SimRobot advance exactly one control interval per `send_action()`. Observation reads and holds never advance physics.
- Existing loop timers provide pacing, including keyboard/gamepad teleoperation. Blocking inference, rendering or network calls slow simulation relative to wall time: physics does not continue independently of the control loop. With RTC, prediction runs in the background and queued actions keep advancing simulation while that loop runs.
- `--fps` must equal the environment's control rate, and `--interpolation_multiplier` must be 1; rollout refuses unsupported rates or interpolation.

`SimRobot` adapts one robot inside a task environment; it is not the environment itself. The native environment owns physics, the scene, objects and task outcomes. Swap `--robot.type=sim --robot.env.*` for the real follower's `--robot.*` when the observation/action contracts match. A teleoperator drives it through the normal processors; its commands must match the simulated controller's names and units. `lerobot-record` stores the declared body as the dataset's `robot_type` (`panda` for LIBERO), or `sim` when it declares none. The Robot camera `image` is recorded and admitted as `observation.images.image`, including for single-camera environments.

The episodic rollout strategy resets the simulator between episodes and stops on termination or truncation. An explicit task instruction uses the ordinary rollout configuration; otherwise the policy follows the simulator's task description. Demonstration recording uses `--dataset.single_task`, as on hardware. In interactive mode, an instruction set with `/subtask` survives the simulator reset of the next `/start`.

`SimRobot.reset_episode(seed=...)` resets the whole task environment, including the robot and objects, and refreshes cached observations and episode status. This is not a robot homing command. `--robot.seed` seeds the initial reset; later unseeded resets continue the simulator's RNG. The calling workflow clears policy queues and stateful processors at the episode boundary; `reset_episode()` does not own those components. `episode_status` and `task_description` expose the environment's task information. These are simulation-specific additions, not requirements on the base `Robot`. Human takeover does not reset the episode.

Feature discovery reads declared spaces without sampling, resetting, or stepping. Any environment constructed to discover its spaces is closed immediately; cached features remain available after disconnecting. The initial Robot interface supports a named 1-D state vector and RGB cameras; extra numeric observations are rejected rather than silently discarded. Batched evaluation can still use additional declared arrays. Native integrations own simulator-specific observation conversions, including LIBERO's orientation and state conventions.

Automatic-reset wrappers are unsupported. Integrations must expose explicit reset and retain the terminal observation. Known automatic-reset wrappers are rejected, and returned `final_observation`/`final_obs` markers cause an error instead of recording the next episode's initial state as the previous result.

Episode limits are read through Gym wrappers or the environment's specification. An unknown limit remains unknown: LeRobot does not silently end the task at 500 steps. Scalar workflows still honor native termination/truncation and their configured duration. Benchmark evaluation requires a declared limit, such as `gymnasium.wrappers.TimeLimit`.

Use the standard LeRobot teleoperation, recording and rollout entry points. Teleoperation mappings belong in the normal action processors; there is no separate per-environment CLI. RL/HIL-SERL is unchanged.

For remote inference, keep the same `--robot.*` options and replace the local policy and inference options with:

```bash
--inference.type=remote \
--inference.endpoint=tcp/127.0.0.1:7447 \
--inference.deployment=libero \
--inference.semantics=libero-delta-v1
```

Start the policy server separately using [remote inference setup](./remote_inference). Its schema must match the robot's observations after `--rename_map`. `docker/sims/policy_libero.yaml` provides the LIBERO policy-server configuration. Omit `--policy.path` from the rollout command because the policy server loads the checkpoint. For local RTC, use `--inference.type=rtc` with the policy's RTC settings.

### RTC in simulation

Local RTC uses the same inference engine, processors and rollout dispatch helper as on a physical robot. Use a checkpoint that supports the requested RTC mode and matches the simulated controller, with `--inference.type=rtc --inference.rtc.enabled=true`. Keep the rollout FPS equal to the simulator's control rate and `--interpolation_multiplier=1`. Trained RTC additionally requires a checkpoint declaring its supported delay range; changing the runtime flag does not train that capability.

The RTC worker predicts the next chunk while the control loop executes the current queue. Each dispatched action advances one simulation interval. If startup has no actions, the queue is exhausted, or the control loop stalls, the explicitly stepped world stays frozen. A sim hold is not a physical controller holding a moving body. This mode tests RTC integration, not hardware-like wall-clock dynamics.

The simulator supports explicit stepping only. Continuous wall-clock physics is not supported.

SimRobot hold leaves the explicitly stepped world frozen, for every controller. A terminal result stays cached until an explicit reset; another action after episode end is rejected. Simulator failures propagate to rollout shutdown. Remote timeouts do not imply a command was not executed: requests are not retried.

## Serve an environment

From a LeRobot source checkout (the image is built from it), run from the repository root:

```bash
lerobot-env-server --docker --config=docker/sims/configs/libero.yaml
```

`--docker` uses `docker/sims/compose.server.yaml`, selects the image from `sim.type`, mounts the effective YAML, and publishes localhost port 7448. Swap the YAML to select another simulator. Each simulator's control rate, action convention and component names come from `src/lerobot/sims/conventions.py`, so a YAML only names the task and the simulator's options.

`--set` overrides keys of the YAML (values parsed as YAML) and leaves the file unchanged:

```bash
lerobot-env-server --docker --config=docker/sims/configs/libero.yaml \
  --set sim.kwargs.gym_kwargs.observation_height=256 \
  --set sim.kwargs.gym_kwargs.observation_width=256
```

The effective configuration is kept in a temporary cache for container restarts; rerun the command after a host reboot. Switching configuration recreates the server and ends active sessions. The image is built when missing; add `--build` to rebuild it after changing the simulator or LeRobot source, or `--stop` to shut down the server. The container requires Docker GPU access for EGL rendering. [EnvHub](./envhub) repositories are served with `--envhub=<user/repo>`; see [EnvHub and the simulator server](./envhub#envhub-and-the-simulator-server).

Without `--docker`, the same command runs the server in the current environment: install the simulator's native dependencies in an isolated environment, install LeRobot with `--no-deps`, and install `docker/sims/requirements.txt`.

LIBERO runtime images use converted NumPy initial-state files. The image build converts trusted upstream assets with `scripts/ci/convert_sim_assets.py`; the server rejects missing converted files. RoboTwin and RoboMME require their own torch for native planning and ManiSkill, respectively; their torch installations are isolated from the policy environment.

Server requests are never retried. After an ambiguous timeout, the client fails; close it and open a new session.
