# Motors

`SerialMotorsBus` is the low-level interface to a chain of Feetech or Dynamixel servos on a serial bus. Robots use it
to read positions and write goal positions; you rarely touch it directly unless you are adding hardware. Each motor's
model is looked up in [rustypot](https://github.com/pollen-robotics/rustypot), which holds the control tables and the
facts that differ between families, and also owns the serial port. `FeetechMotorsBus` and `DynamixelMotorsBus` are
deprecated aliases of it, kept for one release.

### Migrating from the SDK-based buses

The aliases keep the class names, not the old SDK attributes and model tables:

- `bus.model_resolution_table[model]` becomes `bus.resolution(model)`; the other model tables (`model_ctrl_table`,
  `model_number_table`, ...) are now rustypot's servo definitions.
- Operating modes are selected by name, `bus.set_operating_mode("position")`, instead of writing an `OperatingMode`
  value to the `Operating_Mode` register.
- The SDK port and packet handlers are no longer exposed: rustypot owns the serial port.
- `protocol_version` is ignored: each motor's model gives its protocol.

See [Bring Your Own Hardware](../integrate_hardware) for adding a new bus, and
[Updating Feetech Firmware](../feetech) and [Damiao Motors and CAN Bus](../damiao) for device-specific notes.

## Register names

`SerialMotorsBus.read`, `write`, `sync_read`, and `sync_write` use generated register-name types.
A type checker such as mypy rejects misspelled names before you connect the robot:

```python
from lerobot.motors import SerialMotorsBus


def read_position(bus: SerialMotorsBus) -> int | float:
    return bus.read("Present_Position", "elbow_flex")
    # "Unknown_Position" produces a type error.
```

`RegisterName` includes lowercase, uppercase, and title-case spellings from rustypot's servo definitions.
The bus still matches names without case at runtime. The type lists names across all supported models;
rustypot checks whether the selected motor supports the register.

For a dynamic name, a custom register, or another case pattern, use `CustomRegister` explicitly:

```python
from lerobot.motors import CustomRegister, SerialMotorsBus


def read_register(bus: SerialMotorsBus, name: str) -> int | float:
    return bus.read(CustomRegister(name), "elbow_flex", normalize=False)
```

`CustomRegister` leaves the string unchanged and bypasses the static name check. It does not add a register
to a servo definition. Ordinary code should use literal names so the type checker can detect typos.
Untyped callers keep the existing runtime behavior.

The generated file contains names only. It does not duplicate register addresses or control tables.
The snapshot uses the minimum supported rustypot release. Reproduce it from the repository root:

```bash
uv run --no-project --with rustypot==1.11.0 scripts/generate_motor_registers.py
uv run --no-project --with rustypot==1.11.0 scripts/generate_motor_registers.py --check
```

If the minimum rustypot version changes, update the pinned command and regenerate the file.
Use `CustomRegister` for names from newer definitions until the snapshot includes them.

`MotorsBusBase` takes a register-name type parameter. A custom bus that accepts arbitrary strings can
inherit from `MotorsBusBase[str]`, as the CAN buses do.

## DriveMode

`DriveMode` has two members, `NON_INVERTED = 0` and `INVERTED = 1`. Use `.value` where the integer is expected, in a
`Drive_Mode` register or in `MotorCalibration.drive_mode`:

```python
bus.write("Drive_Mode", "elbow_flex", DriveMode.INVERTED.value)
```
