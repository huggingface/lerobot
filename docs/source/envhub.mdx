# EnvHub: Share a Simulator on the Hub

An EnvHub environment is a Hugging Face Space with an `env.py` that builds a [Gymnasium](https://gymnasium.farama.org) environment following LeRobot's conventions (see [The environment](#the-environment)). That file is the whole integration: no pull request to LeRobot, no package to publish. Once it is on the Hub, anyone can:

- **evaluate** a policy on it with `lerobot-eval`,
- **drive it as a robot** with `lerobot-rollout`, `lerobot-record`, `lerobot-teleoperate` and `lerobot-replay`, swappable with the real robot it simulates,
- run it **locally**, in their own Python environment, or **served** by `lerobot-env-server` in a Docker image built from the repository, so that the simulator's dependencies never meet the policy's.

This page shows how to use an EnvHub environment, then everything needed to write and publish one. [Simulation](./simulation) covers the commands in depth; [Adding a benchmark](./adding_benchmarks) is for the benchmarks LeRobot maintains in its CI.

## Use an EnvHub environment

Browse published environments in the [EnvHub environments collection](https://huggingface.co/collections/lerobot/envhub-environments), or browse [Spaces tagged `envhub`](https://huggingface.co/spaces?search=envhub).

The commands below use `spaces/my-org/my-env@<commit>`. Replace it with the Space ID and commit you want to run. The robot and camera options illustrate an SO-101 environment; adapt them to your environment and policy.

### Serve it

From a LeRobot source checkout (the image is built from it), with Docker and GPU access for its containers:

```bash
lerobot-env-server \
  --envhub=spaces/my-org/my-env@<commit> \
  --trust_remote_code=true --docker=true
```

This builds an image with the repository and its `requirements.txt` on first use, and starts the server on `localhost:7448`. `--trust_remote_code=true` is your consent to run the repository's code, in the container: read `env.py`, `requirements.txt` and `packages.txt` first, and pin the commit you read, so that you run exactly that code and results stay reproducible. Without it, the server refuses to start. The client side needs the `remote` extra (`pip install 'lerobot[remote]'`).

The server can as well run on another machine, such as a GPU workstation or a cloud instance, while the policy runs on yours: see [Where the server runs](./simulation#where-the-server-runs).

### Evaluate a policy

```bash
lerobot-eval \
  --policy.path=<your SO-101 checkpoint> \
  --env.type=envhub --env.hub_path=spaces/my-org/my-env@<commit> \
  --env.server.endpoint=tcp/127.0.0.1:7448 \
  --rename_map='{"observation.images.front": "observation.images.camera1", "observation.images.wrist": "observation.images.camera2"}' \
  --eval.n_episodes=10 --eval.batch_size=1
```

Observations reach the policy as `observation.images.<camera>` and `observation.state`; `--rename_map` maps them to the names the checkpoint was trained with.

### Drive it as a robot

The same environment is a robot: `--robot.type=sim`, with the environment options under `--robot.env.*`. Teleoperate it with a real SO-101 leader arm, as you would the real follower:

```bash
lerobot-teleoperate \
  --robot.type=sim --robot.env.type=envhub --robot.env.hub_path=spaces/my-org/my-env@<commit> \
  --robot.env.server.endpoint=tcp/127.0.0.1:7448 \
  --teleop.type=so101_leader --teleop.port=/dev/ttyACM0 --teleop.id=my_leader \
  --fps=30 --display_data=true
```

`lerobot-record` takes the same options to record a dataset, and `lerobot-rollout` to run a policy. The dataset records the body the environment declares, here `so_follower`, as the real follower would. See [Run a sim robot](./simulation#run-a-sim-robot) for episodes, rates and recording.

### Run it locally

Without `--env.server.endpoint` (or `--robot.env.server.endpoint`), the environment runs in your process. Install its `requirements.txt` next to LeRobot, and add `--env.trust_remote_code=true` (`--robot.env.trust_remote_code=true`): your process runs the repository's `env.py`. Served, your process never runs it, so the client needs no consent: the server's `--trust_remote_code=true` covers it.

### From a local folder

A folder holding `env.py` works everywhere a Hub repository does, for an environment you are writing or a clone you have read: `--env.hub_path=./my-env`, `--robot.env.hub_path=./my-env`, `--envhub=./my-env`. It needs the same consent, since it is code all the same. To serve it without building an image, drop `--docker=true`: the server then runs in your current Python environment, with the folder's `requirements.txt` installed there.

```bash
lerobot-env-server --envhub=./my-env --trust_remote_code=true                  # in your Python environment
lerobot-env-server --envhub=./my-env --trust_remote_code=true --docker=true    # in an image built from the folder
```

Published examples: [SO-101 tabletop in MuJoCo](https://huggingface.co/spaces/lerobot/so101-tabletop-mujoco) includes an interactive CPU demo; [SO-101 tabletop in Isaac Sim](https://huggingface.co/spaces/lerobot/so101-tabletop-isaac) includes a recorded rollout and setup instructions.

## Create an environment

### The repository

| File               | Required               | Content                                                                                                                        |
| ------------------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `env.py`           | yes                    | `make_env`, the environment, and optionally `LEROBOT_SIM`                                                                      |
| `requirements.txt` | no                     | Python packages `env.py` needs, installed in the server image                                                                  |
| `packages.txt`     | no                     | Ubuntu packages, one per line, installed in the server image                                                                   |
| `index.html`       | yes for a static Space | A page presenting the environment and explaining how to run it                                                                 |
| `README.md`        | yes                    | What the environment simulates, its observations, actions, task, rewards and episode end, the commands to run it, its licenses |
| anything else      | no                     | Scenes, robot models, textures, configs: `env.py` finds them next to itself, in every mode                                     |

Publish new environments as Spaces, choosing the SDK that fits your presentation: [Static HTML](https://huggingface.co/docs/hub/spaces-sdks-static) for a documentation page, [Gradio](https://huggingface.co/docs/hub/spaces-sdks-gradio) for an interactive demo, or [Docker](https://huggingface.co/docs/hub/spaces-sdks-docker) for a custom application. Every Space should explain the task, robot, installation and evaluation commands, and link to the source and licenses. Rollout videos, camera views, task examples, datasets, checkpoints and reference results make the environment easier to understand and reuse. A live simulator demo is optional.

A static page does not execute `env.py` or need GPU compute; an interactive app can run the simulator if its runtime and hardware support it. In every case, LeRobot downloads the same Space repository and runs the environment locally or on a simulator server, exactly as for a model repository. Publishing a Docker Space does not automatically make its web URL compatible with LeRobot's env-server protocol, and `--docker=true` still builds LeRobot's standard simulator image rather than the Space's Dockerfile.

See [Publish](#publish) for a static Space example and upload commands; Gradio and Docker Spaces are equally valid EnvHubs.

The README's `sdk` selects how Spaces builds the app. With `sdk: docker`, the root `Dockerfile` belongs to the Space demo. Keep any separate simulator-server recipe at a distinct path such as `deploy/Dockerfile.envhub`, and select it explicitly with `docker build -f deploy/Dockerfile.envhub .`. With `sdk: static` or `sdk: gradio`, including a Dockerfile does not select the Docker SDK.

### Python and dependencies

LeRobot needs Python 3.12 or newer, and so does your environment: locally, `env.py` runs in LeRobot's process, and the server image runs Ubuntu 24.04's Python 3.12. A simulator that only supports an older Python (for example Isaac Sim 5 and Isaac Lab 2, on Python 3.11) runs neither way; use a release that supports Python 3.12 (Isaac Sim 6 and Isaac Lab 3, as [RoboLab](./robolab) does).

The server image holds only what the server needs: neither torch nor the rest of LeRobot. List everything `env.py` imports in `requirements.txt`, torch included if your simulator needs it, and pin versions.

### `make_env`

`env.py` must define `make_env(n_envs: int = 1, use_async_envs: bool = False, **kwargs)`, which returns `{suite_name: {task_id: vector_env}}`, each vector env holding `n_envs` environments of that task:

```python
def make_env(n_envs: int = 1, use_async_envs: bool = False, **kwargs):
    factory = partial(MyEnv, **kwargs)
    vector_cls = gym.vector.AsyncVectorEnv if use_async_envs else gym.vector.SyncVectorEnv
    return {"my_task": {0: vector_cls([factory] * n_envs)}}
```

- Build each vector env from per-environment factories, as above, and return it unwrapped: LeRobot takes the factories and runs the environments itself (see [Batches](#batches)). A custom vector wrapper or subclass is refused rather than silently dropped. A single `gym.Env` is also accepted, as one suite with task ID 0.
- Several suites or task IDs make a multi-task benchmark: `lerobot-eval` reports a success rate per task, per suite and overall. A sim robot runs the suite named by `--robot.env.task` (the first by default), and the task given by `--robot.task_id`.
- `kwargs` are the environment's own options. Users pass them with `--env.make_env_kwargs='{"episode_length": 900}'` (`--robot.env.make_env_kwargs` for a sim robot); a server takes them with `--sim.kwargs='{make_env_kwargs: {episode_length: 900}}'`.
- `env.py` is imported once per process, so it can keep process-wide state, such as a simulator application that can only start once (Isaac Sim's `SimulationApp`).

### The environment

Each environment is a `gym.Env` that follows these conventions. A stock Gymnasium environment usually doesn't: CartPole's observation is a flat vector and its action is discrete, so LeRobot refuses it. Wrap such an environment to return this observation dictionary and a continuous action `Box`.

| What                 | Contract                                                                                                                                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Observation          | A dict of NumPy arrays: `pixels` (one HWC `uint8` RGB image, or a dict of them, one per camera), `agent_pos` (the robot's state) and optionally `environment_state`. Other arrays pass through |
| Action               | A one-dimensional continuous `Box`                                                                                                                                                             |
| `task_description`   | The language instruction given to the policy (falls back to `task`)                                                                                                                            |
| `_max_episode_steps` | The step limit, after which LeRobot truncates the episode (500 if absent)                                                                                                                      |
| `step()` return      | `terminated` when the episode ends (success or failure), `truncated` when it is cut short                                                                                                      |
| `info["is_success"]` | Whether the task is achieved, on every `step()`                                                                                                                                                |
| `info["metrics"]`    | Optional: other numbers to report, `{name: float}`; `lerobot-eval` keeps them per episode, taken at the step it ended                                                                          |

LeRobot maps the observation to `observation.images.<camera>` (`observation.image` for a single unnamed image), `observation.state` and `observation.environment_state`. Convert your simulator's outputs to these conventions inside the environment: camera images upright, state in the units and order of your actions where they share joints.

If your simulator allocates GPU or EGL contexts, create them on the first `reset()` rather than in `__init__`, so that an environment built in a worker process does not inherit stale handles.

### `LEROBOT_SIM`

A module-level dictionary in `env.py` that describes the environment. It applies locally and when served, and every key is optional:

| Key            | Meaning                                                  | Default                            |
| -------------- | -------------------------------------------------------- | ---------------------------------- |
| `fps`          | Control rate: `step()`s per second of simulated time     | `30`                               |
| `control_mode` | Action convention: `position`, `delta` or `eef_pose`     | `"position"`                       |
| `semantics`    | Name of the observation and action conventions           | `"envhub-v1"`                      |
| `state_names`  | Names of the `observation.state` components, in order    | `state_0`, `state_1`, ...          |
| `action_names` | Names of the action components, in order                 | `command_0`, `command_1`, ...      |
| `robot_type`   | Simulated body, recorded as the `robot_type` of datasets | none (datasets record `sim_robot`) |

Declare it whenever the defaults do not match your environment. An unknown key is an error, naming the closest valid one. A server's `--sim.*` options override it, e.g. `--sim.fps=15`.

To make an environment a twin of a real robot LeRobot supports, use that robot's names, units and `robot_type`. A teleoperator then drives it as it drives the real follower, datasets recorded in simulation and on hardware match, and a checkpoint trained on one runs on the other. For an SO-101, that is `shoulder_pan.pos` ... `gripper.pos`, in degrees with the gripper from 0 to 100, and `robot_type: "so_follower"`. When LeRobot has no class for your robot, pick a short snake_case `robot_type` (`panda`, `sawyer`).

### A complete example

A point to move onto a target, with no dependency beyond Gymnasium and NumPy. It satisfies everything above; copy it as a starting point:

```python
# env.py
from functools import partial

import gymnasium as gym
import numpy as np
from gymnasium import spaces

JOINTS = ["x.pos", "y.pos"]

# How LeRobot describes this environment, locally and when served. Every key is optional.
LEROBOT_SIM = {
    "fps": 10,
    "control_mode": "position",
    "state_names": JOINTS,
    "action_names": JOINTS,
}


class ReachEnv(gym.Env):
    """Move a point to a target on a plane. The action is the point's next position, in [-1, 1]."""

    metadata = {"render_modes": ["rgb_array"], "render_fps": 10}

    def __init__(self, image_size: int = 96, episode_length: int = 100):
        super().__init__()
        self.image_size = image_size
        self._max_episode_steps = episode_length
        self.task = "reach"
        self.task_description = "Move the blue point onto the red target."
        image = spaces.Box(0, 255, (image_size, image_size, 3), np.uint8)
        self.observation_space = spaces.Dict(
            {"pixels": spaces.Dict({"top": image}), "agent_pos": spaces.Box(-1, 1, (2,), np.float32)}
        )
        self.action_space = spaces.Box(-1, 1, (2,), np.float32)

    def reset(self, seed=None, options=None):
        super().reset(seed=seed)
        self.point = self.np_random.uniform(-1, 1, 2).astype(np.float32)
        self.target = self.np_random.uniform(-1, 1, 2).astype(np.float32)
        return self._obs(), {"is_success": False}

    def step(self, action):
        self.point = np.clip(np.asarray(action, np.float32), -1, 1)
        distance = float(np.linalg.norm(self.point - self.target))
        success = distance < 0.1
        info = {"is_success": success, "metrics": {"distance": distance}}
        # Ends on success (terminated); LeRobot truncates the episode after _max_episode_steps.
        return self._obs(), -distance, success, False, info

    def _obs(self):
        image = np.full((self.image_size, self.image_size, 3), 255, np.uint8)
        for xy, color in ((self.target, (220, 40, 40)), (self.point, (40, 40, 220))):
            col, row = ((xy + 1) / 2 * (self.image_size - 1)).astype(int)
            image[max(row - 3, 0) : row + 4, max(col - 3, 0) : col + 4] = color
        return {"pixels": {"top": image}, "agent_pos": self.point.copy()}


def make_env(n_envs: int = 1, use_async_envs: bool = False, **kwargs):
    """The EnvHub entry point. `kwargs` come from --env.make_env_kwargs."""
    factory = partial(ReachEnv, **kwargs)
    vector_cls = gym.vector.AsyncVectorEnv if use_async_envs else gym.vector.SyncVectorEnv
    return {"reach": {0: vector_cls([factory] * n_envs)}}
```

Find community environments in [EnvHub Spaces](https://huggingface.co/spaces?search=envhub). Each Space should document its simulator, installation requirements, observations and actions, and provide a page or demo showing what to expect.

### Batches

`lerobot-eval --eval.batch_size=N` runs N environments of a task at once, and `make_env` receives `n_envs=N`; a sim robot runs one. A batch is stepped in one of two ways.

**LeRobot steps a batch of single environments**, the default and what most simulators need (MuJoCo, PyBullet, ...). Write a `gym.Env` that simulates one environment, and return `n_envs` factories of it from `make_env`, as above. LeRobot builds the environments from the factories: with `--eval.use_async_envs=true` (the default), each one runs in its own worker process and the batch steps in parallel; with `false`, they all run in one process, one after the other. LeRobot uses only the factories, so which vector class `make_env` builds them into makes no difference.

**Your simulator steps the whole batch**, when it holds every environment in one world and steps them at once, as GPU simulators such as Isaac Lab do. Define `vector_env_fns` in `env.py` as well, returning one factory per task, each building a vector env of `n_envs` environments; LeRobot then uses it in place of `make_env`:

```python
from functools import partial


def vector_env_fns(task: str, n_envs: int, **make_env_kwargs):
    # {suite_name: {task_id: factory}}, each factory building one vector env of n_envs envs
    return {"suite_1": {0: partial(MyBatchedEnv, n_envs, "Task1"), 1: partial(MyBatchedEnv, n_envs, "Task2")}}
```

Each vector env must have `num_envs == n_envs` and must not autoreset (`metadata["autoreset_mode"] = gym.vector.AutoresetMode.DISABLED`). It returns batched observations in the format above, takes one seed per environment in `reset(seed=[...])`, and reports `info["is_success"]` per environment. `--env.make_env_kwargs` are passed to it. Since it already steps the whole batch, evaluate with `--eval.use_async_envs=false`: a worker process would only copy every batch between processes, and a server would build the simulator a second time, in the worker.

`vector_env_fns` also suits a benchmark with many tasks: `make_env` builds the environments of every task when it is called, while only the factories of the tasks that run are called.

## Test before publishing

Every step takes the local folder that holds `env.py` in place of a Hub repository.

1. Build the environments as LeRobot does, and check the observation keys, shapes and task:

   ```python
   import numpy as np

   from lerobot.envs import HubEnvConfig, make_env

   # LeRobot's make_env, which calls the make_env of your env.py
   envs = make_env(HubEnvConfig(hub_path="./my-env", trust_remote_code=True), n_envs=2)
   suite = next(iter(envs))
   env = envs[suite][0]
   obs, info = env.reset(seed=0)
   print({key: (value.shape, value.dtype) for key, value in obs.items()})
   print(env.call("task_description"))
   obs, reward, terminated, truncated, info = env.step(np.zeros(env.action_space.shape, np.float32))
   print(reward, terminated, truncated, info["is_success"])
   env.close()
   ```

2. Check it as a robot: the state and action names, and the camera views:

   ```python
   from lerobot.envs.configs import HubEnvConfig
   from lerobot.robots.sim_robot import SimRobot, SimRobotConfig

   robot = SimRobot(SimRobotConfig(env=HubEnvConfig(hub_path="./my-env", trust_remote_code=True)))
   print(robot.robot_type, list(robot.action_features))
   robot.connect()
   observation = robot.get_observation()
   robot.send_action({name: observation[name] for name in robot.action_features})
   robot.disconnect()
   ```

   With a teleoperator whose actions match yours, `lerobot-teleoperate --robot.type=sim --robot.env.type=envhub --robot.env.hub_path=./my-env --robot.env.trust_remote_code=true ... --display_data=true` shows the cameras in Rerun as you drive it.

3. Serve it from the folder, which builds the image from your `requirements.txt` and `packages.txt`, then run the same checks against it with `--env.server.endpoint=tcp/127.0.0.1:7448`:

   ```bash
   lerobot-env-server --envhub=./my-env --trust_remote_code=true --docker=true
   ```

   `--build=true` rebuilds only what changed: the apt packages when `packages.txt` changes, the requirements when `requirements.txt` changes, and otherwise just the repository's files.

## Publish

Create a Space with your chosen SDK, and keep `env.py`, its dependencies and assets in the same repository as the presentation or demo. The following example uses Static HTML; for Gradio or Docker, replace `index.html` with your app entry point or Dockerfile and use the matching SDK configuration:

```text
my-env/
├── README.md            # Space metadata, usage and licenses
├── index.html           # Environment page
├── env.py               # LeRobot entry point
├── requirements.txt     # Simulator dependencies, if needed
├── packages.txt         # System dependencies, if needed
└── assets/              # Robot models, scenes and textures
```

Add the Space configuration to the top of `README.md`, followed by your environment documentation. Set the license to the one that applies to your code:

```yaml
---
title: My robotics environment
emoji: 🤖
colorFrom: blue
colorTo: green
sdk: static
app_file: index.html
tags: [lerobot, envhub, robotics, simulation]
license: apache-2.0
---
```

A minimal `index.html` can start with the task description and a link to your usage guide; expand it with videos and examples as the environment develops:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>My robotics environment</title>
  </head>
  <body>
    <h1>My robotics environment</h1>
    <p>An SO-101 arm picks up cubes and places them in a box.</p>
    <p>
      <a href="https://huggingface.co/spaces/my-org/my-env/blob/main/README.md"
        >Installation, evaluation and licenses</a
      >
    </p>
  </body>
</html>
```

Replace the example name, task and README link with yours. For this static example, upload the folder using the Hub CLI (`--sdk gradio` or `--sdk docker` for the other SDKs):

```bash
hf auth login
hf repos create my-org/my-env --type space --sdk static
hf upload my-org/my-env ./my-env . --repo-type space
```

Then serve the environment from the Space repository (the Space's web app does not need to run a simulator):

```bash
lerobot-env-server --envhub=spaces/my-org/my-env@<commit> --trust_remote_code=true --docker=true
```

Use the same `spaces/my-org/my-env@<commit>` for `--env.hub_path` or `--robot.env.hub_path`. A bare `my-org/my-env` is also detected automatically; see [Hub paths](#hub-paths). After publishing:

- Note the commit, and use it in your README's commands: users run exactly what you tested.
- State in the README the licenses of everything the repository includes (robot models, scenes, textures), and a reference result if you have one: a checkpoint, its revision, the `lerobot-eval` command and the success rate it gets.
- Add `tags: [lerobot, envhub]` to the README's metadata, so the environment can be found on the Hub.
- To have it listed in the [EnvHub environments collection](https://huggingface.co/collections/lerobot/envhub-environments), open an issue on [LeRobot's GitHub](https://github.com/huggingface/lerobot/issues) with a link to the repository.

Updates are new commits: users pinned to an older commit keep running the code they reviewed.

## Reference

### Hub paths

`--env.hub_path` (and `--envhub` for the server) take:

| Pattern              | Loads                               | Example                              |
| -------------------- | ----------------------------------- | ------------------------------------ |
| `spaces/user/repo`   | `env.py` from a Space               | `spaces/my-org/my-env`               |
| `user/repo`          | Automatically detect the repo type  | `my-org/my-env`                      |
| `user/repo@revision` | `env.py` at a commit, branch or tag | `spaces/my-org/my-env@<commit>`      |
| `user/repo:path`     | Another file                        | `my-org/my-envs:envs/task_a.py`      |
| `user/repo@rev:path` | Another file at a revision          | `my-org/my-envs@v1.0:envs/task_a.py` |
| `./folder`           | `env.py` in a local folder          | `./my-env`                           |

<Tip>
  **Spaces are preferred for new EnvHub environments.** Existing environments in
  model repositories remain fully supported, including their current commands
  and pinned revisions. No migration is required. Spaces add a page or
  interactive demo to help people discover and try your environment. Use
  `models/user/repo` if you need to select a model repository explicitly.
</Tip>

Bare `user/repo` paths try a model repository first, then a Space if no accessible model repository exists. This preserves existing EnvHub commands and commit pins. If both types share a name, the model repository wins: use `spaces/user/repo` or `models/user/repo` to select one explicitly. The prefixes also work with revisions and custom files, e.g. `spaces/my-org/my-env@v1.0:envs/task_a.py`.

### Versions

An environment's versions are its Hub commits. A revision after `@` (a commit, a branch or a tag) selects one, in your process and on the server:

- **In your process**, the repository at that revision is downloaded and cached. Without a revision, each run follows the latest commit of `main`.
- **On the server**, `--envhub=spaces/user/repo@<revision>` builds the image from that revision's files, and each revision gets its own image. Without a revision, the image holds the commit that was latest when it was built, until `--build=true` rebuilds it from the latest one.
- **Tag releases** so users can pin a name rather than a hash, and keep `main` for development. Pin a commit for papers and comparisons: unlike a tag or a branch, it cannot move.

### Options

| Option                                        | Meaning                                                                                             |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `--env.type=envhub`                           | An EnvHub environment (`--robot.env.type=envhub` for a sim robot)                                   |
| `--env.hub_path`                              | The repository, see [Hub paths](#hub-paths)                                                         |
| `--env.trust_remote_code`                     | Consent to run the repository's code in your process; not needed when served                        |
| `lerobot-env-server --trust_remote_code=true` | Consent to run the repository's code on the server, required to serve it, from `--envhub` or a YAML |
| `--env.make_env_kwargs`                       | Keyword arguments for `make_env`; when served, set them on the server instead                       |
| `--env.server.endpoint`                       | Run the environment on an env server; see [Simulation](./simulation) for the other server options   |
| `lerobot-env-server --envhub=<path>`          | Serve a repository; with `--docker=true`, in an image built from it                                 |
| `lerobot-env-server --sim.kwargs=...`         | The server's `make_env` options, e.g. `'{make_env_kwargs: {episode_length: 900}}'`                  |
| `lerobot-env-server --sim.<key>=...`          | Override a `LEROBOT_SIM` value, e.g. `--sim.fps=15`                                                 |

### Security

Running an EnvHub environment runs its code, with your permissions. LeRobot never runs it without your explicit consent: `trust_remote_code` in your process, `--trust_remote_code=true` on the server. Before giving it:

1. Read `env.py`, `requirements.txt` and `packages.txt`.
2. Pin the commit you read.
3. Prefer serving it: in its container, the code sees its image and the server's configuration, not your files. The container shares your host network.

### Troubleshooting

| Error                                                                        | Fix                                                                                                                        |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `Refusing to run the EnvHub environment`                                     | Add `--env.trust_remote_code=true` (`--robot.env.trust_remote_code=true`) after reading the code, or serve the environment |
| `failed to import because the dependency '<name>' is not installed`          | Install the repository's `requirements.txt` next to LeRobot, or serve the environment                                      |
| `requires an unwrapped SyncVectorEnv or AsyncVectorEnv`                      | Return the vector env built from factories, without wrappers                                                               |
| `LEROBOT_SIM has unknown keys`                                               | Use the keys listed in [`LEROBOT_SIM`](#lerobot_sim); the error names the closest one                                      |
| `The env server at ... runs another environment than this command describes` | The server runs another environment than `--env.*` describes; pass the same options, or restart the server with yours      |
| `A sim robot needs an observation.state feature with component names`        | Return `agent_pos` in the observation                                                                                      |
| `images must be HWC uint8 with three channels`                               | Convert camera images to height x width x 3, `uint8`                                                                       |
