# Steerable ReBot with a high-level vision-language planner

Train WALL-OSS-Flow to follow diverse steering commands, then use Astra to choose
those commands from images. LeRobot's existing rollout controller, inference engine,
processors, and language runtime execute the VLA. The planner only supplies text.

The experiment files live in `examples/rebot_agent/`. `astra_goal.md` is the reusable
goal prompt; `training.json` and `train_wall_oss_flow.py` configure the first fine-tune.

## Relationship to Steerable Policies

Follow [the paper](https://arxiv.org/html/2602.13193v3) and
[Bridge implementation](https://github.com/steerable-policies/steerable-policies-bridge),
reviewed at `b95286e7823e1f05e490a96ae98f7a3e3ac396f8`.
Its `RLDSBatchTransform` finds the frame's subtask, samples a command from the
associated list, and uses it for ordinary behavioral cloning. The architecture
does not require a second source of robot actions.

The paper extracts objects with Molmo, propagates masks with SAM2, localizes grippers
with DETR, derives motion language, decomposes episodes into subtasks, and composes
multiple equivalent steering styles. It uses a VLM both to compose commands and, at
runtime, to select commands using observation/command history. The released Bridge
training code consumes precomputed annotations; it is not a complete ReBot extractor.

| Component           | ReBot implementation / current boundary                                                                                                |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| VLA and robot       | Existing WALL-OSS-Flow and bimanual ReBot support in main; adaptations from the paper's OpenVLA/Pi0.5 and WidowX                       |
| Semantic labels     | Existing timestamped dataset annotations and main's annotation reader/decoder                                                          |
| Visual grounding    | Staged Molmo/SAM2 extraction and DETR gripper fitting/extraction from reviewed per-arm boxes; trained extractors still need validation |
| Motion grounding    | `fk_motion.py` uses calibrated measured joints and main's `RobotKinematics`; actual URDF/calibration are required                      |
| Command composition | `prepare_steering.py` builds grounded template variants; a VLM paraphrasing stage is still an extension                                |
| Annotation review   | Astra inspects timestamped source images and proposed commands; accepted/uncertain/rejected results are saved                          |
| Training            | Fresh uniform sampling among reviewed alternatives on each visit; 20% overall tasks is our chosen mixture                              |
| Planning            | Astra through main's `/autosteer`, with bounded visual history; VLA remains the action controller                                      |

This is a paper-guided adaptation, not a completed reproduction. Configuring visual
styles does not generate their training labels. Start with the semantic baseline;
enable the richer model only after reviewing its grounded annotations.

## Training data and command contract

The source is `pepijn223/rebot_diverse_picking_100_annotated`, pinned to
`93c97807c46535745d0587d4296416bf2d4aa80d`. Keep the last ten episodes held out.
The semantic baseline uses `dataset.task_recipe` with 80% active subtask / 20% task.
The task adapter leaves observations, actions, and source annotations unchanged.

The source's sole canonical task says "blocks" and "green bin", which conflicts with
the pilot video and its object-specific subtask annotations. Both experiment conditions
therefore use "Pick up objects from the table and place them into the bin." for the
20% overall-task branch. This avoids imposing an unsupported object set or bin color;
it is an experiment recipe correction, not a rewrite of the source dataset. The
policy's `${task}` pass-through still receives the selected subtask or steering command.

The richer model takes a JSON `dataset.steering_manifest`. Each half-open interval
`[start_frame, end_frame)` uses episode-local frame indices, and has:

```json
{
  "version": 1,
  "source": { "repo_id": "owner/dataset", "revision": "PINNED_COMMIT" },
  "segments": [
    {
      "episode_index": 0,
      "start_frame": 0,
      "end_frame": 20,
      "review": {
        "verdict": "accepted",
        "reviewer": "REVIEWER_MODEL",
        "notes": "Visible evidence"
      },
      "commands": [
        {
          "style": "point",
          "text": "reach with the left gripper to",
          "camera": "observation.images.base",
          "image_size": [640, 480],
          "points": [[100, 200]],
          "evidence": {
            "extractor": "TRACKER_CHECKPOINT",
            "track_id": "object_1"
          }
        }
      ]
    }
  ]
}
```

This is a schema illustration, not annotations for the supplied dataset. Styles are
`subtask`, `motion`, `point`, `trace`, and `combination`. Visual commands keep ordered
points separately from wording. The renderer prefixes the camera and original image
size, then inserts the coordinates. Points refer to relevant targets; traces refer
to the gripper's path. Do not substitute one for the other.

Every command requires grounding provenance. Overlapping intervals, unreviewed
segments, out-of-image points, source revision mismatches, and missing sampled-frame
coverage fail explicitly. The loader checks visual dimensions against dataset metadata.
Image augmentations are disabled for this configuration because independent cropping
would invalidate coordinate labels. WALL-OSS's fixed image processing remains in use;
command coordinates consistently refer to the original named view at train and test.

Training samples uniformly from a frame's command list on every visit, using the
worker-seeded RNG, with 20% task conditioning. Evaluation selection is deterministic
per frame. Set task probability to zero for an all-steering ablation. This differs
from main's recipe blend alone, whose per-index choices repeat across visits.

## Prepare and review grounded features

`extract_visual.py` prepares original-size frames with main's reader/decoder, identifies
up to four task-relevant objects with MolmoE-1B-0924, points to them with Molmo-7B-D-0924,
and tracks the resulting seeds with SAM2.1. Each model is pinned to a Hub revision.
Run stages separately so only one extractor occupies GPU memory at a time. Preparation
needs dataset dependencies; model stages additionally need the models' dependencies
and SAM2. Molmo's remote code fails to load in the training stack's Transformers 5.5
(`all_tied_weights_keys` is missing). Use the separate pinned Molmo dependency overlay
for identification and pointing. Those stages consume exported frames and do not
import main's dataset/Hub stack. Preparation and VLA training keep LeRobot's lockfile.
The SAM2 reference code reviewed here is
`facebookresearch/sam2@2b90b9f5ceec907a1c18123530e92e794ad901a4`.

Place `source.json` in the downloaded dataset root with its `repo_id` and immutable
40-character `revision`. A partial download can add `"partial": true`. Extraction also
hashes actual source parquet and exported images. Start with a pilot:

```bash
uv run examples/rebot_agent/extract_visual.py prepare \
  --dataset-root /path/to/pinned_dataset --output outputs/rebot_visual \
  --episodes 0 1 2 3 4 --cameras observation.images.base --stride 15
# Inside a GPU allocation with annotation dependencies installed:
USE_TF=0 uv run --no-sync --with-requirements examples/rebot_agent/molmo-requirements.txt \
  examples/rebot_agent/extract_visual.py identify --output outputs/rebot_visual
USE_TF=0 uv run --no-sync --with-requirements examples/rebot_agent/molmo-requirements.txt \
  examples/rebot_agent/extract_visual.py point --output outputs/rebot_visual
uv run examples/rebot_agent/extract_visual.py track --output outputs/rebot_visual
uv run examples/rebot_agent/extract_visual.py filter-objects --output outputs/rebot_visual
```

Use stride 1 and all three cameras for full temporal extraction after inspecting the
pilot. Stages resume completed clip outputs and verify image hashes. Outputs preserve
raw Molmo responses, object IDs, source frame IDs, timestamps, masks, mask geometry,
and overlays. Identities are scoped to a clip and camera; association across cameras
or subtasks is not established. Missing/ambiguous points stay missing. Mask presence
is a prediction, not verified visibility; geometric diagnostics are not confidence.

If identification failed only because Molmo wrapped an object list in prose or omitted
quotes around names, run `extract_visual.py reparse-identify --output outputs/rebot_visual`
before resuming pointing. This CPU-only step keeps the raw response, model identity,
previous file hash and error, and parser hash. It changes only failed, unreviewed results
with no dependent points/tracks. Ambiguous lists remain failed; recovering syntax does
not verify that the named objects exist or are relevant.

The CPU-only `filter-objects` stage follows Appendix A-C's name-in-task heuristic,
using the annotated subtask for each clip. It writes `task_objects.json` beside the
untouched raw tracks and a `task_object_filter.json` summary. Matching ignores case
and punctuation but requires the complete object name at word boundaries. It does
not infer synonyms: a predicted "basket" does not match "bin". Excluded candidates,
original IDs, missing points/masks, timestamps and source hashes remain available.
An empty result for a return-home instruction is valid; it does not supply a target
for a pointing command. Any missing required pick/place object needs further grounding.

This filter cannot detect a plausible name pointing to the wrong object. In the first
five-episode ReBot pilot, a "black block" seed tracked the remote control while the
demonstrated small block moved into the bin. Other sampled tracks followed the tape
roll and green cloth from table to bin. Review seed identity and motion throughout
the clip; neither name matching nor a nonempty mask establishes action alignment.

For an instruction-named object omitted by the identifier, create a separate recovery
extraction after filtering the parent:

```bash
uv run examples/rebot_agent/extract_visual.py prepare-required \
  --parent outputs/rebot_visual --output outputs/rebot_bins --objects bin
# Run the existing point, track and filter-objects stages on outputs/rebot_bins.
```

This selects only matching instructions whose filtered candidates lack a grounded
point for the requested name. It copies and verifies the original frames, records
parent hashes, and explicitly marks identification as instruction-derived with no
identification model. Molmo still has to localize the candidate, and missing points
remain missing. Return-home clips are not given a bin target merely because one is in
the scene. Recovery outputs remain unreviewed and never overwrite or automatically
merge the parent tracks; object IDs are local to each extraction and clip. This is a
repair step for omissions found in the ReBot pilot, rather than a claim that language
establishes object presence or that the paper includes this recovery stage.

These are **unreviewed features**, not automatically equivalent action instructions.
Inspect overlays and split long semantic spans into action-consistent intervals before
composing point/motion/trace commands. Object trajectories are not gripper trajectories.
The paper trained DETR on 100 manually labeled Bridge gripper images; ReBot needs its
own reviewed per-arm labels and a validated detector. Generic COCO DETR is insufficient.

### Review and fit the ReBot gripper detector

Prepare 100 real images across 25 training episodes and all three views:

```bash
uv run examples/rebot_agent/gripper_labels.py prepare \
  --dataset-root /path/to/pinned_dataset --output outputs/gripper_review
```

Open `outputs/gripper_review/review.html` in a browser. Draw tight boxes around visible
gripper jaws, excluding the wrist body. Assign physical left/right arm identity, not
image-left/image-right. Record each arm as visible, not visible, or uncertain. Confirm
images under a reviewer ID and export the label JSON. The tool supports local browser
drafts and importing exported labels. It does not pre-accept model predictions.

Optionally show model-proposed boxes as dashed, unassigned overlays:

```bash
uv run examples/rebot_agent/gripper_labels.py review \
  --pack outputs/gripper_review/pack.json \
  --suggestions /path/to/model_suggestions.json \
  --output outputs/gripper_review/review_with_suggestions.html
```

The suggestions document has `kind: "model_proposals"`, a model `reviewer`, the
`pack_sha256`, and an `images` list. Each entry contains its pack image `id`,
`image_sha256`, optional `notes`, and `candidates: [{"bbox_xyxy": [x1, y1, x2, y2]}]`.
Coordinates use original-image pixels and candidates must not assign an `arm`.
The renderer checks pack/image hashes and box bounds. An empty candidate list makes
no visibility claim. Clicking **Use for left/right** copies a proposal into an
unconfirmed label; the reviewer must check boundaries, visibility, and physical arm
identity before confirmation. Exported labels retain the chosen model proposal and
its source hash separately from the human review. Rendering suggestions does not
change existing browser drafts or the image pack.

The default pack contains 80 detector-training and 20 detector-validation images,
separated by whole episode; all are outside VLA holdout episodes 90–99. All three
camera streams must be downloaded for the selected episodes. The exporter requires
review of every image and excludes an entire image when either arm is uncertain,
so uncertainty never becomes an empty negative target. It preserves source hashes,
the exact reviewed labels, and the source pack alongside COCO annotations.

```bash
uv run examples/rebot_agent/gripper_labels.py export \
  --pack outputs/gripper_review/pack.json \
  --labels /path/to/rebot_gripper_labels.json --output outputs/gripper_coco
# On one GPU inside the science-cluster allocation, after copying the image pack:
uv run examples/rebot_agent/gripper_detector.py train \
  --labels /path/to/gripper_coco --image-root /path/to/gripper_review \
  --output outputs/gripper_smoke --smoke
uv run examples/rebot_agent/gripper_detector.py train \
  --labels /path/to/gripper_coco --image-root /path/to/gripper_review \
  --output outputs/gripper_detr --epochs 50
uv run examples/rebot_agent/gripper_detector.py extract \
  --checkpoint outputs/gripper_detr/checkpoint \
  --visual outputs/rebot_visual --output outputs/gripper_tracks
```

The auxiliary detector uses pinned `facebook/detr-resnet-50`, replacing its COCO
classification head with the two gripper classes. Its initial training settings are
50 epochs, batch size 2, learning rates 1e-4/1e-5 for non-backbone/backbone weights,
and gradient clipping at 0.1; these still require tuning on the GPU allocation.
Install the DETR dependencies documented by Transformers (including its backbone
and matching-loss dependencies). Validation reports per-arm precision/recall at
IoU 0.5 and center error on matches; this is not COCO mAP. Checkpoint save/reload is
tested by re-evaluating the restored model and processor. The smoke option trains
at most two batches and evaluates the detector validation split.

Extraction preserves timestamps, camera/arm identity, confidence scores, and weight
hashes. Low-confidence, ambiguous, and invalid detections remain missing. Scores are
not calibrated visibility probabilities. Outputs remain unreviewed evidence: inspect
gripper overlays and tracking continuity before using centers as trace labels. No
occlusion interpolation or object-track substitution is performed.

Extract features on a small diverse episode subset first. Each entry in the input
feature JSON has `episode_index`, `start_frame`, `end_frame`, `subtask`, and
`subtask_evidence`. Optional `motions` entries carry `text` and `evidence`. Optional
`views` carry `camera`, `image_size`, `targets`, and `traces`:

- Each target has a grounded `point`, an imperative `instruction`, and `evidence`.
- Each trace has `arm` (`left`/`right`), ordered `points`, and `evidence`.
- Evidence should retain extractor model/revision, track identity, visibility/quality,
  time alignment, and coordinate transforms. Reject ambiguous gripper identities.

The top-level `source` is the pinned dataset identity, and `segments` contains these
entries. Generate this artifact from actual extractors; a language model guessing
points from the task description is not equivalent.

`fk_motion.extract_motion` accepts measured state trajectories, state feature names,
and explicit `arm`, `units`, `urdf`, `joint_names`, `state_keys`, `signs`,
`offset_degrees`, `tool_frame`, `frame`, `calibration`, `calibration_status`, `deadband_m`, and three
`axis_directions` mappings (`positive`/`negative`). It converts units, runs FK, rejects
substantial reversals, and returns motion entries with displacement, URDF hash,
joint mapping, axis conventions, and calibration provenance. Emitting language labels
requires `calibration_status="verified"`: verify the recording's joint signs/zeros
and the named base-frame axis-to-language convention, not just the URDF filename.
The training command loader also rejects missing/unverified calibration on FK
evidence, including evidence nested in combined commands. A VLM accepting the
visible command does not override this requirement. Use `measured_positions` and
the segmentation CLI for nominal, explicitly unverified diagnostic calculations.
It currently describes translations only; rotations and open/closed gripper labels
need additional validated extraction. No URDF or calibration is guessed. Image
projection is not part of this helper.

The ReBot B601 driver's calibration routine sets zero positions inside each motor
and then saves `homing_offset=0` in its calibration metadata. Finding that file
alone does not establish the physical zero pose used for earlier recordings.
Validate the recorded setup; do not recalibrate or move the arms to inspect it.

The same file provides offline `segment_motion` and a CLI to find interval candidates:

```bash
uv run examples/rebot_agent/fk_motion.py \
  --dataset-root /path/to/pinned_dataset --config /path/to/motion_config.json \
  --output outputs/rebot_motion_pilot --episodes 0 1 2 3 4
```

The config contains `arms.left` and `arms.right`, with the FK fields above plus
`gripper_state_key` and an explicit `calibration_status` (`verified` or `unverified`).
`segmentation` requires `translation_speed_m_s` and `gripper_speed_deg_s`. Its defaults
are a five-sample median velocity window, `minimum_duration_s=0.15`,
`translation_reversal_m=0.01`, and `gripper_reversal_deg=10.0`. These are starting
heuristics, not calibrated ReBot constants. Inspect the pilot before selecting them.

Each arm/axis is debounced separately. Raw excursions above the displacement deadband
retain boundaries even when shorter than the velocity filter window. Subtask boundaries
are always retained. Short intervals and disagreements with raw measurements are flagged;
the final frame is preserved as unresolved because it has no outgoing observation.
Intervals partition all frames without assigning open/closed, object identity, grasp
success, or camera-space directions. Outputs include raw and filtered numeric signs,
measured deltas, source/config/URDF hashes and per-frame FK/gripper arrays. Nominal mapping
runs remain explicitly unverified, and no run produces accepted training labels.
Filtering uses future demonstration observations and must never run as a live planner.

The command adapter combines episode padding with an `action_is_pad` mask for targets
outside the selected reviewed interval, using the dataset's actual action offsets.
Source action values remain unchanged. Overall-task samples retain their original
episode mask; steering samples can have shorter valid horizons without changing the
80/20 sampling ratio. Every sample must retain at least one valid target.
WALL-OSS-Flow zeroes masked targets before noisy action embedding and excludes them
from its loss. Loss averages over valid time steps per sample, preserving the existing
spatial-padding weight, so short commands are not downweighted by their duration.
The FAST-token supervision path rejects temporal padding; other policies must explicitly
honor `action_is_pad` before using this adapter. This masking is a WALL-OSS action-chunk
adaptation, not part of the released Bridge command substitution implementation.

Seeed publishes the [B601-DM URDF](https://github.com/Seeed-Projects/reBot-DevArm/blob/b8286c70e67bd20623212d409cbf2c79322570bc/Rebot_Arm_description/DM/urdf/ReBot_Arm_DM.urdf).
Its arm joints are `joint1`–`joint6`, base `base_link`, and tool `end_link`.
Manufacturer CAN IDs 1–6 match LeRobot's shoulder pan/lift, elbow flex, wrist flex/yaw/roll
order. LeRobot reports degrees. This establishes a nominal mapping, not the recorded
physical zero pose or either arm's mounting frame. Verify those before using direction
labels. The robot host is Madeleine. Inspect configuration files without calling the
robot's `connect()`, which enables motors.

Compose and review with:

Each feature view's `targets` entries accept either `point: [x, y]` or
`points: [[source_x, source_y], [destination_x, destination_y]]`, together with
`instruction` and `evidence`. The instruction must explain the points' roles in
that order. All coordinates belong to the view's named camera and original
`image_size`; a pair cannot mix camera views. The compiler preserves the supplied
order and emits both pointing and semantic-plus-pointing candidates. Each candidate
still needs review against the demonstrated interval: an object/destination pair
does not establish that a pick-and-place occurred, and coordinates from one frame
must not be reused across intervals where their targets move. Existing `point`
features remain supported. Supplying both `point` and `points` is rejected.

```bash
uv run examples/rebot_agent/prepare_steering.py \
  --features /path/to/grounded_features.json \
  --dataset-root /path/to/pinned_dataset_copy \
  --output outputs/rebot_steering_review --model gpt-6-astra
```

The script uses `OPENAI_API_KEY`. It saves all reviews and an accepted-only manifest
without rewriting the dataset. Rejected intervals become coverage gaps that must be
fixed before training. `coverage.json` checks all dataset episodes and frames, including
episodes absent from the feature input. It also reports frame coverage by style,
coordinate coverage by camera/style, missing styles, and the expected command mixture
under uniform frame/alternative sampling. These describe the annotations, not measured
robot capabilities. Repeated alternatives affect sampling weight; several alternatives
of one style on a frame do not multiply that style's frame coverage.

Training checks coverage before sampling. The full-mixture launcher requires all five
steering styles to be present in each selected train/eval split; the semantic baseline
uses its separate recipe. A style that appears only in held-out episodes cannot satisfy
the training check. Global presence does not guarantee adequate coverage: review the
reported per-style frame counts and mixture before launching the final experiment.
Main's trainer writes split-specific `steering_coverage.json`, including the manifest
hash and 80/20 task mixture, in the training directory and saved checkpoints. The
library's `dataset.steering_required_styles` defaults to empty for explicitly configured
subset experiments; the ReBot full-mixture launcher sets all five styles.
Use `--resume` to reuse completed reviews with identical saved input features.
The reviewer sees up to six timestamped frames per segment;
this can miss short events, so manually audit overlays and command boundaries, and
shorten segments where needed. Astra agreement is not ground truth. Offline review
may inspect future demonstration frames; live planning receives only current images.

## Train and deploy

Follow `examples/rebot_agent/README.md` for the science-cluster launcher. It supports
one to four GPUs, BF16 DDP, a ten-step smoke test, and a full training run. It records
the configuration, code revision, diff, and a copy of the reviewed manifest. Source
dataset and native base weights/processor are pinned. `base_model_revision` is separate
from the fine-tuned LeRobot checkpoint's revision.

After validating checkpoint reload, add these flags to an existing calibrated
ReBot rollout command with `--policy.path=/path/to/checkpoint`:

```bash
--interactive=true --inference.type=sync --planner.enabled=true \
--planner.model=gpt-6-astra --planner.camera_keys='["base","left_wrist","right_wrist"]' \
--planner.styles='["task","subtask"]' --autosteer_interval_s=2
```

Enter `/start`, then `/autosteer <overall goal>`. The external planner holds action
production until its first command. It uses the existing text-query channel; task
changes invalidate queued VLA actions. `/vqa` still queries the policy's own text
head. Human `/subtask` overrides planning. A stopped/failed planner holds new action
production until a fresh instruction, and its history resets for a new planning
session. Use `--planner.log_path=...` to retain decisions and visible assessments.

Initially external planning supports only synchronous inference with `interpolation_multiplier=1`. API latency pauses
action production, and cadence is configured in execution seconds rather than the
paper's 20 environment steps. This timing difference needs physical measurement.

After multi-style training, enable `task`, `subtask`, `motion`, `point`, and `combination`
as validated. Coordinate commands additionally require an explicit list of cameras
whose geometry the checkpoint has learned, for example
`--planner.grounding_camera_keys='["base"]'`. Keep `planner.camera_keys` set to all
useful observation views: the planner can inspect wrist images while being restricted
to base-view coordinates. The adapter enforces this both in its response schema and
when reading the response. An observed camera is not automatically a trained grounding
view. Object/destination point pairs use `point_mode=targets`; gripper paths use
`point_mode=path` and require trace steering. This permits source/destination pointing
without accidentally enabling trajectory commands.

Keep gripper traces out of the default off-the-shelf planner: Appendix B
excluded them because the VLM struggled to generate them. Trace labels can still serve
policy training and controlled tests. Our original-pixel, named-camera command format
adapts the paper's 0–255 convention; keep it consistent at training and inference.

## Validation milestone

Evaluate 50 attempts with known resets and an outcome rubric. Compare task-only,
semantic-subtask Astra planning, and all validated styles under matched conditions.
Measure completion, instruction compliance, arm/direction/point accuracy, command
switching, planning latency, and performance on distractors and paraphrases. Preserve
failure/unknown outcomes. Store Astra's assessment separately from an operator label.

`examples/rebot_agent/physical_eval.py` provides an append-only evaluation journal
on Linux/macOS. It does not launch or control the robot. Prepare a JSON list of
17 real reset scenarios before collecting results. Each scenario needs a unique
`id`, `task`, `reset_instructions`, `success_rubric`, and `tags`. Across the list,
include `paraphrase`, `distractor`, `novel_object`, and `multi_step`. Verify that
objects tagged novel were actually withheld from training. Reuse the same object
layout, instruction, and rubric for every condition within a scenario.

```bash
uv run examples/rebot_agent/physical_eval.py plan \
  --input scenarios.json --plan evaluation_plan.json --seed 42
```

The fixed schedule contains 16 matched triplets and one task-only/full-style pair:
17 task-only, 16 semantic, and 17 full-style attempts. Triplet orders are
counterbalanced; the final pair's order is seeded. Reports expose the incomplete
triplet and compute pairwise comparisons only where both scheduled conditions ran.
Do not change the plan after collection begins; the journal binds every event to
its hash. Use a new experiment to evaluate an improved checkpoint.

For each scheduled attempt, reset the scene and capture initial-state evidence.
Create `run.json` with `checkpoint_sha256`, `rollout_config_sha256`, `reset_operator`,
`initial_state_evidence`, `dataset_root`, and `planner_log`. Hash the actual model
weights and full rollout configuration. Use a fresh dataset root and planner log
for each attempt, and retain the initial images, config, and checkpoint reference.
These provenance declarations still require a subsequent artifact audit.

```bash
# Journal the attempt BEFORE starting policy action production.
uv run examples/rebot_agent/physical_eval.py begin --plan evaluation_plan.json \
  --journal attempts.jsonl --attempt-id attempt_001 --input run.json
```

Use main's interactive synchronous rollout with `--strategy.type=sentry` and
`--dataset.push_to_hub=false` to retain frames, including failed attempts. Match
`--dataset.root` and `--planner.log_path` to this attempt's journal entry. For
task-only control, disable the external planner and set `--task` to the fixed
scenario instruction. For semantic planning, enable only task/subtask styles.
For the full condition, enable only styles and coordinate cameras the checkpoint
has learned and passed validation. Keep the same time limit, cameras, action cadence,
and human stop/reset controls across conditions. Record any manual language override
as part of the evidence; a returned planner command does not prove it was executed.

After `/stop` or an error, append an `end` event using the same CLI and an input
JSON containing `reason`: `completed`, `timeout`, `operator_stop`, `runtime_error`,
or `interrupted`. This records how the attempt ended, not whether it succeeded.
An unclosed attempt remains visible and must be ended before starting another.
Never replace a failure by reusing its ID. Attach `recording` evidence with
`dataset_root`, `episode_indices`, and `evidence_sha256` of an archived recording
manifest. Include every saved episode if recording rotated during the attempt.

Append `operator` or `model` events with `outcome` (`success`, `failure`, or `unknown`),
`reviewer`, and `evidence`. **Only a human reviewer supplies `operator` events.**
Keep Astra assessments under `model`, even when they agree with a human. Optional
`metrics` map `command_compliance`, `arm_accuracy`, `direction_accuracy`,
`point_accuracy`, or `language_recovery` to nonnegative `correct`, `incorrect`, and
`unknown` counts under a predeclared rubric. Omit inapplicable metrics rather than
marking them correct. Corrections append new events, retaining the earlier labels.

```bash
uv run examples/rebot_agent/physical_eval.py report --plan evaluation_plan.json \
  --journal attempts.jsonl > evaluation_report.json
```

The report retains all started attempts, unstarted slots, unknown outcomes, and
operator metric coverage. Success-rate bounds include unknowns in their denominator;
known-pair differences disclose excluded unknown pairs. Planner logs report full-call
latency, holds/errors, unfinished calls, proposed styles, and proposed style switches.
These are planning diagnostics, not action-execution or physical-success labels.
Audit the recordings and reset evidence before interpreting journal counts as the
50 real-world trials required by this experiment.

Completing the experiment requires trained and reloadable checkpoints, reviewed visual
features, validated ReBot URDF/calibration and camera configuration, and the recorded
physical comparisons. These code paths alone do not establish improved physical success.
