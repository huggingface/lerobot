# Annotation Pipeline

`lerobot-annotate` adds subtasks, plans, memory, task rephrasings, interjections,
speech and visual Q&A to **existing LeRobot v3 datasets**. The same annotation
modules run through a resumable engine locally, on Slurm or on Hugging Face Jobs.
The engine also supports non-VLM steps; it does not add new annotation workflows.

The engine lives in `lerobot.annotations.runtime`; `annotations/storage.py` handles
recoverable dataset updates and `annotations/hub.py` handles explicit publication.
Slurm and HF execution adapters remain in `lerobot.jobs`.

Videos, FPS, cameras, actions/state and publisher-owned labels are preserved.
Conversion, resizing, re-encoding and action-space changes belong in separate
preparation scripts. Use a writable dataset copy, not an immutable Hub snapshot.

## Run a small annotation job

Install the `dataset` and `annotations` extras, then start with a few episodes.
This example uses an already-running OpenAI-compatible model endpoint, so the
laptop does not load the VLM. Set `model_id` to the model that endpoint serves.

```bash
uv sync --extra dataset --extra annotations
uv run lerobot-annotate \
    --root=/data/my-lerobot-v3-copy \
    --only_episodes='[0,1]' \
    --vlm.model_id=Qwen/Qwen3-VL-4B-Instruct \
    --vlm.auto_serve=false \
    --vlm.api_base=http://model.internal:8000/v1 \
    --runtime.run_uri=/data/runs/annotation \
    --runtime.workers=2 --runtime.batch_size=2 \
    --executor.episode_parallelism=1
```

Alternatively, use `--repo_id=owner/dataset --revision=SOURCE_SHA`; the CLI creates
and reuses a writable working copy without modifying the pinned Hub snapshot.
Use `vlm.auto_serve=true` to own a local vLLM service when the environment has the
required dependencies and GPU memory. vLLM is not installed by the annotation extra.

Annotations go into `language_persistent` and `language_events` in the dataset's
Parquet shards. [Language Columns and Recipes](./language_and_recipes) explains
how policies consume them.

| Module          | Annotations                                | Column                |
| --------------- | ------------------------------------------ | --------------------- |
| `plan`          | `subtask`, `plan`, `memory`, `task_aug`    | `language_persistent` |
| `interjections` | `interjection` and `say` speech tool calls | `language_events`     |
| `vqa`           | Grounded user/assistant Q&A                | `language_events`     |

Each module is enabled by default; disable it with `--plan.enabled=false`,
`--interjections.enabled=false` or `--vqa.enabled=false`. The tool catalogue lives
in `meta/info.json["tools"]`; existing tools are retained and `say` is added.

## Execution, options and resume

```text
           ┌─ plan/subtasks → interjections → plan refresh ─┐
v3 input ──┤                                                ├─ validate → materialize
           └─ VQA ──────────────────────────────────────────┘
```

Stages are sequential by default. Workers initialize once and commit checked batches
to `runtime.run_uri`; re-running the same configuration reuses valid outputs, repairs
corrupt/incomplete work and avoids model startup on a fully cached run. Uncommitted
work can repeat. Changing model, prompt or upstream content invalidates affected work;
a module's version must change when its behavior changes.

| Option                                                                        | Default                            | Use                                                                                                                                          |
| ----------------------------------------------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `runtime.mode`                                                                | `run`                              | `plan` previews independent work without inference/submission; downstream plans wait for real outputs. `resume` also verifies existing work. |
| `runtime.run_uri`                                                             | Local annotation staging directory | Persistent local/shared path or remote store; required explicitly for HF Jobs.                                                               |
| `runtime.workers` / `batch_size` / `shard_size`                               | `1` / `16` / `64`                  | Worker processes/groups, items per checkpoint batch, items per work shard. Use at least one shard per requested worker.                      |
| `runtime.max_parallel_stages`                                                 | `1`                                | Admit independent stages concurrently; requires an explicit CPU/GPU/memory `resource_budget`.                                                |
| `runtime.max_retries`                                                         | `2`                                | Bounded retries for temporary network/service failures; schema/input errors and unknown bugs fail immediately.                               |
| `executor.episode_parallelism` / `vlm.client_concurrency`                     | `16` / `16`                        | Threads inside each language worker and requests per client, not global endpoint limits.                                                     |
| `plan.frames_per_second` / `max_frames_per_prompt` / `window_overlap_seconds` | `2` / `60` / `1`                   | Subtask sampling density, frame budget including overlap, and context overlap.                                                               |
| `plan.emit_plan` / `emit_memory` / `n_task_rephrasings`                       | `true` / `true` / `10`             | Select plan/memory output; `0` rephrasings disables task augmentation.                                                                       |
| `vlm.camera_key` / `vqa.restrict_to_default_camera` / `vqa.vqa_emission_hz`   | First image camera / `false` / `1` | Default camera, whether VQA uses only that camera, and VQA frequency.                                                                        |

Subtasks use timestamped contact sheets and a describe→segment pass. Optional
`plan.subtask_seeded_relabel=true` refines wording with another call per subtask.
Long episodes use overlapping context but nonoverlapping output ownership, preserving
exact source frame IDs/timestamps in `meta/annotations/windows/*.parquet`. An unlabelled
window fails rather than borrowing neighbouring labels. Inspect boundaries and idle tails:
structural validation is not a human assessment of label quality.

Tune `vlm.max_new_tokens` and model-specific `vlm.chat_template_kwargs` so the
model has enough response budget for valid JSON, especially on long windows.

For concurrent stages, use a configuration file or Python; reserve worker resources
separately from an external/owned model service:

```python
from lerobot.annotations.steerable_pipeline.config import AnnotationPipelineConfig
from lerobot.annotations.runtime.configs import RuntimeConfig
from lerobot.annotations.runtime.types import Resources

cfg = AnnotationPipelineConfig()
cfg.runtime = RuntimeConfig(
    run_uri="/data/runs/annotation", workers=2,
    max_parallel_stages=2, resource_budget=Resources(cpus=4, memory_gb=16),
)
# Pass cfg to run_annotation_pipeline(cfg, Path("/data/my-lerobot-v3-copy")),
# or serialize it and use --config_path=annotation.json.
```

For a shared model endpoint, run one authenticated coordinator and point **all**
clients at `vlm.endpoint_limit_url` with the same `vlm.endpoint_limit_key`:

```bash
uv run python -m lerobot.annotations.runtime.endpoint_limits \
    --host=0.0.0.0 --port=8090 --key=annotation --limit=8 \
    --token-env=ANNOTATION_LIMIT_TOKEN
```

Set `vlm.endpoint_limit_token_env=ANNOTATION_LIMIT_TOKEN` on clients; use TLS or a
private trusted network. The limit covers participating clients across workers/runs.
Unreachable coordinators fail closed. Ambiguous timeouts or killed workers leave permits
held: drain/cancel inference before restarting the coordinator, rather than assuming
old requests ended. Put API credentials in `vlm.api_key_env`, not saved configuration.

## Slurm and Hugging Face Jobs

### Slurm

Run the controller where `sbatch`/`squeue` are available. Code, dataset, Python environment
and run storage must be visible to workers. Language clients need a reachable model
service; the controller's localhost is not another node's localhost.

```bash
uv run lerobot-annotate --root=/shared/my-lerobot-v3-copy \
    --vlm.auto_serve=false --vlm.api_base=http://model.internal:8000/v1 \
    --runtime.backend=slurm --runtime.workers=4 \
    --runtime.run_uri=/shared/runs/annotation \
    --runtime.slurm.python_executable=/shared/env/bin/python \
    --runtime.slurm.working_directory=/shared/project \
    --runtime.slurm.max_concurrent=4 --runtime.slurm.time_limit=02:00:00
```

Steps declare CPU, GPU and memory requests; Slurm supports both CPU and GPU jobs.
Each array has a dependent finalizer. Resume refuses duplicate active submissions;
detaching the controller does not cancel cluster jobs. Configure `partition`, `account`
and writable model/kernel caches for your cluster. `runtime.mode=plan` renders scripts
for independent stages without submitting jobs.

### Running on Hugging Face Jobs

Replace `SOURCE_SHA`, `CODE_SHA`, account/repository names and the image digest below.
Remote annotation requires a pinned Hub source, persistent remote storage and a public
code repository. The image must include Python 3.12+, git, ffmpeg and compatible dataset,
annotation and model-service dependencies; code installation uses `--no-deps`.

```bash
hf auth login
uv run lerobot-annotate --repo_id=owner/dataset --revision=SOURCE_SHA \
    --runtime.run_uri=hf://buckets/your-account/annotations/run-1 \
    --runtime.hf_jobs.namespace=your-account \
    --runtime.hf_jobs.code_revision=CODE_SHA \
    --job.target=h200 --job.image=YOUR_RUNTIME@sha256:IMAGE_DIGEST \
    --job.timeout=30m --job.detach=true
```

The built-in language recipe runs on **one HF node with local workers**, optionally
owning its VLM service. Generic steps can use multiple HF worker jobs only when they
explicitly declare remotely readable inputs. Local roots are never silently uploaded.
Resolved configuration files work remotely; credentials travel as secrets. Pin model
revisions (`vlm.model_revision`) and verify externally served models yourself. Check
`hf jobs hardware`, cap concurrency/timeouts, and smoke-test the image before scaling.

Outputs survive job exit even without Hub publication. The job prints a release index;
restore it with its key relative to the run store:

```python
from pathlib import Path
from lerobot.annotations.runtime.artifacts import ArtifactStore
from lerobot.jobs.processing import restore_release

store = ArtifactStore("hf://buckets/your-account/annotations/run-1")
restore_release(store, "releases/RELEASE_DIGEST.json", Path("restored"))
```

Unchanged videos reference the pinned source revision; restoration verifies their hashes.
For account/job setup, see the [HF Jobs guide](https://huggingface.co/docs/huggingface_hub/guides/jobs).

## Data safety and publication

- One controller owns each run. Process a separate dataset version while training:
  local commits are recoverable, not atomic snapshots for simultaneous readers.
- Native rows/columns and publisher-owned labels are retained. Ownership records in
  `meta/annotations/ownership/*.parquet` identify generated families that reruns may replace.
- Labels and provenance are Parquet; JSON is used for internal control/debug records.
  Validation checks source clocks, annotation structure and cross-family consistency.
- Publication is explicit: `push_to_hub=true` requires `new_repo_id`, pinned source
  `repo_id`/`revision`, a fresh `release_tag` and a reviewed `redistribution_permission`.
  Permission notes do not invent a missing licence. Existing targets additionally require
  `expected_target_revision` and must be processed datasets with matching lineage.
- Later releases start from the processed target's pinned revision and upload changed
  Parquet/metadata, not another video copy. Publication has bounded file/byte limits;
  large staged uploads need a separate workflow. Seeds do not guarantee bitwise VLM/GPU
  reproducibility, and cached-run time is not processing throughput.

## Add an annotation step

For prompt/grounding changes, reuse the existing modules and templates under
`annotations/steerable_pipeline/`. For a new computation, implement an importable
processing module; it need not use a VLM. This lifecycle sketch leaves prediction
logic to your application:

```python
import pyarrow as pa
from lerobot.annotations.runtime.types import ItemResult, ModuleSpec, Outcome, Resources

class MyStep:
    def __init__(self):
        self.spec = ModuleSpec(
            name="my_annotation", version="1", scope="episode",
            outputs={"labels": pa.schema([
                ("episode_index", pa.int64()), ("frame_index", pa.int64()),
                ("timestamp", pa.float64()), ("label", pa.string()),
            ])},
            resources=Resources(cpus=1, gpus=0, memory_gb=4),
        )

    def setup(self, context):
        pass  # Initialize the model/client once here, never in __init__.

    def process_batch(self, items, context):
        results = []
        for item in items:
            rows = self.predict(item.payload, seed=item.seed)
            table = pa.Table.from_pylist(rows, schema=self.spec.outputs["labels"])
            artifact = context.write_parquet(item, "labels", table)
            results.append(ItemResult(item.item_id, Outcome.COMPLETED, (artifact,)))
        return results

    def predict(self, references, *, seed):
        raise NotImplementedError("Implement bounded prediction on exact source frames")

    def teardown(self):
        pass  # Release worker-owned resources.
```

Choose `scope` from `asset`, `episode`, `camera_stream`, `window` or `reduction`, and
declare every output schema/resource requirement. Constructors must remain lightweight:
planning inspects them without loading models. Return one result per item; masks and
rejections need explicit reasons. Preserve source frame IDs/timestamps; window predictors
can use `EpisodeWindow` and `reconcile_frame_rows`/`reconcile_spans` from
`lerobot.annotations.runtime.windows`. Bump the module version when semantics change.

Wire the step into a Python recipe, not a new CLI. A source provides `dataset_ref`
and `discover(stage, store, upstream)`, yielding bounded JSON `InputItem` references
and resolving verified upstream artifacts. It must verify pinned inputs; declaring
`DatasetRef` alone does not make local files immutable.

```python
from lerobot.annotations.runtime.configs import RuntimeConfig, StageConfig
from lerobot.annotations.runtime.pipeline import run_pipeline

# source is your reference-only source; my_package.steps must exist on every worker.
stages = [StageConfig("labels", "my_package.steps:MyStep")]
store, completed = run_pipeline(source, stages, RuntimeConfig(run_uri="/data/runs/custom"))
```

Use `depends_on=("other_stage",)` for ordering. Independent stages may overlap within
the resource budget. `when="quality.usable"` records a reasoned mask for a false boolean
supplied by the source after its declared dependency; it is **not** a built-in quality
detector. For HF multi-job execution set `ModuleSpec.hf_jobs_compatible=True` only after
making every input/model reference remote-readable; choose the CPU/GPU image/flavor
and concurrency under `runtime.hf_jobs`.

A custom step produces checked artifacts, not automatic dataset columns. Add explicit
validation/materialization when introducing new columns, preserve native data, and
review a small sample before scaling. Keep model/prompt semantics in the annotation
module and scheduling, storage and retries in the engine. Run `lerobot-annotate --help`
for the complete option list.
