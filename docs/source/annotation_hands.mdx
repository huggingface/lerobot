# Hand action annotations

In Annotation Studio, select **Hand actions** alongside the other annotations.
Choose a dataset, episodes and an RGB human-POV camera, then choose an HF Jobs
GPU under **Models & compute**. Use the same estimate, review, launch and progress
pages as other annotations. There is no separate raw-video conversion command,
folder selector, local-machine mode or Slurm mode for this feature.

## Dataset output

The annotated copy retains every selected source episode and frame, including
frames with no usable hands. It writes hand actions into the existing dataset's
Parquet rows:

| Feature                                 | Meaning                                                                                                              |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `action`                                | 102 float32 values: left/right wrist position and axis-angle rotation (12), then left/right finger articulation (90) |
| `annotation.hand_action_valid`          | One boolean; true where a complete finite bimanual action is available, including native motion infilling            |
| `annotation.hand_action_observed_valid` | Strict native observed-only bimanual training mask (minimum 30-frame spans)                                          |
| `annotation.hand_observed`              | Per-hand direct-observation flags                                                                                    |
| `annotation.hand_infilled`              | Per-hand native motion-infiller flags; these are inferred, not observed                                              |
| `annotation.hand_confidence`            | Left/right confidence for valid action frames; zero otherwise                                                        |
| `annotation.hand_reference_frame`       | Source episode frame defining that span's fixed FLU coordinate frame; -1 when invalid                                |
| `annotation.original_action`            | Original source action, if present, preserved before replacement                                                     |

The native **HaWoR motion infiller** is retained: usable infilled poses are written
to `action` with their provenance. Training can use `annotation.hand_action_valid`
for all available predictions, or `annotation.hand_action_observed_valid` for
strict observed-only training. Truly unrecoverable actions contain **zero
placeholders** and must be masked; zeros are not measured poses.
This preserves episode lengths and camera/frame alignment without inventing
missing hands. A fully unobserved episode remains present with all actions invalid.
Failed inference is reported as a failed episode, rather than a completed episode
with fabricated values. Existing datasets already containing preserved original
actions are rejected to avoid overwriting that provenance.

The native recipe uses calibrated HaWoR/MANO, DROID-W camera tracking with MoGe,
FP16 hands and ByteTrack; world joint smoothing, wrist rotation restoration,
articulated orientation refinement and bounded wrist-plane correction retain
the pinned recipe's behavior. The native strict training mask requires uninterrupted spans of at least 30 frames
with both hands directly observed and camera tracking valid. The annotated copy
also retains complete finite infilled predictions, with separate masks.
Continuous recoverable spans share a fixed start-camera FLU frame (forward, left,
up), including across occlusions bridged by the native infiller. Each span records
its reference frame; coordinate conversion uses the pinned native geometry code.
These are inferred human poses, not robot joint commands or ground truth.
Monocular metric scale remains model-dependent.

## Calibration and compute

Use measured `pinhole` or `opencv_fisheye` calibration matching the selected
camera's exact resolution. Studio can read `camera.intrinsics` from the camera's
`info` metadata, or accept the calibration JSON in the wizard. Required fields
are `model`, `width`, `height`, `fx`, `fy`, `cx`, `cy`, and `distortion`.
The selected recipe requires positive isotropic focal lengths; fisheye requires
four distortion coefficients. Missing calibration fails before dispatch.
Native source FPS is preserved; processing FPS is a separate quantity.

HF Jobs choices are A100 80 GB, RTX PRO 6000 96 GB and H200 141 GB. Their actual
throughput has not been benchmarked. An optional **Planning speed** is an
explicit user assumption used for duration estimates, never a measured result.
The historical reference is 53.9 input FPS on an RTX 5090 over ten calibrated
HOT3D clips / 1,500 source frames, including model startup, camera/hands and export
but excluding installation/downloads. This is not a benchmark of HF hardware.
Queue, setup, downloads and copying add time. Quotes show live HF hardware prices
and reserve the complete timeout; reservations are not actual charges.

## MANO and research rights

The [official MANO site](https://mano.is.tue.mpg.de/) requires registration and
agreement to its [license](https://mano.is.tue.mpg.de/license.html).
Standard terms restrict use to permitted non-commercial purposes and restrict
third-party transfer and redistribution. A public checkpoint mirror or a research
checkbox does not grant those rights. Review the
[HaWoR terms](https://github.com/ThunderVVV/HaWoR) and
[other checkpoint terms](https://huggingface.co/macrodata/egovision-safetensors)
as well. Model-format conversion does not change a license.

Obtain MANO through the official process yourself. If your permissions permit
storing/using your files on your controlled HF compute, place your own licensed
`MANO_LEFT.safetensors` and `MANO_RIGHT.safetensors` in a **private model repository
in your own account**. Conversion, storage and hosting must be within your
permissions. Studio does not accept a license for you or certify legal compliance.
No official-account credentials are requested or stored by the Space.

The Job uses your HF token to pull those files at the exact quoted commit,
rechecks ownership/privacy, records checksums, and supplies local paths to native
model resolution. There is no public MANO fallback. Assets and asset caches are
never written into the annotated dataset or its execution checkpoints. Research
outputs are private. Do not enable unrestricted shared hosting under the standard
MANO terms; obtain separate permission for uses outside your license.

## Deployment contract

This integration is experimental. The Space must be configured with a
**dependency-complete HF Jobs image pinned by digest**, without shared MANO
files, and `HAND_JOB_BACKEND` operator settings. `HAND_JOB_IMAGE` identifies that
image; it is not an end-user machine selector. The operator configuration names
the separately installed runtime package, its interpreters, DROID paths and a
SHA-256-pinned non-MANO asset manifest. That runtime retains its own license;
this Apache adapter neither copies nor relicenses its inference implementation.

The runtime checkout is pinned to `d61017dd3a95c59a51d836aab6f7bac1baee34eb`.
The image supplies git, NumPy, FFmpeg, ego-vision 0.1.25, CUDA-compatible hand
models and camera dependencies in isolated interpreters. The manifest lists
checksummed runtime/model files and `HF_HOME`/`TORCH_HOME` cache directories.
`HandBackendConfig` defines the remaining operator fields. No credentials belong
in that manifest. Native inference is offline after the authorized private MANO
pull. The bridge retains warm hand/camera services across episodes and returns
native action predictions with observed/infilled provenance; no separate filtered
LeRobot dataset is created. The export policy is versioned separately from the
inference recipe.

The same #4892 execution engine checkpoints each stage, including the preceding
language and human-video stages where selected. Cached stages do not repeat
inference; automatic inference retries remain disabled. The outer Job owns GPU
allocation and billing. An unconfigured image prevents launch rather than
silently sending work to a custom machine. Native GPU validation is still
required before treating the integration or speed estimates as production-ready.
