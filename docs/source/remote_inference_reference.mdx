# Remote inference configuration and networking

Start with the [operator guide](./remote_inference) for the two-process setup, mode selection and tuning. This page covers exact deployment schemas, checkpoint compatibility and secured router connections.

## Deployment schema

The checked-in [`server.yaml`](https://github.com/huggingface/lerobot/blob/main/examples/remote_inference/server.yaml) is a generic SO-101 example, not a hardware-tested checkpoint profile. Its full configuration is repeated below for convenient copying.

<details>
<summary>Complete generic server configuration</summary>

```yaml
# Generic schema example, not a tested checkpoint/robot profile.
# Copy and adapt the checkpoint, calibration, camera names/views and units together.
# Nested CLI flags override this file; see docs/source/remote_inference.mdx.
deployment: manipulation
model:
  repo_or_path: /absolute/path/to/checkpoint
  revision: null # For Hub checkpoints, pin a commit before validating a deployment.
  device: cuda
execution:
  supported_modes: [chunk]
  action_fps: 30.0
  action_deadline_s: 5.0
  idle_timeout_s: 10.0 # Absent-client ownership grace, not a robot motion timeout.
  # Explicit continuous canonical coordinates permitted for optional client blending.
  # Leave empty for append/alignment-only. Do not include gripper/discrete controls by default.
  blendable_components: []
  warmup_calls: 2
language:
  enabled: false
  deadline_s: 60.0
zenoh:
  mode: peer
  listen_endpoints: [tcp/127.0.0.1:7447]
semantics: so101-degrees-gripper-percent-v1
robot_type: so101_follower
features:
  - name: observation.state
    shape: [6]
    dtype: float32
    names:
      [
        shoulder_pan.pos,
        shoulder_lift.pos,
        elbow_flex.pos,
        wrist_flex.pos,
        wrist_roll.pos,
        gripper.pos,
      ]
    semantics: so101-degrees-gripper-percent-v1
  - name: observation.images.front
    shape: [480, 640, 3]
    dtype: uint8
    kind: rgb
    semantics: rgb-front-table-v1
action_feature:
  name: action
  shape: [6]
  dtype: float32
  names:
    [
      shoulder_pan.pos,
      shoulder_lift.pos,
      elbow_flex.pos,
      wrist_flex.pos,
      wrist_roll.pos,
      gripper.pos,
    ]
  semantics: so101-degrees-gripper-percent-v1
```

</details>

`features` and `action_feature` are required. Each declares a name, shape, dtype, modality (`tensor` or `rgb`) and explicit semantic convention. State/action vectors also need their ordered component names. RGB uses height × width × 3, `uint8`, RGB channel order. The example's SO-101 convention means body joints in degrees and the gripper in the calibrated 0–100 range. Camera placement and calibration must also match the checkpoint. Matching dimensions alone does not verify these conventions.

Use checkpoint-facing observation names in the deployment schema. If the physical camera is named `scene` but that same view is declared as `observation.images.front`, configure the client with `--rename_map='{"observation.images.scene":"observation.images.front"}'`. Renaming changes a key, not the camera's view, resolution or image preparation. Do not rename an unrelated view to make admission pass. Policy-specific resizing, padding and missing-camera masks remain the policy's responsibility and must be explicitly supported by its input contract.

A local artifact is identified by its relevant file contents and effective inference configuration. For Hub models, configure `model.revision` with a pinned commit; the server resolves the artifact before loading. The client can require the resulting identity with `--inference.expected_artifact=...`. A deployment name is a routing name, not a checkpoint identity. Deployment identifiers must be single alphanumeric/underscore/dot/hyphen key segments; Hub IDs belong in `model.repo_or_path`.

Known checkpoint component ordering is checked even when relative actions are disabled. Additional robot cameras can remain available for local recording; only required observations are sent. An artifact pin identifies model/processor contents and effective inference settings, not host paths or transport settings.

## Checkpoint compatibility

The server runs the checkpoint's saved preprocessor, direct chunk prediction and postprocessor. Supported checkpoints must accept current observations, declare their prediction/execution horizon and return actions with the agreed order and units. Admission rejects unsupported contracts before policy motion.

| Policy or setup                                                                      | Current boundary                                                                                                                                               |
| ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ACT                                                                                  | Current-observation chunks without temporal ensembling                                                                                                         |
| SmolVLA, XVLA, LaWAM                                                                 | Targeted preparation/horizon declarations; specific checkpoints have physical action evidence. SmolVLA has guided RTC evidence; XVLA and LaWAM use chunk mode. |
| VLA-JEPA, GR00T                                                                      | Current-frame/horizon declarations have focused software tests; supplied checkpoints still need warmup and task validation.                                    |
| Temporal-history policies or additional state normally prepared by `select_action()` | Require an adapter; changing the schema cannot add that behavior.                                                                                              |
| Unitree G1/SONIC                                                                     | No replacement for the former remote recipe: latent tokens and the onboard balance controller need a controller-aware integration.                             |

Keep a working synchronous reference. Downloading or warming a checkpoint does not establish task quality, RTC support or useful text generation. A policy declaration does not add support to a new robot; see the [robot waiting contract](./integrate_hardware#waiting-and-camera-independent-return).

The current robot opt-ins are SO followers and OMX followers with position-only actions. Other integrations must validate and declare their waiting behavior; enabling torque or using `.pos` names is not sufficient.

For chunk-only deployments, `--execution.n_action_steps=30` can shorten the saved execution slice when that checkpoint supports the setting. It cannot exceed the prediction horizon and is rejected when RTC is advertised. This override does not edit the checkpoint.

## Identity and independent experiments

Pair server `--deployment=arm-a` with client `--inference.deployment=arm-a`; use another name for an independent experiment. Multiple pairs can share a router, but each policy-server process still loads one model and admits one active client. If several servers advertise the same deployment, discovery fails as ambiguous unless the client selects `--inference.instance=...`.

Both processes log their LeRobot version and available source revision at startup. A dirty checkout or unknown revision is reported explicitly. Protocol capabilities and execution settings decide compatibility; a matching version label alone is insufficient. Alignment/blending requested against an older server fail before motion instead of falling back silently to append.

If a policy reset fails, the deployment becomes unavailable and refuses new work. The server process can remain alive for diagnostics; restart it after resolving the failure. A running process is not by itself a ready deployment.

The routing root is `lerobot/inference/v1/deployments/{deployment}`. Each server lifetime and admitted session get distinct IDs beneath it. Query/reply carries discovery, admission and control; publish/subscribe carries observations/actions/text; liveliness tracks presence. Explicit endpoints disable multicast/gossip discovery. Ordering uses request/generation identities and local action progress. Motion deadlines use the client's monotonic clock; the server independently bounds its work. Server/client clocks need not be synchronized.

## Image bandwidth and connection detection

Raw RGB is the default lossless encoding. To reduce image bandwidth, set client `--inference.encoding=jpeg --inference.jpeg_quality=90` (quality range 1–100). Encoding work and lost image detail can affect turnaround and policy behavior; compare the same task after enabling JPEG. Depth and arbitrary tensors are never silently JPEG encoded.

Server-presence loss is detected through Zenoh liveliness, so a broken link may not be reported until its transport lease expires. Configure `transport/link/tx/lease` in the JSON5 supplied through client `--inference.zenoh_config_path` and matching server transport configuration when needed. This is separate from client action deadlines and server absent-client cleanup.

A server log saying `presence restored` means its ownership cleanup was cancelled; it does not restore a client session that already observed server loss. Observation transport drops under congestion instead of blocking the motor loop. Freshness limits, request deadlines and bounded starvation remain active while a link stalls.

## Private connections through a router

A router provides a reachable rendezvous for the two processes. It adds a hop and a shared failure point; it does not supply a VPN, automatic firewall traversal, model scheduling or motion recovery. Each client and policy server connects explicitly to it. Router loss leaves the existing local buffer, freshness and operation limits in force; reconnecting cannot undo a terminal fault.

Use authenticated encrypted connections for private remote deployments. Bare TCP and a session ID provide no authentication. The example uses TLS-only links, mutual certificate verification, disabled discovery and certificate-role ACLs, validated with Zenoh 1.9.0 and 1.10.1. These controls depend on the actual topology: participants connect in client mode without direct peer links. See the official [TLS configuration](https://zenoh.io/docs/manual/tls/) and [ACL semantics](https://zenoh.io/docs/manual/access-control/).

The complete configurations are in [`examples/remote_inference/zenoh`](https://github.com/huggingface/lerobot/tree/main/examples/remote_inference/zenoh):

| File           | Purpose                                                                  |
| -------------- | ------------------------------------------------------------------------ |
| `router.json5` | TLS listener and default-deny ACL for deployment `manipulation`          |
| `server.json5` | Policy-server connection using a `policy-server` certificate common name |
| `robot.json5`  | Robot connection using a `robot-client` certificate common name          |

Provision a private CA and distinct role certificates/keys under `./certs`, or replace the example paths with absolute paths. Only the router needs `router-key.pem`, only the server needs `policy-server-key.pem`, and only the robot needs `robot-client-key.pem`. All participants need the CA certificate. The router certificate must cover the DNS name used by the clients; replace `localhost` consistently for an actual network deployment. Keep the CA private key out of these runtime directories.

<details>
<summary>Router startup and complete server/client transport overrides</summary>

Run the router from a directory where the certificate paths resolve:

```bash
zenohd --config examples/remote_inference/zenoh/router.json5
```

Keep the validated checkpoint and full schemas in `server.yaml`; override its transport fields together. The empty listener list is necessary because router clients cannot listen:

```bash
uv run --no-sync lerobot-policy-server --config_path=server.yaml \
  --zenoh.mode=client \
  --zenoh.listen_endpoints='[]' \
  --zenoh.connect_endpoints='[tls/localhost:7447]' \
  --zenoh.config_file=examples/remote_inference/zenoh/server.json5
```

Equivalently, replace the entire server YAML `zenoh` block with:

```yaml
zenoh:
  mode: client
  listen_endpoints: []
  connect_endpoints: [tls/localhost:7447]
  config_file: examples/remote_inference/zenoh/server.json5
```

Use these client options with the ordinary rollout hardware/task arguments:

```bash
--inference.endpoint=tls/localhost:7447 \
--inference.zenoh_mode=client \
--inference.zenoh_config_path=examples/remote_inference/zenoh/robot.json5
```

Transport configuration preserves the JSON5 TLS/ACL settings and sets explicit endpoints, with multicast/gossip discovery and shared memory disabled.

</details>

The ACL permits robot observation/control traffic and server action/text replies. It prevents a separate participant using the robot role from forging server actions, and an unrecognized certificate role from subscribing to observations or querying the deployment. Change the deployment path in the ACL together with `deployment`; changing a name does not authorize access. Router ACLs cannot govern a process's own local publication/subscription delivery or defend a compromised robot process. For distinct trust groups, use separately authorized identities and deployment-scoped rules; sharing the example role certificates would share their permissions.

## Deployment patterns

- **One host or trusted LAN:** direct explicit TCP endpoints; the same process split and motion behavior apply.
- **Private remote GPU:** both robot and GPU server make outbound connections to a reachable secured router. The router supplies a meeting point, not a VPN or automatic firewall traversal.
- **Shared experiment router:** separate deployment names and access rules for each pair. Separate model processes can contend for the same GPU and increase turnaround.
- **Dedicated GPU Space:** a future experiment, not a validated deployment. First prove authenticated outbound Zenoh connectivity to a separate router; a Space's HTTP endpoint is not a raw Zenoh listener. Then validate startup, sleep/wake behavior and one task. Consult current [Docker Spaces](https://huggingface.co/docs/hub/spaces-sdks-docker) and [networking](https://huggingface.co/docs/hub/spaces-overview#networking) documentation before attempting it.

## Transport validation

The supported binding range is `eclipse-zenoh>=1.9.0,<1.11.0`; the lockfile selects 1.10.1. Direct transport/lifecycle checks and the mTLS/ACL example passed with matching binding/router versions 1.9.0 and 1.10.1. Validate the actual router/client combination when upgrading. Transport success does not establish a usable robot latency budget or routed hardware acceptance.

With remote dependencies installed, run:

```bash
uv run --no-sync pytest tests/remote_inference/test_codec.py tests/remote_inference/test_zenoh.py -q -rs
LEROBOT_ZENOHD=/absolute/path/to/zenohd \
  uv run --no-sync pytest tests/remote_inference/test_zenoh.py -q -rs
```

Router tests create temporary certificates and check encrypted exchange, presence, ACL denials and missing client certificates. They skip without `LEROBOT_ZENOHD` or `openssl`. Validate router interruption and full request turnaround before a physical routed run.
