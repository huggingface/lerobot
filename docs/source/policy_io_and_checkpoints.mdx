# Policy Inputs, Outputs, Checkpoints, and Action Representations

This page describes the data contract between LeRobot policies, their public
checkpoints, datasets, and robot controllers. It covers every policy registered
on `main` and the four policy integrations currently under review.

Research snapshot: **July 30, 2026**.

<Warning>

A matching vector width does not establish compatibility. A six-dimensional
vector might contain named joint positions, an end-effector pose, mobile-base
commands, or normalized motor values. Check the checkpoint, dataset, processor,
and controller metadata before training or deployment.

</Warning>

## Start here

Three contracts must agree:

- The **policy architecture** fixes tensor shapes, horizons, padding capacity,
  and model-side preprocessing.
- The **checkpoint** fixes ordered feature keys, active dimensions, camera
  roles, normalization statistics, and any robot-specific packing.
- The **controller** fixes joint or end-effector control, frames, rotation
  representation, units, absolute or relative commands, gripper convention,
  frequency, and physical limits.

“Relative” can also mean two different things:

- **Controller-relative** actions are native delta commands, such as LIBERO's
  `delta xyz + delta axis-angle + gripper`.
- **Chunk-relative** actions are produced when
  `RelativeActionsProcessorStep` subtracts the current state from selected
  action channels.

A LIBERO dataset may already contain controller-relative actions while
`use_relative_actions=false`. Applying both transforms would subtract twice.
See [Action Representations](./action_representations) for the distinction
between absolute trajectories, relative trajectories, and sequential deltas.

On this page, **unknown** means that a meaning or unit is not serialized by the
LeRobot checkpoint/configuration or stated in maintained documentation. It is
not permission to infer semantics from shape.

## Policies and checkpoints

For most policy architectures, state and action semantics remain
dataset-defined. Padding to a model capacity does not create a canonical robot
ordering.

### ACT (`act`)

- **Checkpoints:** [`act_aloha_sim_transfer_cube_human`](https://huggingface.co/lerobot/act_aloha_sim_transfer_cube_human)
  and [`act_aloha_sim_insertion_human`](https://huggingface.co/lerobot/act_aloha_sim_insertion_human).
- **I/O:** state or environment state plus config-ordered images → continuous
  action chunk, 100 steps by default.
- **Representation:** dataset-defined joint, EEF, mobile-base, or mixed
  vectors; mean/std normalization. The ALOHA Sim checkpoints use the top camera
  and 14D state/action.

### Diffusion (`diffusion`)

- **Checkpoints:** [`diffusion_pusht`](https://huggingface.co/lerobot/diffusion_pusht)
  and [`diffusion_pusht_keypoints`](https://huggingface.co/lerobot/diffusion_pusht_keypoints).
- **I/O:** two observation steps of state and optional config-ordered images →
  a continuous diffusion sequence, with 32 actions executed by default.
- **Representation:** dataset-defined; state/action use min-max normalization.
  The PushT checkpoints predict an absolute 2D target position in simulator or
  pixel coordinates.

### TD-MPC (`tdmpc`)

- **Checkpoints:** no maintained policy checkpoint; train for the target
  environment.
- **I/O:** state or pixels, optional environment state → one continuous action.
- **Representation:** environment-defined. The processed action is expected in
  `[-1, 1]`; actions use min-max normalization and other inputs use identity.

### VQ-BeT (`vqbet`)

- **Checkpoint:** [`vqbet_pusht`](https://huggingface.co/lerobot/vqbet_pusht).
- **I/O:** five state or image observations → quantized behavior action
  sequence.
- **Representation:** dataset-defined with state/action min-max normalization.
  The maintained PushT checkpoint predicts a 2D target.

### Multitask DiT (`multi_task_dit`)

- **Checkpoints:** no maintained robot-action checkpoint; the configured VLM is
  an initializer.
- **I/O:** two observations, config-ordered images, state, and task text → a
  32-step diffusion/flow sequence, with 24 actions executed.
- **Representation:** dataset-defined with state/action min-max normalization.

### Gaussian actor (`gaussian_actor`)

- **Checkpoints:** no maintained checkpoint; this is an online RL policy trained
  per environment.
- **I/O:** state or environment state and images → one Gaussian actor action.
- **Representation:** environment-defined with state/environment/action
  min-max normalization.

### π0, π0.5, and π0-FAST

All three consume config-ordered images, task text, and state padded to 32D.
Their active state/action ordering remains checkpoint- and dataset-defined; the
32D capacity is not a published OpenPI robot schema.

- **π0:** [`pi0_base`](https://huggingface.co/lerobot/pi0_base),
  [`pi0_libero_base`](https://huggingface.co/lerobot/pi0_libero_base), and
  [`pi0_libero_finetuned_v044`](https://huggingface.co/lerobot/pi0_libero_finetuned_v044).
  It predicts `50 × 32D` flow actions and crops to the configured width.
  Normalization defaults to mean/std.
- **π0.5:** [`pi05_base`](https://huggingface.co/lerobot/pi05_base),
  [`pi05_libero_base`](https://huggingface.co/lerobot/pi05_libero_base),
  [`pi05-libero`](https://huggingface.co/lerobot/pi05-libero),
  [`pi05_droid`](https://huggingface.co/lerobot/pi05_droid),
  [`pi05_robocasa`](https://huggingface.co/lerobot/pi05_robocasa), and
  [`nvidia/pi05-arena-gr1-microwave`](https://huggingface.co/nvidia/pi05-arena-gr1-microwave).
  It predicts `50 × 32D` flow actions and defaults to q01/q99 normalization.
- **π0-FAST:** [`pi0fast-base`](https://huggingface.co/lerobot/pi0fast-base)
  and [`pi0fast-libero`](https://huggingface.co/lerobot/pi0fast-libero). It
  predicts tokenized action chunks and defaults to mean/std normalization.

The packaged processor is authoritative for absolute/chunk-relative behavior.
Base checkpoints commonly disable chunk-relative conversion; it can be enabled
for selected named channels. Base image slots are `base_0_rgb`,
`left_wrist_0_rgb`, and `right_wrist_0_rgb`. LIBERO variants use the exterior
view first, wrist second, and may mask a third view.

### SmolVLA (`smolvla`)

- **Checkpoints:** [`base`](https://huggingface.co/lerobot/smolvla_base),
  [`LIBERO`](https://huggingface.co/lerobot/smolvla_libero),
  [`Meta-World`](https://huggingface.co/lerobot/smolvla_metaworld),
  [`RoboCasa`](https://huggingface.co/lerobot/smolvla_robocasa),
  [`VLABench`](https://huggingface.co/lerobot/smolvla_vlabench),
  [`RoboCerebra`](https://huggingface.co/lerobot/smolvla_robocerebra),
  [`LIBERO-plus`](https://huggingface.co/lerobot/smolvla_libero_plus),
  [`RoboTwin`](https://huggingface.co/lerobot/smolvla_robotwin),
  [`RoboMME`](https://huggingface.co/lerobot/smolvla_robomme), and
  [`GR1 Arena`](https://huggingface.co/nvidia/smolvla-arena-gr1-microwave).
- **I/O:** config-ordered images, task text, and state/action padded to 32D → a
  50-step flow chunk.
- **Representation:** active fields are dataset/checkpoint-defined; mean/std
  normalization. Camera slot meanings are listed under
  [Camera order](#camera-order-and-physical-role).

### GR00T N1.7 (`groot`)

- **Checkpoints:** [`GR00T-N1.7-3B`](https://huggingface.co/nvidia/GR00T-N1.7-3B)
  and LIBERO [`spatial`](https://huggingface.co/nvidia/gr00t17-lerobot-libero_spatial-640),
  [`object`](https://huggingface.co/nvidia/gr00t17-lerobot-libero_object-640),
  [`goal`](https://huggingface.co/nvidia/gr00t17-lerobot-libero_goal-640), and
  [`LIBERO-10`](https://huggingface.co/nvidia/gr00t17-lerobot-libero_10-640).
- **I/O:** checkpoint-defined camera streams, language, embodiment, and state
  up to 132D → actions up to 132D.
- **Representation:** checkpoint embodiment metadata defines joint/EEF fields,
  camera mapping, transforms, and `statistics.json`. Without that metadata,
  semantics are adapter-defined. Do not replace its camera mapping with sorted
  keys.

### X-VLA (`xvla`)

- **Checkpoints:** [`base`](https://huggingface.co/lerobot/xvla-base),
  [`LIBERO`](https://huggingface.co/lerobot/xvla-libero),
  [`WidowX`](https://huggingface.co/lerobot/xvla-widowx),
  [`Google robot`](https://huggingface.co/lerobot/xvla-google-robot),
  [`AGIBOT World`](https://huggingface.co/lerobot/xvla-agibot-world), and
  [`folding`](https://huggingface.co/lerobot/xvla-folding).
- **I/O:** config-ordered images, language, and optional state → a 30-step
  action, commonly in a padded 20D model space.
- **Representation:** the registered `action_mode` is authoritative:
  `ee6d` is left then right `[xyz(3), rotation-6D(6), gripper]` (20D);
  `joint` is left joints plus gripper, then right joints plus gripper (14D);
  `franka_joint7` uses the first 7 slots; and `so101_bimanual` uses six named
  left motor channels, then six right channels, then eight pads.

`auto` only pads/crops the first `real_dim` channels. It does not infer joint
names, units, arm side, coordinate frame, or gripper meaning.

### WALL-X (`wall_x`)

- **Checkpoint:** [`x-square-robot/wall-oss-flow`](https://huggingface.co/x-square-robot/wall-oss-flow).
  This is a `wall_x` base model, not the Wall-OSS-0.5 architecture.
- **I/O:** config-ordered images, text, and state up to 20D → `32 × 20D`
  continuous or tokenized actions.
- **Representation:** checkpoint/dataset-defined. The configuration fixes
  capacity but does not name every channel. Normalization is checkpoint-specific
  and defaults to mean/std.

### EO-1 (`eo1`)

- **Checkpoints:** no maintained robot-action checkpoint; the Qwen VLM is an
  initializer.
- **I/O:** config-ordered images, language, and state padded to 32D → `8 × 32D`
  flow actions cropped to the active width.
- **Representation:** dataset-defined with mean/std normalization.

### EVO1 (`evo1`)

- **Checkpoints:** no maintained LeRobot policy checkpoint. An upstream LIBERO
  artifact exists, but mainline documentation does not claim direct
  weight-preserving compatibility.
- **I/O:** configured images, language, and state padded to 24D → `50 × 24D`
  flow actions.
- **Representation:** dataset-defined with min-max normalization.

### FastWAM (`fastwam`)

- **Checkpoints:** [`base`](https://huggingface.co/lerobot/fastwam_base),
  [`LIBERO`](https://huggingface.co/lerobot/fastwam_libero_uncond_2cam224), and
  [`RoboTwin`](https://huggingface.co/lerobot/fastwam_robotwin_uncond_3cam_384).
- **I/O:** **lexicographically sorted** image keys, language, and optional
  state → a 32-step world-action-model output.
- **Representation:** checkpoint/dataset-defined with mean/std normalization.
  The released LIBERO checkpoint uses 7D controller-relative EEF actions; the
  RoboTwin checkpoint uses a checkpoint-defined 14D action.

### LingBot-VA (`lingbot_va`)

- **Checkpoints:** [`base`](https://huggingface.co/lerobot/lingbot_va_base),
  [`LIBERO-Long`](https://huggingface.co/lerobot/lingbot_va_libero_long), and
  [`RoboTwin`](https://huggingface.co/lerobot/lingbot_va_robotwin).
- **I/O:** camera clips in explicit `obs_cam_keys` order and language → a fixed
  30D semantic space.
- **Representation:** slots `0:7` are left EEF pose, `7:14` right EEF pose,
  `14:21` left joints, `21:28` right joints, and slots `28`/`29` the left/right
  grippers. Released checkpoints do not use the joint slots.

LIBERO activates `0:7` as EEF delta `xyz + rotation(3) + gripper`. RoboTwin
activates left and right `xyz + quaternion(xyzw) + gripper`; the environment
executes the poses through IK. Output normalization is q01/q99.

### MolmoAct2 (`molmoact2`)

- **Checkpoints:** [`LIBERO`](https://huggingface.co/lerobot/MolmoAct2-LIBERO-LeRobot),
  [`Think-LIBERO`](https://huggingface.co/lerobot/MolmoAct2-Think-LIBERO-LeRobot),
  [`Bimanual YAM`](https://huggingface.co/lerobot/MolmoAct2-BimanualYAM-LeRobot),
  [`DROID`](https://huggingface.co/lerobot/MolmoAct2-DROID-LeRobot),
  [`SO-100/101`](https://huggingface.co/lerobot/MolmoAct2-SO100_101-LeRobot),
  and original [`allenai/MolmoAct2`](https://huggingface.co/allenai/MolmoAct2)
  artifacts through `checkpoint_path`.
- **I/O:** explicit `image_keys`, language, and state → continuous, discrete,
  or both action paths.
- **Representation:** `control_mode`, image order, `norm_tag`, and checkpoint
  metadata are authoritative. LIBERO declares delta EEF pose; DROID, YAM, and
  SO checkpoints declare absolute joint pose. Normalization is usually q01/q99.

### VLA-JEPA (`vla_jepa`)

- **Checkpoints:** [`Pretrain`](https://huggingface.co/lerobot/VLA-JEPA-Pretrain),
  [`LIBERO`](https://huggingface.co/lerobot/VLA-JEPA-LIBERO), and
  [`SimplerEnv`](https://huggingface.co/lerobot/VLA-JEPA-SimplerEnv).
- **I/O:** config-ordered images, language, and optional state → a seven-step
  flow action; training can add a world-model loss.
- **Representation:** checkpoint/dataset-defined; state uses mean/std and
  action uses min-max normalization.

### Pending policy integrations

These checkpoints require the linked PR and should not be presented as
available in a released LeRobot version.

#### Wall-OSS-0.5 ([PR #4200](https://github.com/huggingface/lerobot/pull/4200))

[`lerobot/wall-oss-0.5`](https://huggingface.co/lerobot/wall-oss-0.5) fixes
26D state/action capacity, 32-step chunks, q01/q99 normalization, and camera
order `face_view`, then `right_wrist_view`. Its LeRobot config does not name the
26 channels, so it requires an already-canonical 26D dataset.

#### G0.5 ([PR #4195](https://github.com/huggingface/lerobot/pull/4195))

The gated, non-commercial checkpoint names are `lerobot/g05_base`,
`lerobot/g05_libero`, `lerobot/g05_robotwin20`, and `lerobot/g05_so101`.
The shared 20D layout is
`left_control(9), left_gripper(1), right_control(9), right_gripper(1)`; the
27D base adds `lower_body(7)`.

- Base/R1 Lite maps released joint groups into the 27D layout, uses head, left
  wrist, and right wrist with six-frame history, predicts 32, and executes 16.
- LIBERO maps its 7D right EEF delta into slots `10:16, 19`, uses exterior then
  right wrist, predicts 32, and executes 10.
- RoboTwin maps dual-arm 6D pose plus grippers into
  `0:6, 9, 10:16, 19`, uses head/left wrist/right wrist, predicts 32, and
  executes 8.
- SO-101 maps six right-arm joint channels into `10:16`; cameras are exterior,
  optional left wrist, then right wrist. It predicts 32 and executes 16.

The base uses z-score-tail normalization with q01/q99 grippers. Other profiles
use step-indexed q01/q99 statistics.

#### Being-H0.5 ([PR #4193](https://github.com/huggingface/lerobot/pull/4193))

[`being_h05_base`](https://huggingface.co/lerobot/being_h05_base) and
[`being_h05_robocasa`](https://huggingface.co/lerobot/being_h05_robocasa) use
three explicit `image_keys`, named state fields, and a masked 200D semantic
space.

- State slots: EEF position `0:3`, axis-angle `3:6`, gripper joints `44:46`,
  base position `70:73`, and base rotation `73:76`.
- Action slots: EEF translation `0:3`, axis-angle `3:6`, gripper `18:19`, base
  command `70:74`, and control mode `74:75`.
- Native RoboCasa action order is
  `EEF translation(3), EEF rotation(3), gripper(1), base motion(4),
control mode(1)`.

EEF/base actions are relative; gripper and control mode are absolute/binary.
The state is absolute. The base-rotation metadata/input-width mismatch must be
validated rather than inferred.

#### Hy-VLA ([PR #4196](https://github.com/huggingface/lerobot/pull/4196))

[`hy_vla_umi`](https://huggingface.co/lerobot/hy_vla_umi) and
[`hy_vla_robotwin`](https://huggingface.co/lerobot/hy_vla_robotwin) use cameras
in `top_head`, `hand_left`, `hand_right` order. Native state/action is:

```text
left xyz(3), quaternion xyzw(4), gripper(1),
right xyz(3), quaternion xyzw(4), gripper(1)
```

Each arm becomes `xyz(3), rotation-6D rows(6), gripper(1)`, giving 20D before
padding to 32D. UMI predicts 50 poses relative to the first state. RoboTwin
uses six frames at five-step intervals, predicts paired relative and absolute
tokens, executes seven physical absolute-EEF actions, then replans.

Published `lerobot/pi052_*` repositories are excluded because `pi052` is not a
registered policy type on `main` at this snapshot. RTC is an inference wrapper,
not an action representation. SARM, ROBOMETER, and TOPReward are reward models,
not action policies.

## Controller layouts

Policy processors may reorder these native environment layouts and invert that
mapping after inference:

- **PushT:** 2D agent state → absolute 2D target in simulator/pixel
  coordinates; native image key is `observation.image`.
- **LIBERO:** commonly 8D proprio → `[dx, dy, dz, dRx, dRy, dRz, gripper]`.
  This is controller-relative EEF control by default; `control_mode=absolute`
  selects the absolute controller. Cameras are exterior/agent view, then
  eye-in-hand/wrist.
- **RoboTwin joint mode:** 14D state/action, left seven then right seven. The
  current configuration does not attach per-joint names or units.
- **RoboTwin EEF mode:** current mainline state remains 14D joint state. Action
  is left then right `[xyz, quaternion xyzw, gripper]`; each pose delta is
  composed with the episode's initial pose. Native cameras are head, left
  wrist, right wrist.
- **RoboCasa:** 16D state in
  `base position(3), base quaternion(4), relative EEF position(3),
relative EEF quaternion(4), gripper qpos(2)` order. The 12D action is
  `base motion(4), control mode(1), EEF position(3), EEF rotation(3),
gripper(1)`. Native cameras are left exterior, eye-in-hand wrist, right
  exterior.
- **Meta-World:** 4D state and action; action lies in `[-1, 1]`. The exact
  Cartesian/gripper interpretation belongs to Meta-World. Camera is the corner
  view.
- **VLABench:** 7D state and default 7D EEF action; upstream environment defines
  exact units and rotation. Cameras are primary, secondary, wrist.
- **RoboMME:** 8D state and either 8D joint-angle or 7D EEF-pose action,
  selected by `action_space`. Cameras are exterior, wrist.
- **SO-100/SO-101:** six named motor positions → six named target motor
  positions. `SOFollowerConfig.use_degrees=true` by default; the alternative is
  calibration-scaled `[-100, 100]`. Cameras are user-defined.

## Camera order and physical role

ACT, Diffusion, the π family, SmolVLA, X-VLA, EO-1, EVO1, WALL-X, and VLA-JEPA
use visual `input_features` insertion order from checkpoint `config.json`.
Exceptions are:

- FastWAM sorts keys lexicographically.
- LingBot-VA uses `obs_cam_keys`.
- MolmoAct2 uses `image_keys`, then checkpoint metadata, then a sorted fallback.
- GR00T uses embodiment metadata.
- G0.5 uses `camera_order`.
- Being-H0.5 uses `image_keys`.
- Hy-VLA fixes `top_head`, `hand_left`, `hand_right`.
- Wall-OSS-0.5 uses `camera_key_mapping`.

Generic slot names are not physical roles. For released benchmark checkpoints:

- SmolVLA LIBERO/LIBERO-plus: exterior, wrist, masked remainder.
- SmolVLA Meta-World: corner, masked remainder.
- SmolVLA RoboTwin: head, left wrist, right wrist.
- SmolVLA RoboCasa: left exterior, eye-in-hand wrist, right exterior.
- SmolVLA RoboCerebra/RoboMME: exterior, wrist, masked remainder.
- SmolVLA VLABench: primary, secondary, wrist.
- VLA-JEPA LIBERO: `image` is exterior and `image2` wrist.
- VLA-JEPA pretrain: `exterior_1_left`, then `exterior_2_left`.
- MolmoAct2 LIBERO: `image` is exterior and `wrist_image` wrist.
- MolmoAct2 Bimanual YAM: top, left, right.
- MolmoAct2 DROID: `exterior_1_left`, `exterior_2_left`, `wrist_left`.
- LingBot-VA RoboTwin: head, left wrist, right wrist.
- LingBot-VA LIBERO: exterior, wrist.

## Units, ranges, and grippers

Normalization statistics are empirical dataset ranges, not robot safety
limits. A q01/q99 normalizer does not prove that a motor can safely travel to
those values.

- LeRobot SO followers expose degrees by default or calibration-scaled
  `[-100, 100]`. A checkpoint trained with one mode is not interchangeable with
  the other.
- Simulator grippers may use `[-1, 1]`, `[0, 1]`, or binary commands while
  state contains physical finger-joint positions. These are not
  interchangeable.
- EEF position is often meters and joint rotation often radians in MuJoCo or
  SAPIEN, but assume that only when the adapter or checkpoint guarantees it.
- Hard limits, velocity limits, collision limits, controller gains, and
  emergency-stop behavior belong to the robot/controller configuration, not
  the checkpoint normalization file.

## Inspect a checkpoint

Checkpoint files are more authoritative than this snapshot:

```python
from lerobot.configs.policies import PreTrainedConfig
from lerobot.policies.factory import make_pre_post_processors
from lerobot.processor.normalize_processor import (
    NormalizerProcessorStep,
    UnnormalizerProcessorStep,
)

checkpoint = "lerobot/pi05-libero"
config = PreTrainedConfig.from_pretrained(checkpoint)
preprocessor, postprocessor = make_pre_post_processors(
    config,
    pretrained_path=checkpoint,
)

print("input order:", list(config.input_features or {}))
print("output order:", list(config.output_features or {}))

for pipeline in (preprocessor, postprocessor):
    for step in pipeline.steps:
        print(type(step).__name__, step.get_config())
        if isinstance(step, (NormalizerProcessorStep, UnnormalizerProcessorStep)):
            for feature, stats in step.stats.items():
                print(feature, {name: value.tolist() for name, value in stats.items()})
```

Inspect dataset field names and statistics separately:

```python
from lerobot.datasets.lerobot_dataset import LeRobotDatasetMetadata

metadata = LeRobotDatasetMetadata("your-org/your-dataset")
print(metadata.features["observation.state"].get("names"))
print(metadata.features["action"].get("names"))
print(metadata.stats)
```

If names, units, frames, or controller semantics are missing, the dataset is
not self-describing enough for safe automatic adaptation.
