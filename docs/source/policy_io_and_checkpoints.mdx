# Policy Inputs, Outputs, Checkpoints, and Action Representations

This page is the central reference for the data contract between a LeRobot
dataset or environment, a policy checkpoint, and a robot controller. It covers
the policy types registered on `main`, public LeRobot-compatible checkpoints,
and four policy integrations that are still under review.

Research snapshot: **July 30, 2026**.

<Warning>

A policy class does not, by itself, define what every vector element means.
For many policies, `observation.state=[6]` and `action=[6]` only describe
shapes. The checkpoint, training dataset, robot driver, and environment
adapter define whether those values are joint angles, Cartesian poses, mobile
base commands, gripper commands, degrees, radians, meters, or normalized motor
units. Never infer semantics from the vector width alone.

</Warning>

## How to read this reference

There are three separate contracts:

1. **Architecture contract**: tensor shapes, action horizon, padding capacity,
   model-side normalization, and whether the policy can consume images,
   language, or state.
2. **Checkpoint contract**: ordered feature keys, camera roles, active vector
   dimensions, saved normalization statistics, and any embodiment-specific
   packing.
3. **Controller contract**: joint or end-effector control, coordinate frame,
   rotation convention, units, absolute or relative commands, gripper
   convention, control frequency, and physical limits.

All three must agree. A shape-compatible checkpoint is not necessarily
controller-compatible.

### “Relative” has two meanings

Keep these two axes separate:

- **Controller-relative**: the environment consumes a delta end-effector
  command, such as LIBERO's `delta xyz + delta axis-angle + gripper`.
- **Chunk-relative**: a processor subtracts the state at prediction time from
  selected action channels. In LeRobot this is controlled by
  `RelativeActionsProcessorStep` / `use_relative_actions`.

A LIBERO policy can use controller-relative EEF commands while
`use_relative_actions=false`: its dataset already contains EEF deltas, so no
second state-subtraction transform should be applied. See
[Action Representations](./action_representations) for absolute, relative
trajectory, and sequential-delta definitions.

### Meaning of “unknown”

**Unknown** means the semantic information is not encoded in the LeRobot
checkpoint/configuration or its maintained documentation. It does not mean
that the original dataset authors never specified it. Treat an unknown as a
required migration decision, not as permission to guess.

### Fixed semantic model layouts

#### X-VLA

| `action_mode`    | Model-facing order                                                                                         | Returned order            |
| ---------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------- |
| `ee6d`           | left `[xyz(3), rotation-6D(6), gripper]`, right in the same order = 20D                                    | 20D; grippers at 9 and 19 |
| `joint`          | left joints then gripper at 6; right joints then gripper at 13 = 14D                                       | 14D                       |
| `franka_joint7`  | First 7 active channels, then 13 zero pads                                                                 | First 7 channels          |
| `so101_bimanual` | left `[shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll, gripper]`, then right, then 8 pads | First 12 channels         |
| `auto`           | First `real_dim` channels, then zero padding to `max_dim`                                                  | First `real_dim` channels |

`auto` adapts shape only. It does not detect joint names, degrees versus
radians, arm side, coordinate frame, or gripper semantics.

#### LingBot-VA

The model always uses this 30D space:

| Channels | Meaning                                          |
| -------- | ------------------------------------------------ |
| `0:7`    | Left-arm EEF pose                                |
| `7:14`   | Right-arm EEF pose                               |
| `14:21`  | Left-arm joints; unused by released checkpoints  |
| `21:28`  | Right-arm joints; unused by released checkpoints |
| `28`     | Left gripper                                     |
| `29`     | Right gripper                                    |

- LIBERO activates `0:7`: EEF delta `xyz + rotation(3) + gripper`.
- RoboTwin activates `[0:7, 28, 7:14, 29]`: left
  `xyz + quaternion(xyzw) + gripper`, then right. The environment executes the
  poses through IK; the policy does not predict joint angles.

#### G0.5 (pending)

`left_control(9), left_gripper(1), right_control(9), right_gripper(1)`.
The 27D base adds `lower_body(7)`.

| -------------- | -------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------ |
| Base / R1 Lite | Released R1 joint groups in the 27D whole-body layout                      | head, left wrist, right wrist; six-step history | Checkpoint-selected flow or ActionCodec; 32 predicted, 16 executed |
| LIBERO         | Raw 7D right EEF delta + gripper → policy slots `10:16, 19`                | exterior, right wrist                           | Controller-relative EEF; 32 predicted, 10 executed                 |
| RoboTwin       | Raw 14D dual-arm 6D pose + grippers → slots `0:6, 9, 10:16, 19`            | head, left wrist, right wrist                   | 32 predicted, 8 executed                                           |
| SO-101         | Raw six right-arm joint channels → slots `10:16`; left wrist may be masked | exterior, optional left wrist, right wrist      | Joint control; 32 predicted, 16 executed                           |

The base uses z-score-tail normalization with q01/q99 grippers. LIBERO,
RoboTwin, and SO-101 use step-indexed q01/q99 statistics.

#### Hy-VLA (pending)

Native UMI/RoboTwin state and action are 16D:

```text
left xyz(3), quaternion xyzw(4), gripper(1),
right xyz(3), quaternion xyzw(4), gripper(1)
```

The processor converts each arm to
`xyz(3), rotation-6D rows(6), gripper(1)`, producing a 20D bimanual model
layout, then pads it to 32D.

| Checkpoint        | Representation                                                                                                    | History and execution                                                   |
| ----------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `hy_vla_umi`      | 50 poses relative to the first state in the chunk                                                                 | One frame; returns the 50-step physical chunk                           |
| `hy_vla_robotwin` | 20 relative tokens followed by 20 absolute tokens; postprocessor pairs them into 20 physical absolute-EEF actions | Six frames at five-environment-step intervals; executes 7, then replans |

#### Being-H0.5 (pending)

The model uses a 200D semantic space with validity masks:

| Signal                                       | Semantic slots    |
| -------------------------------------------- | ----------------- |
| State EEF position / axis-angle rotation     | `0:3` / `3:6`     |
| State gripper joints                         | `44:46`           |
| State mobile-base position / rotation        | `70:73` / `73:76` |
| Action EEF translation / axis-angle rotation | `0:3` / `3:6`     |
| Action gripper                               | `18:19`           |
| Action mobile-base command / control mode    | `70:74` / `74:75` |

The native RoboCasa action exposed to LeRobot is 12D in this order:
`EEF translation(3), EEF rotation(3), gripper(1), base motion(4),
control mode(1)`. The Being processor maps it to semantic slots and maps the
model output back to the environment layout. EEF/base actions are relative;
gripper and control mode are absolute/binary. The state uses named absolute
fields. Base rotation is quaternion metadata, while the current serialized
RoboCasa input feature exposes three base-rotation values; this mismatch should
remain explicitly validated rather than inferred by width.

#### Wall-OSS-0.5 (pending)

The base checkpoint fixes 26D state/action capacity, 32-step chunks, q01/q99
normalization, `face_view`, and `right_wrist_view`. It does **not** publish
field names for the 26 positions in LeRobot's `config.json`. The integration
therefore requires an already-canonical 26D dataset and intentionally does not
adapt arbitrary robots.

### Hardware ranges and grippers

Normalization statistics are empirical dataset ranges, not robot safety limits.
A q01/q99 normalizer does not prove that a motor can safely travel to those
values.

- For LeRobot SO followers, the default driver exposes degrees, while an
  alternative calibration mode exposes `[-100, 100]`. Gripper is another named
  motor channel in that same configured unit.
- Simulator grippers often use binary or bounded controller commands such as
  `[-1, 1]` or `[0, 1]`, while state may contain two physical finger-joint
  positions. Those are not interchangeable.
- EEF position is often meters and joint rotation often radians in MuJoCo or
  SAPIEN, but this page only labels units when the LeRobot adapter or checkpoint
  contract makes that guarantee.
- Robot hard limits, velocity limits, collision limits, controller gains, and
  emergency-stop behavior belong to the robot/controller configuration, not
  the learned policy's normalization file.

## Inspect the exact serialized contract

The checkpoint files are more authoritative than this snapshot. Inspect the
config and processor order before deployment:

```python
from lerobot.configs.policies import PreTrainedConfig
from lerobot.policies.factory import make_pre_post_processors
from lerobot.processor.normalize_processor import (
    NormalizerProcessorStep,
    UnnormalizerProcessorStep,
)

checkpoint = "lerobot/pi05-libero"
config = PreTrainedConfig.from_pretrained(checkpoint)
preprocessor, postprocessor = make_pre_post_processors(
    config,
    pretrained_path=checkpoint,
)

print("input order:", list(config.input_features or {}))
print("output order:", list(config.output_features or {}))

for pipeline in (preprocessor, postprocessor):
    for step in pipeline.steps:
        print(type(step).__name__, step.get_config())
        if isinstance(step, (NormalizerProcessorStep, UnnormalizerProcessorStep)):
            for feature, stats in step.stats.items():
                print(feature, {name: value.tolist() for name, value in stats.items()})
```

Also inspect dataset feature names:

```python
from lerobot.datasets.lerobot_dataset import LeRobotDatasetMetadata

metadata = LeRobotDatasetMetadata("your-org/your-dataset")
print(metadata.features["observation.state"].get("names"))
print(metadata.features["action"].get("names"))
print(metadata.stats)
```

If `names`, units, frames, or controller semantics are missing, the dataset is
not self-describing enough for safe automatic adaptation.

## Proposal: one contract-driven dataset adapter

LeRobot already has the right execution primitive:
serializable `PolicyProcessorPipeline` steps. What is missing is one
machine-readable I/O contract shared across policies and checkpoints. OpenPI's
training configuration makes a useful separation between **repack transforms**
(dataset-only key remapping), **data transforms** (robot/embodiment conversions
used for training and inference), and **model transforms** (tokenization,
resize, pad). LeRobot should adopt that separation in its contract, without
putting every embodiment into one giant policy-specific function.

### Proposed serialized `PolicyIOContract`

Every maintained checkpoint should include a versioned contract with:

```yaml
version: 1
cameras:
  - slot: exterior
    feature: observation.images.image
    aliases: [agentview, head, top]
    role: exterior
    side: center
    order: 0
    history: { frames: 1, stride: 1 }
    required: true
state:
  fields:
    - {
        name: shoulder_pan,
        semantic: joint.position,
        side: right,
        unit: degree,
      }
action:
  fields:
    - {
        name: shoulder_pan,
        semantic: joint.position,
        side: right,
        unit: degree,
      }
  reference: absolute
  controller: joint_position
  horizon: 50
  execute: 10
normalization:
  mode: quantiles
  stats_source: policy_preprocessor_step_3_normalizer_processor.safetensors
```

Each vector field needs, where applicable:

- semantic type: joint position/velocity/torque, EEF translation/rotation,
  gripper, mobile-base translation/rotation, or controller mode;
- robot side and ordered joint name;
- unit and valid physical range;
- coordinate frame;
- rotation representation and component order (`axis_angle`, `rpy`,
  quaternion `xyzw`/`wxyz`, or rotation-6D);
- absolute/relative/sequential-delta reference and the state field used as the
  origin;
- model slot and raw dataset slot;
- required, optional, masked, or padded status;
- gripper open/close convention and hardware range.

### Proposed `DatasetToPolicyContractProcessor`

The single public processor should **compile** a deterministic pipeline:

```text
dataset keys
  → exact/alias key repack
  → camera-role assignment and history sampling
  → named state/action field selection
  → unit/frame/rotation/controller conversion
  → absolute/relative conversion
  → semantic slot packing and padding
  → checkpoint normalization
  → model-specific token/image transforms
```

Postprocessing applies the invertible steps in reverse before dispatching an
action to the environment or robot.

Resolution should follow this order:

1. Exact semantic ID and side, for example
   `joint.position/right/shoulder_pan`.
2. An explicit user override stored with the run.
3. A unique checkpoint alias.
4. A high-confidence name match only when semantic type, side, unit, and width
   also agree.
5. Otherwise fail with a diagnostic and a generated candidate mapping.

The processor must never silently decide that “the first six values look like
joints.” Six values can be SO-101 motor targets, EEF `xyz + axis-angle`, mobile
base plus gripper, or an arbitrary learned latent. Shape is a validation
signal, not semantic evidence.

### Suggested user surface

```bash
lerobot-train \
  --dataset.repo_id=your-org/custom-data \
  --policy.path=lerobot/pi05_base \
  --io_adapter.auto=true \
  --io_adapter.mapping=io_mappings/my_robot_to_pi05.yaml \
  --io_adapter.write_report=outputs/io_contract_report.json
```

The report should contain:

- every source → target feature and vector-field mapping;
- camera role/order/history and any masked views;
- every unit, frame, rotation, and absolute/relative conversion;
- action/state channels that were padded, dropped, or left unmapped;
- source and target normalization-stat fingerprints;
- non-invertible transforms;
- warnings requiring explicit acceptance.

`--rename_map` can remain as a lightweight observation-key override, but the
contract adapter should supersede it for action fields, vector order, cameras,
units, and embodiment conversion.

### Migration plan

1. Add `PolicyIOContract` and a validator without changing inference.
2. Generate contracts for current benchmark checkpoints from their serialized
   configs and processors; fail CI if documented camera/action layouts drift.
3. Add named vector metadata to LeRobot datasets and robot recordings.
4. Implement generic pack/unpack, camera-role, unit, rotation, and
   absolute/relative steps.
5. Migrate the explicit adapters first: X-VLA, LingBot-VA, MolmoAct2, G0.5,
   Being-H0.5, and Hy-VLA.
6. Keep policy-specific transforms only for genuinely model-specific work
   such as tokenization, image normalization, ActionCodec, or semantic-slot
   architecture.
7. Enable automatic mapping only when the resolver produces one unambiguous,
   fully validated plan.

This gives LeRobot one front door for custom datasets while preserving the
checkpoint-specific processors that are already necessary. The unification
target is the **contract and resolver**, not one unsafe universal vector guesser.
