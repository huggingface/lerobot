# DM0.5 for LeRobot

DM05, also released as DM0.5, is Dexmal's Vision-Language-Action model for open-world robot control. The LeRobot
adapter preserves the OpenDM model path while using standard LeRobot datasets, processors, training,
checkpointing, Hub loading, and evaluation.

For model details, see the [DM0.5 technical blog](https://www.dexmal.com/blog/dm0.5/index_en.html), the
[OpenDM repository](https://github.com/Dexmal/OpenDM), and the raw
[Dexmal/DM05](https://huggingface.co/Dexmal/DM05) release.

## Installation

```bash
pip install -e ".[training,dm05]"   # training
pip install -e ".[libero,dm05]"     # LIBERO evaluation on Linux
```

## Checkpoint

Use `lerobot/dm05_base` with `--policy.path`. It is a self-contained LeRobot conversion of the raw OpenDM
checkpoint and supports `DM05Policy.from_pretrained()`.

The base config records OpenDM's 14-dimensional state/action contract. DM05's core model supports up to 32
dimensions; fresh fine-tuning resolves the effective image, state, and action features from the target dataset.

## Dataset contract

DM05 accepts standard LeRobot datasets with:

- one or more image or video observations;
- `observation.state`;
- `action`;
- task descriptions.

Set `policy.image_keys` when camera order must be explicit. RoboTwin, ALOHA, and other sources do not need a
DM05-specific reader after conversion to the standard LeRobot schema. Keep the standard `observation.state` and
`action` keys; use `rename_map` only to align camera names.

## Training

The LIBERO recipe follows OpenDM:

```bash
lerobot-train \
  --dataset.repo_id=lerobot/libero \
  --rename_map='{"observation.images.image": "observation.images.front", "observation.images.image2": "observation.images.wrist"}' \
  --dataset.video_backend=pyav \
  --policy.path=lerobot/dm05_base \
  --policy.add_state=false \
  --policy.chunk_size=10 \
  --policy.n_action_steps=10 \
  --policy.repo_id=your_repo_id \
  --output_dir=outputs/train/dm05-libero \
  --steps=50000 \
  --batch_size=8 \
  --policy.device=cuda
```

### Key training parameters

| Parameter                     | LIBERO value                        | Meaning                                                              |
| ----------------------------- | ----------------------------------- | -------------------------------------------------------------------- |
| `dataset.repo_id`             | `lerobot/libero`                    | Standard LeRobot training dataset                                    |
| `policy.path`                 | `lerobot/dm05_base`                 | Self-contained base checkpoint                                       |
| `rename_map`                  | `image`/`image2` to `front`/`wrist` | Camera names used by the eval command and `lerobot/dm05_libero`      |
| `policy.add_state`            | `false`                             | Matches OpenDM's LIBERO prompt without state tokens                  |
| `policy.use_relative_actions` | `false` (checkpoint default)        | Learns stored actions unchanged; relative mode is an explicit opt-in |
| `policy.chunk_size`           | `10`                                | Number of actions predicted per chunk                                |
| `policy.n_action_steps`       | `10`                                | Number executed before the next model call; at most `chunk_size`     |
| `policy.repo_id`              | `your_repo_id`                      | Hub destination; use `policy.push_to_hub=false` for local-only runs  |

Environment control mode is configured separately from the policy action representation. Relative mode requires
matching state/action dimensions.

### Cameras

The camera set is part of the policy config, and the prompt always renders exactly those cameras. Fine-tuning from
`lerobot/dm05_base`, which declares none, takes the training dataset's cameras. A fine-tuned checkpoint keeps its
own camera names: map a dataset with different names onto them with `--rename_map`, for example
`--rename_map='{"observation.images.top": "observation.images.front"}'`.

### Normalization statistics

Training uses the dataset's state/action statistics in `meta/stats.json`. Action statistics must match the representation used for training. With `policy.use_relative_actions=true`, compute them after the relative-action transform, using the same chunk size and excluded dimensions. See the [relative-action guide](./action_representations#using-relative-actions-in-lerobot).

## Evaluation

The LIBERO checkpoint `lerobot/dm05_libero` was trained for 50,000 steps and evaluated on all 40
LIBERO tasks with 5 episodes per task:

```bash
MUJOCO_GL=egl lerobot-eval \
  --policy.path=lerobot/dm05_libero \
  --env.type=libero \
  --env.task=libero_spatial,libero_object,libero_goal,libero_10 \
  --env.camera_name_mapping='{"agentview_image":"front","robot0_eye_in_hand_image":"wrist"}' \
  --env.observation_height=256 \
  --env.observation_width=256 \
  --env.control_mode=relative \
  --eval.n_episodes=5 \
  --eval.batch_size=1 \
  --seed=7 \
  --policy.device=cuda
```

| Suite     |           Successes |
| --------- | ------------------: |
| Spatial   |               49/50 |
| Object    |               50/50 |
| Goal      |               50/50 |
| LIBERO-10 |               48/50 |
| **Total** | **197/200 (98.5%)** |

This is a 200-episode reproduction check, not the 2,000-episode LIBERO benchmark protocol.

## RoboDojo MEM SFT

Train DM05-MEM on RoboDojo `cover_blocks` with effective batch 64, then evaluate
the saved checkpoint on 50 layouts.

### Training

Install `pip install -e '.[training,dm05]'`. Set `BASE_MODEL` to a complete LeRobot
conversion of [Dexmal/DM05-MEM](https://huggingface.co/Dexmal/DM05-MEM), including
`core_config`, processor assets and policy weights (not the raw release), and `DATASET_ROOT`
to the official RoboDojo `cover_blocks` subset: 100 episodes, 54,296 frames at 25 FPS,
three 640x480 cameras, and 14-dimensional state and absolute joint actions.
Create the subset with LeRobot's dataset editor, retaining source episodes 300--399
and aggregating their statistics into the subset's `meta/stats.json`. Do not use
full-benchmark statistics with an episode filter.

```bash
torchrun --standalone --nproc_per_node=8 -m lerobot.scripts.lerobot_train \
  --dataset.repo_id=local/robodojo-cover-blocks --dataset.root="$DATASET_ROOT" \
  --dataset.video_backend=pyav \
  --policy.path="$BASE_MODEL" \
  --policy.push_to_hub=false --policy.use_memory=true \
  --policy.memory_image_key=observation.images.cam_high \
  --policy.memory_frames=20 --policy.memory_stride=25 --policy.robot_type=Aloha \
  --policy.image_keys='["observation.images.cam_high","observation.images.cam_left_wrist","observation.images.cam_right_wrist"]' \
  --policy.chunk_size=25 --policy.n_action_steps=25 --policy.tokenizer_max_length=1536 \
  --policy.use_relative_actions=false --policy.norm_clip=false --policy.device=cuda \
  --policy.llm_attn_implementation=sdpa --policy.vision_attn_implementation=sdpa \
  --policy.scheduler_warmup_steps=600 --policy.scheduler_decay_steps=30000 \
  --batch_size=8 --parallelism.dp_shard=8 --accelerator.mixed_precision=bf16 \
  --steps=40000 --save_freq=5000 --log_freq=25 --num_workers=4 --seed=1000 \
  --output_dir=outputs/train/dm05-mem-cover
```

Eight Pro6K GPUs, batch 8 per GPU and accumulation 1 give effective batch **64**.
All 100 trajectories are used with shuffled-frame sampling; no trajectory holdout.
Train for 40,000 optimizer updates and save every 5,000 updates. Warm up for 600
updates, decay to `2.5e-6` by 30,000 updates, and keep that learning rate to 40,000.

### Evaluation

Install [RoboDojo](https://github.com/RoboDojo-Benchmark/RoboDojo) and its XPolicyLab
dependencies in the simulator environment, and install this LeRobot checkout in the
policy environment. Evaluation requires a RoboDojo-side `LeRobotDM05` adapter,
which is not included in this repository. It must load the saved LeRobot processors,
update MEM history on every simulation frame, and reset the policy at episode boundaries.
For chunk deployment, local and remote execution collect the main camera on every
control frame, even while playing queued actions. Run observation capture at the
training rate (25 FPS here): `memory_stride=25` means 25 captured frames, not 25
predictions. Remote deployment sends the sampled history and padding mask with
each chunk request; direct `PolicyRunner` callers must provide the same history
in `ObservationSnapshot`. Reset the execution engine between episodes.
Create `$ROBODOJO/XPolicyLab/policy/LeRobotDM05/deploy.yml`:

```yaml
policy_name: LeRobotDM05
protocol: ws
host: localhost
port: 9000
bench_name: RoboDojo
task_name: cover_blocks
env_cfg_type: arx_x5
action_type: joint
eval_batch: false
seed: 0
device: cuda
model_path: /absolute/path/to/checkpoints/040000/pretrained_model
```

From `$ROBODOJO`, start the policy server in the policy environment:

```bash
PYTHONPATH="$ROBODOJO:$ROBODOJO/XPolicyLab" python XPolicyLab/setup_policy_server.py \
  --config_path XPolicyLab/policy/LeRobotDM05/deploy.yml
```

Then run the simulator client in its environment:

```bash
EVAL_NUM=50 bash scripts/eval_policy.sh --task_name cover_blocks --env_cfg_type arx_x5 \
  --device_id 0 --policy_name LeRobotDM05 --port 9000 --protocol ws --host localhost \
  --root_dir "$ROBODOJO" --eval_batch false --seed 0 --additional_info action_type=joint
```

Use one environment per policy process and layouts 0--49. Set the simulator's
evaluation count to 50 and verify that `_result.json` contains all 50 layout IDs.
Report success rate as successful layouts divided by 50. The adapter loads the saved
pre/postprocessors and updates the observation history on every simulation frame.

Best measured success rate: **92% (46/50 layouts)**.

## Checkpoint layout

Use the complete checkpoint directory, which contains policy weights, config, and processor state. A standalone
`model.safetensors` is not sufficient for training or inference.
