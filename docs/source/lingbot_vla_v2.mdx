# LingBot-VLA 2.0

LingBot-VLA 2.0 is an open-source vision-language-action model integrated into LeRobot as
the `lingbot_vla_v2` policy. It pairs a **Qwen3-VL-4B** multimodal backbone (native-resolution
image tokens via `image_grid_thw`) with a **sparse-MoE Qwen2 action expert** (32 experts,
top-4, sigmoid router) and **Flow-Matching** continuous action generation over a unified
**55-D** state/action space, supporting cross-embodiment and bimanual manipulation.

It is the successor to the [`LingBot-VA`](./lingbot_va) (v1) policy from the same authors and
slots into the same post-train → evaluate → deploy flow as π0, SmolVLA, WALL-OSS and v1.

## Model Overview

- **Backbone:** Qwen3-VL-4B (native-resolution patchification; the image token budget is
  capped with `image_max_pixels` / `image_min_pixels`).
- **Action expert:** dual-stream Qwen2 with a sparse Mixture-of-Experts MLP (32 experts,
  top-4 routing, sigmoid router, `routed_scaling_factor=4.0`) plus a shared expert.
- **Action generation:** flow matching over a padded 55-D canonical state/action space
  (`max_state_dim = max_action_dim = 55`, `chunk_size = 50`, `num_steps = 10`).
- **Reference checkpoint:** `robbyant/lingbot-vla-v2-6b` (~6B, "Native Depth").

### What the LeRobot Integration Covers

- The `lingbot_vla_v2` policy (config / modeling / processor) with strict-loading of the
  upstream checkpoint and `lerobot-train` post-training.
- A standard LeRobot processor pipeline (rename → batch → relative actions → normalize →
  slot mapping → Qwen3-VL image tokenization → chat template → tokenizer), where only the
  raw→canonical 55-D slot mapping step is LingBot-specific. Normalization stats come from
  the dataset (`dataset_stats`) and live in the saved processor state.
- Flash-attention is not required: the policy defaults to `sdpa` attention (fused PyTorch
  kernels, bf16).

## Installation

```bash
pip install -e ".[training,lingbot_vla2]"
```

This pulls the LingBot-VLA v2 optional dependencies, including a Qwen3-VL capable
`transformers` build and `qwen-vl-utils`.

## Usage

To use LingBot-VLA 2.0 in LeRobot, specify the policy type as:

```python
policy.type=lingbot_vla_v2
```

When fine-tuning from the released upstream checkpoint, start from the converted LeRobot
checkpoint [`lerobot/lingbot_vla_v2_base`](https://huggingface.co/lerobot/lingbot_vla_v2_base)
(the raw upstream checkpoint only carries a minimal `config.json` and is not loaded at
runtime). No embodiment is baked in: at fine-tuning time you provide the per-robot slot
mappings and LeRobot builds the real processor from them plus the dataset stats.
`config.json` carries `type: lingbot_vla_v2`; the Qwen3-VL tokenizer/processor is pulled
from `Qwen/Qwen3-VL-4B-Instruct` (or a local `--policy.tokenizer_path`) at processor build
time, as for the other VLAs in this repo. Pass it with LeRobot's standard checkpoint entry
point, `policy.path`.
Do not pass `policy.type` in that command; LeRobot infers `lingbot_vla_v2` from the
checkpoint's `config.json`.

LingBot-VLA 2.0 also requires the per-robot slot mapping used by its processor:

- `policy.state_slots` / `policy.action_slots`: typed dict fields mapping dataset state/action keys onto canonical slots.
- `policy.tokenizer_path`: Qwen3-VL processor/tokenizer path or Hub id.

Norm stats are derived from the dataset automatically (LeRobot's `dataset_stats` mechanism) — no separate norm-stats file needed.

## Checkpoints

| Checkpoint                        | Params | Notes                                                                                                                   |
| --------------------------------- | ------ | ----------------------------------------------------------------------------------------------------------------------- |
| `lerobot/lingbot_vla_v2_base`     | ~6B    | Converted from `robbyant/lingbot-vla-v2-6b` ("Native Depth" variant); the 84 distillation-head tensors are dropped.     |
| `lerobot/lingbot_vla_v2_robotwin` | ~6B    | Converted from the RoboTwin post-trained upstream weights, with its processor (slot mappings + q01/q99 stats) embedded. |

## Training / fine-tuning

Use the standard LeRobot training script with the LingBot-VLA v2 policy and the required
robot-config assets:

```bash
lerobot-train \
  --dataset.repo_id=<your/dataset> \
  --policy.path=lerobot/lingbot_vla_v2_base \
  --policy.repo_id=<your/lingbot_vla_v2_policy> \
  --policy.state_slots='{"observation.state.arm.position": {"origin_keys": [{"observation.state": {"start": 0, "end": 6}}]}}' \
  --policy.action_slots='{"action.arm.position": {"origin_keys": [{"action": {"start": 0, "end": 6}}], "subtract_state": false}}' \
  --policy.tokenizer_path=Qwen/Qwen3-VL-4B-Instruct \
  --policy.dtype=bfloat16 \
  --policy.attention_implementation=sdpa \
  --policy.image_max_pixels=262144 \
  --policy.image_min_pixels=131072 \
  --policy.loss_type=L1_fm \
  --policy.optimizer_lr=5e-5 \
  --policy.scheduler_decay_lr=5e-5 \
  --batch_size=1 \
  --steps=40000
```

For a local smoke test without Hub access, add `--policy.push_to_hub=false`,
`--save_checkpoint=false`, `--num_workers=0`, and use local paths for
`tokenizer_path` and `policy.path`.

Official real-world hyperparameters: lr `5e-5` (constant), AdamW, global batch 3, `L1_fm`
loss, `tokenizer_max_length=72`. Multi-GPU is supported through `torchrun` as a plain
launcher with `--parallelism.*` / `--accelerator.*` flags (no accelerate config files);
the policy has been run with 4-way FSDP on 24 GB cards (cap `image_max_pixels` and enable
`gradient_checkpointing` to fit).

### Key Training Parameters

| Parameter                               | Default                     | Description                                                                                                 |
| --------------------------------------- | --------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `state_slots`                           | `null`                      | Typed dict mapping dataset state keys into the 55-D canonical LingBot slots.                                |
| `action_slots`                          | `null`                      | Typed dict mapping dataset action keys into the 55-D canonical LingBot slots.                               |
| `tokenizer_path`                        | `Qwen/Qwen3-VL-4B-Instruct` | Qwen3-VL processor/tokenizer path or Hub id. Use a local path when the training node cannot access the Hub. |
| `dtype`                                 | `bfloat16`                  | Model dtype; LeRobot maps this to Accelerate mixed precision. Use `float32` for CPU smoke tests.            |
| `attention_implementation`              | `sdpa`                      | Action-stream attention backend: `eager` or `sdpa`.                                                         |
| `vit_attn_implementation`               | `sdpa`                      | Qwen3-VL vision attention backend; use Hugging Face names such as `eager`, `sdpa`, or `flash_attention_2`.  |
| `moe_implementation`                    | `fused`                     | `fused` (the only supported value) matches the released checkpoint's grouped expert layout.                 |
| `image_max_pixels` / `image_min_pixels` | `262144` / `131072`         | Qwen3-VL dynamic-resolution bounds; increasing them can raise memory quadratically with eager attention.    |
| `loss_type`                             | `fm`                        | Flow-matching loss; the real-world recipe uses `L1_fm`.                                                     |

### Acceleration Options

The default `attention_implementation=sdpa` uses fused PyTorch kernels in the model dtype
(bf16 on GPU). Set `attention_implementation=eager` for a conservative debug fallback. `gradient_checkpointing=true`
trades ~30% step time for a much smaller activation footprint, and `moe_metrics_interval=N`
(default 50) limits MoE monitoring overhead to every Nth step. `sdpa` preserves
the tested eager parity.

MoE is enabled by default (`use_moe=true`) to match the released v2 architecture. Do not disable
it, change `token_num_experts`, `token_top_k`, `token_moe_intermediate_size`,
`token_shared_intermediate_size`, `router_activation`, or `routed_scaling_factor` when loading
MoE checkpoints unless the checkpoint was trained with the same architecture. The released
upstream checkpoint stores experts in the grouped/fused layout, so `moe_implementation=fused`
is the default for checkpoint compatibility.

Example 8-GPU launch:

```bash
torchrun --nproc_per_node=8 -m lerobot.scripts.lerobot_train \
  --dataset.repo_id=<your/dataset> \
  --policy.path=lerobot/lingbot_vla_v2_base \
  --policy.state_slots='{"observation.state.arm.position": {"origin_keys": [{"observation.state": {"start": 0, "end": 6}}]}}' \
  --policy.action_slots='{"action.arm.position": {"origin_keys": [{"action": {"start": 0, "end": 6}}], "subtract_state": false}}' \
  --policy.dtype=bfloat16 \
  --policy.attention_implementation=sdpa \
  --policy.vit_attn_implementation=sdpa \
  --policy.moe_implementation=fused \
  --policy.loss_type=L1_fm \
  --parallelism.dp_shard=-1 \
  --accelerator.mixed_precision=bf16 \
  --batch_size=1 \
  --steps=40000
```

## Data format

Raw per-embodiment features are mapped onto the trained 55-D canonical slots by the
typed slot mappings (`state_slots` / `action_slots`) in the config. Missing source keys
are warned once per canonical slot, but the slot mappings must still match the
checkpoint's canonical layout to avoid wrong padding or normalization.

When fine-tuning a converted checkpoint on a **new** embodiment, the explicit
`--policy.state_slots` / `--policy.action_slots` take precedence over the assets
embedded in the checkpoint (a warning is logged when they differ). Checkpoints saved
during fine-tuning embed the new slot mappings, so they stay self-contained and portable.
Norm stats are derived from the dataset automatically (LeRobot's `dataset_stats`
mechanism) and embedded in the processor's state.

## Example: adapting to a single-arm robot

This example adapts the released checkpoint to a 7-DoF single arm (6 arm joints + 1 gripper,
joint angles in degrees, absolute action space) with two cameras (`front` + `wrist`), e.g. a
Seeed reBot B601-RS dataset recorded with LeRobot.

**1. Declare the slot mappings.** The canonical layout packs filled dims from
position 0 of each slot; unfilled slots are zero-padded and excluded from the loss via
`joint_mask`. `subtract_state: false` keeps an action slot absolute (set it to `true` only
when the dataset stores actions as deltas relative to the state, and never for
`effector.position`). The mappings are passed directly as config fields — no YAML or
stats files:

```bash
STATE_SLOTS='{
  "observation.state.arm.position": {"origin_keys": [{"observation.state": {"start": 0, "end": 6}}]},
  "observation.state.effector.position": {"origin_keys": [{"observation.state": {"start": 6, "end": 7}}]}
}'
ACTION_SLOTS='{
  "action.arm.position": {"origin_keys": [{"action": {"start": 0, "end": 6}}], "subtract_state": false},
  "action.effector.position": {"origin_keys": [{"action": {"start": 6, "end": 7}}], "subtract_state": false}
}'
```

Here `state[0:6]` / `action[0:6]` map onto the 14-D `arm.position` slot (rest padded) and
`state[6]` / `action[6]` onto the 2-D `effector.position` slot. Cameras are handled by
LeRobot's standard `--rename_map` (dataset camera keys → the checkpoint's declared
`input_features` cameras); unmapped canonical views are zero-filled.

**2. Fine-tune** with the standard training command. Normalization stats are derived
from the dataset automatically (the processor's `NormalizerProcessorStep` uses
`dataset_stats`); checkpoints saved during fine-tuning embed the slot mappings, stats
and processors, so they stay self-contained and portable:

```bash
lerobot-train \
  --dataset.repo_id=<your/rebot_dataset> \
  --dataset.root=<dataset_root> \
  --policy.path=lerobot/lingbot_vla_v2_base \
  --policy.state_slots="$STATE_SLOTS" \
  --policy.action_slots="$ACTION_SLOTS" \
  --rename_map='{"observation.images.front": "observation.images.camera_top", "observation.images.wrist": "observation.images.camera_wrist_left"}' \
  --policy.dtype=bfloat16 \
  --policy.loss_type=L1_fm \
  --policy.optimizer_lr=5e-5 \
  --policy.scheduler_decay_lr=5e-5 \
  --batch_size=4 \
  --steps=5000 \
  --save_freq=1000
```

**3. Deploy** on the robot with `lerobot-rollout` (`--strategy.type=episodic` records
evaluation episodes; pass the same `--rename_map` so camera observations match the
checkpoint's `input_features`). `select_action` returns actions in the robot's raw
action space (here: 7 absolute joint angles in degrees) after the postprocessor inverts
the slot mapping, un-normalizes and converts relative actions back to absolute:

```bash
lerobot-rollout \
  --strategy.type=episodic \
  --policy.path=<output_dir>/checkpoints/last/pretrained_model \
  --policy.n_action_steps=25 \
  --device=cuda \
  --robot.type=<your_robot_type> \
  --robot.port=<port> \
  --robot.cameras="{ wrist: {...}, front: {...} }" \
  --task="pick up the cube" \
  --fps=30 \
  --dataset.repo_id=<eval_repo_id> \
  --dataset.num_episodes=10 \
  --dataset.push_to_hub=false
```

## Numerical validation

The port was validated layer-by-layer against the original `Robbyant/lingbot-vla-v2`
implementation (transformers 4.57.3 native vs LeRobot's 5.5.4 port, both eager, same weights
and fixed inputs/noise):

- **Strict-load key parity:** the port `state_dict` matches the checkpoint's action-path keys
  exactly (1624 keys, 0 missing / 0 unexpected; only the 84 distillation-head keys are skipped
  via `use_depth=False`).
- **Bit-exact intermediates:** prefix token embeddings, the full per-layer Qwen3-VL KV cache,
  `embed_suffix` (state/action/time embeddings), and the MoE router logits + top-4 expert
  selection are numerically identical (max\|Δ\| = 0) in both bf16 and fp32.
- **Only residual:** the MoE expert SwiGLU output differs by ~0.06 per block, isolated to the
  vendored triton `fused_moe` kernel's internal reduced-precision tensor-core MMA (the port's
  eager path is full-precision). This is a benign kernel-precision difference, not an
  architecture or weight-loading defect.

## Benchmark

Upstream-reported scores on **RoboTwin 2.0** (50 dual-arm manipulation tasks × 100
episodes each, Sapien simulation, `demo_clean` / `demo_randomized` task configs,
success judged by per-task `expert_check`):

| Setting           | Success rate |
| ----------------- | ------------ |
| `demo_clean`      | 93.52 %      |
| `demo_randomized` | 92.80 %      |

These numbers are reported by the LingBot team for the released upstream weights
([project page](https://github.com/Robbyant/lingbot-vla-v2)); the numerical-validation
section above shows this port matches those weights bit-exactly on the action path.
To reproduce the evaluation through the LeRobot port with the converted checkpoint:

```bash
lerobot-eval \
  --policy.path=lerobot/lingbot_vla_v2_robotwin \
  --env.type=robotwin \
  --env.task=beat_block_hammer \
  --eval.batch_size=1 \
  --eval.n_episodes=5 \
  --rename_map='{"observation.images.head_camera": "observation.images.cam_high", "observation.images.left_camera": "observation.images.cam_left_wrist", "observation.images.right_camera": "observation.images.cam_right_wrist"}'
```

The RoboTwin post-trained checkpoint ships with its processor (slot mappings + q01/q99
normalization stats) embedded, so the command runs out of the box. See
[RoboTwin](./robotwin) for the environment setup.

## Notes

- The Qwen3-VL backbone and Qwen2 action expert are adapted from HuggingFace Transformers and
  the upstream `Robbyant/lingbot-vla-v2` repository, kept close to source with scoped ruff
  per-file-ignores.
- The implementation reuses the Transformers Qwen configs/model builders where they match the
  released checkpoint. The LeRobot wrapper keeps custom forward/piping code for the LingBot
  dual-stream action expert, cached visual-language prefix, action/time-conditioned suffix,
  sparse-MoE routing/load-balancing, and flow-matching action head.
- Inference action postprocessing is handled by the postprocessor pipeline (inverse slot
  mapping → unnormalize → absolute actions), so `select_action` / `predict_action_chunk`
  return raw dataset action keys after the policy postprocessing path.
