# 即時分塊（RTC）[[real-time-chunking-rtc]]

即時分塊（Real-Time Chunking，RTC）讓以流匹配（flow matching）為基礎的大型機器人策略（policy），例如 [Pi0](./pi0)、[Pi0.5](./pi05) 與 [SmolVLA](./smolvla)，即使推論延遲很高，也能產生流暢、連續且反應靈敏的動作。LeRobot 提供原本在推論時進行引導的 guided 模式；對於相容的 Pi05 檢查點，也提供訓練時的動作條件化（action conditioning），搭配低成本的硬前綴（hard prefix）推論。

這些策略會一次產生一段未來的動作區塊（chunk，例如一次 50 步），而不是單一動作。
由於模型很大，產生每個區塊所需的時間，比機器人執行它的時間還要長。
如果只是單純地依序執行區塊，每當下一個區塊太晚送達，或與先前已執行的動作不一致時，就會出現停頓、不順暢的過渡，或行為突然轉變等問題。

RTC 的解法是在機器人繼續執行目前區塊的同時，以非同步的方式產生下一個區塊，並引導新的區塊，讓它與前一個區塊中已執行的部分順暢銜接。

## RTC 的運作方式（簡化版）[[how-rtc-works-simplified]]

RTC 讓機器人在移動的同時就先預想下一步。當機器人正在執行一個動作區塊時，RTC 就會提早開始產生下一個區塊。
但等新區塊準備好時，機器人已經又移動了一些，因此 RTC 必須確保新區塊仍能與機器人目前的動作順暢銜接。

為此，RTC 將新區塊的開頭視為影像修補（inpainting），也就是「填補空缺」的問題：
它會輕微調整新區塊的前段，讓它自然地接上機器人正在進行的動作。結果就是沒有停頓，也沒有突然的跳動。

以技術上的說法，RTC 會在流匹配的去雜訊過程中加入一個引導項（guidance term），強制新區塊中重疊的時間步貼近前一個區塊已執行的部分，通常會搭配一個柔性的過渡遮罩。

## 快速開始[[quick-start]]

### 安裝[[installation]]

RTC 已內建在 LeRobot 中，只要安裝你需要的策略相依套件即可：

```bash
# 用於 Pi0 或 Pi0.5
pip install -e ".[pi]"

# 用於 SmolVLA
pip install -e ".[smolvla]"
```

### 搭配 Pi0 使用 RTC[[using-rtc-with-pi0]]

在真實機器人上部署 RTC 時，可以使用 `lerobot-rollout --strategy.type=base --inference.type=rtc`。
以下程式碼片段是一個簡化的範例，說明 RTC 如何在你的管線中搭配 Pi0 運作：

```python
from lerobot.policies.pi0 import PI0Policy, PI0Config
from lerobot.configs import RTCAttentionSchedule
from lerobot.policies.rtc import RTCConfig, ActionQueue

# 載入啟用 RTC 的 Pi0
policy_cfg = PI0Config()

# 啟用 RTC
policy_cfg.rtc_config = RTCConfig(
    enabled=True,
    execution_horizon=10,  # 要與前一個區塊混合的步數
    max_guidance_weight=10.0,  # 強制一致性的強度
    prefix_attention_schedule=RTCAttentionSchedule.EXP,  # 指數混合
)

# 載入策略
policy = PI0Policy.from_pretrained("lerobot/pi0_base", policy_cfg=policy_cfg, device="cuda")

# 現在使用帶 RTC 參數的 predict_action_chunk
inference_delay = 4  # 推論延遲的步數，此值應根據策略的推論延遲計算

# 初始化動作佇列
action_queue = ActionQueue(policy_cfg.rtc_config)

# 以下列函式在另一個執行緒中啟動
def get_actions():
  while True:
    if should_get_actions:

      prev_actions = action_queue.get_left_over()
      obs = get_robot_observations(robot)

      # 使用 RTC 產生動作
      actions = policy.predict_action_chunk(
          obs,
          inference_delay=inference_delay,
          prev_chunk_left_over=prev_actions,
      )

      action_queue.merge(
          actions, actions, inference_delay
      )

for step in range(num_steps):
    action = action_queue.get()

    # 執行前 N 個動作
    execute_actions(action)
```

## 主要參數[[key-parameters]]

`RTCConfig` 有以下可以調整的參數：

**`mode`** 用來選擇動作前綴的條件化方式：

- `guided`（預設）在去雜訊過程中套用原始的 Jacobian 引導，可搭配一般的流匹配檢查點使用。
- `trained` 會以每個動作各自的 flow timestep，對前一個區塊的前綴進行硬性修補（hard inpainting）。目前需要以 `policy.rtc_training_max_delay > 0` 訓練的 Pi05 檢查點，而且不需要為引導執行反向傳播。

本機 rollout 與策略伺服器會套用相同的保守 trained 模式准入規則（admission rule）：`rtc_training_max_delay <= execution_horizon <= prediction_steps - rtc_training_max_delay`。
對 Pi05 而言，`prediction_steps` 是檢查點的 `chunk_size`。這保留了既有的本機限制：所設定的前綴會涵蓋最大訓練延遲，並在其之外留下至少相同數量的預測步驟。本機 rollout 在連接機器人之前，還要求 `inference.queue_threshold >= rtc_training_max_delay`；遠端請求的時序則使用自己的 refill 設定。

這裡的 `execution_horizon` 是提供的前綴容量，而非請求之間的播放量。Pi05 只會對 `inference_delay` 前綴進行硬性條件化。此准入規則不是延遲保證，也不代表較大的容量在執行時必然會失敗；實際測得的重疊、剩餘動作與新鮮度（freshness）檢查仍會決定回傳的區塊是否能執行。一般區塊與 guided RTC 不受這項僅適用於 trained 模式的規則影響。

**`execution_horizon`**：要與前一個區塊保持一致的時間步數。數值越高，過渡越順暢，但反應可能會變慢。

常見的值：8-12 步

```python
RTCConfig(execution_horizon=10)
```

**`max_guidance_weight`**：強制與前一個區塊保持一致的強度。這是一個可調整的超參數，用來在過渡的順暢度與策略的反應速度之間取得平衡。對於 10 步的流匹配（SmolVLA、Pi0、Pi0.5），10.0 是最佳值。

**`prefix_attention_schedule`**：如何在重疊區域內分配一致性的權重。

- `LINEAR`：從 inference_delay 到 execution_horizon 線性衰減
- `EXP`：指數衰減（建議入門時使用）
- `ONES`：在整個 execution_horizon 上都使用完整權重
- `ZEROS`：二元（到 inference_delay 為止使用完整權重，之後為零）

**`inference_delay`**：你的系統推論延遲有多少個時間步。這個值會傳給 `predict_action_chunk()`，而不是寫在設定中，因為它在執行時可能會變動。

## 離線測試 RTC[[testing-rtc-offline]]

在真實機器人上執行之前，先用資料集的樣本測試 RTC，將它的運作方式視覺化：

```bash
python examples/rtc/eval_dataset.py \
    --policy.path=lerobot/pi0_libero_finetuned \
    --dataset.repo_id=HuggingFaceVLA/libero \
    --rtc.execution_horizon=10 \
    --rtc.max_guidance_weight=10.0 \
    --device=cuda
```

在評估相容的訓練時 RTC Pi05 檢查點時，請加上 `--rtc.mode=trained`。
不支援的策略會拒絕 trained 模式，而不會退回
guided RTC。

    --strategy.type=base \
    --policy.path=${HF_USERNAME}/policy_repo_id \
    --inference.type=rtc \
    --inference.rtc.mode=guided \
    --inference.rtc.execution_horizon=10 \
    --inference.rtc.max_guidance_weight=10.0 \
    --robot.type=so100_follower \
    --robot.port=/dev/tty.usbmodem58FA0834591 \
    --robot.cameras="{ gripper: {type: opencv, index_or_path: 1, width: 640, height: 480, fps: 30}, front: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30}}" \
    --task="Move green small object into the purple platform" \
    --duration=120 \
    --device=cuda

延遲：

## RTC 與遠端推論的關係[[how-rtc-relates-to-remote-inference]]

`--inference.type=rtc` 是本機 RTC：推論會在 rollout 行程中的背景執行緒執行，且不使用任何傳輸。若要在同一台機器上以獨立行程執行策略伺服器與機器人客戶端，則需改用遠端後端。

兩種非同步後端在支援的機器人上，都採用相同的[有界等待與關閉行為](./remote_inference#what-the-robot-does-while-waiting-or-stopping)。關於其逾時預設值，請參閱[本機 RTC 預算](./inference#inference-backends)。等待並不會放寬 RTC 的前綴、延遲或新鮮度（freshness）檢查。

RTC 與[遠端推論（remote inference）](./remote_inference)都能改善即時機器人控制，但它們解決的是不同的問題。

| 面向     | 遠端推論                                 | RTC                                       |
| -------- | ---------------------------------------- | ----------------------------------------- |
| **目的** | 在另一個行程或另一台電腦上執行推論       | 以剩餘軌跡為條件進行預測                  |
| **執行** | 本機緩衝播放，可選的對齊與混合           | 為支援的策略提供 guided 或 trained 的延續 |
| **關係** | 可以提供一般區塊或 RTC                   | 可在本機執行，或透過遠端後端執行          |
| **限制** | 延遲、新鮮度與緩衝區覆蓋範圍仍會限制動作 | 需要策略所宣告的 RTC 契約（contract）     |

當檢查點支援協商出的 RTC 模式時，遠端推論就能使用 RTC。一般區塊也支援可選的播放位置對齊與混合；關於模式、相容性與調校，請參閱[遠端推論指南](./remote_inference)。

## 進階：除錯追蹤[[advanced-debug-tracking]]

RTC 內建除錯追蹤功能，協助你了解推論期間發生了什麼事：

```python
# 啟用除錯追蹤
policy_cfg.rtc_config.debug = True
policy_cfg.rtc_config.debug_maxlen = 100

# 推論後，存取除錯資料
debug_data = policy.rtc_processor.get_debug_data()

# 將去雜訊步驟、修正等視覺化
from lerobot.policies.rtc.debug_visualizer import RTCDebugVisualizer
visualizer = RTCDebugVisualizer()
# ... 建立圖表
```

離線 RTC 視覺化的完整範例，請參閱 `examples/rtc/eval_dataset.py`。
