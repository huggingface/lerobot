# 非同步推論[[asynchronous-inference]]

我們透過 [SmolVLA](https://huggingface.co/papers/2506.01844) 推出了一種在真實世界機器人上執行推論的新方式：**將動作預測（action prediction）與動作執行解耦**。
本教學將示範如何以微調過的 SmolVLA，以及 LeRobot 支援的所有策略（policy），使用非同步推論（_async inference_）。
**用 LeRobot 支援的所有策略試試非同步推論**吧！

**你將學到：**

1. 為什麼非同步推論很重要，以及它與較傳統的循序推論有何不同。
2. 如何在同一台機器上，甚至跨網路，啟動 `PolicyServer` 並連接 `RobotClient`。
3. 如何依你的機器人與策略，調校關鍵參數（`actions_per_chunk`、`chunk_size_threshold`）。

如果遇到困難，歡迎到我們的 [Discord 社群](https://discord.gg/s3KuuzsPFb)尋求協助！

簡單來說，使用 _非同步推論_ 時，策略伺服器（policy server）在計算下一個動作區塊（action chunk）的同時，機器人仍會持續動作，因此不會有「等待推論」造成的延遲，行為也會更流暢、反應更靈敏。
這與同步推論（sync）有根本上的不同：同步推論時，策略在計算下一個動作區塊期間，機器人只能閒置等待。

## 開始使用非同步推論[[getting-started-with-async-inference]]

關於非同步推論的更多資訊，請參閱我們的[部落格文章](https://huggingface.co/blog/async-robot-inference)。本指南的目的是協助你在自己的環境中快速設定並執行非同步推論。

首先，以 `async` 額外套件安裝 `lerobot`，以取得執行非同步推論所需的相依套件。

```shell
pip install -e ".[async]"
```

接著啟動策略伺服器（在一個終端機中，或在另一台機器上），並指定讓用戶端（client）連線的主機位址與連接埠。
執行以下指令即可啟動策略伺服器：

```shell
python -m lerobot.async_inference.policy_server \
     --host=127.0.0.1 \
     --port=8080
```

這會啟動一個在 `127.0.0.1:8080`（`localhost`，連接埠 8080）監聽的策略伺服器。此時策略伺服器還是空的，因為要執行哪個策略、使用哪些參數，都是在與用戶端第一次交握（handshake）時才指定的。以下列指令啟動用戶端：

```shell
python -m lerobot.async_inference.robot_client \
    --server_address=127.0.0.1:8080 \ # SERVER: 策略伺服器的主機位址與連接埠
    --robot.type=so100_follower \ # ROBOT: 你的機器人類型
    --robot.port=/dev/tty.usbmodem585A0076841 \ # ROBOT: 你的機器人連接埠
    --robot.id=follower_so100 \ # ROBOT: 你的機器人 id，用於載入校正檔
    --robot.cameras="{ laptop: {type: opencv, index_or_path: 0, width: 1920, height: 1080, fps: 30}, phone: {type: opencv, index_or_path: 0, width: 1920, height: 1080, fps: 30}}" \ # POLICY: 用於取得影格的相機，其鍵需符合策略預期的鍵
    --task="dummy" \ # POLICY: 要讓策略執行的任務（`Fold my t-shirt`）。並非所有策略都需要定義，例如 `act`
    --policy_type=your_policy_type \ # POLICY: 要執行的策略類型（smolvla、act 等）
    --pretrained_name_or_path=user/model \ # POLICY: 伺服器上要執行之檢查點的模型名稱/路徑（例如 lerobot/smolvla_base）
    --policy_device=mps \ # POLICY: 伺服器上執行策略所用的裝置（cuda、mps、xpu、cpu）
    --actions_per_chunk=50 \ # POLICY: 一次輸出的動作數量
    --chunk_size_threshold=0.5 \ # CLIENT: 在傳送新觀測至伺服器前的區塊大小閾值
    --aggregate_fn_name=weighted_average \ # CLIENT: 在重疊部分彙整動作的函式
    --debug_visualize_queue_size=True # CLIENT: 是否在執行期視覺化佇列大小
```

總結來說，你需要指定以下各項的設定：

- `SERVER`：策略伺服器的位址與連接埠
- `ROBOT`：要連接的機器人類型、連接埠，以及機器人在本機的 `id`
- `POLICY`：要執行的策略類型，以及伺服器上要執行的檢查點（checkpoint）的模型名稱／路徑。你也需要指定伺服器要使用哪個裝置，以及一次輸出多少個動作（上限為該策略的最大動作數）。
- `CLIENT`：傳送新的觀測（observation）給伺服器之前的區塊大小閾值，以及在重疊部分彙整動作的函式。你也可以選擇在執行時將佇列大小視覺化，協助你調校 `CLIENT` 的參數。

要特別注意的是：

- `actions_per_chunk` 與 `chunk_size_threshold` 是需要依你的設定調校的關鍵參數。
- `aggregate_fn_name` 是在重疊部分彙整動作的函式。你可以將新的函式加入函式登錄表，或在 `robot_client.py` 中加入自己的函式（請見[這裡](https://github.com/huggingface/lerobot/blob/main/src/lerobot/async_inference/robot_client.py#L224)）
- `debug_visualize_queue_size` 是調校 `CLIENT` 參數的實用工具。

## 非同步推論與同步推論[[async-vs-synchronous-inference]]

同步推論是讓動作區塊的預測與動作的執行交替進行，這本質上就會產生*閒置影格*，也就是機器人閒置等待策略輸出新動作區塊的那些影格。
因此，推論會出現明顯的即時延遲，機器人會因為沒有可用的動作而直接停下來。
隨著機器人模型的規模越來越大，這個問題可能只會更嚴重。

  <img

    width="80%"
  ></img>
</p>
<p align="center">
  <i>同步推論</i>會讓機器人在策略計算下一個 動作區塊時閒置。
</p>

為了解決這個問題，我們設計了非同步推論，這種做法將動作的規劃與執行解耦，帶來 (1) 更高的適應性，以及最重要的 (2) 沒有閒置影格。
關鍵在於，使用非同步推論時，下一個動作區塊會在目前的區塊用完*之前*就計算好，因此不會閒置。
藉由在重疊部分彙整不同的動作區塊，可以取得最新的規劃與更緊密的控制迴圈，這就是更高適應性的來源。

## 啟動策略伺服器[[start-the-policy-server]]

策略伺服器是 `PreTrainedPolicy` 的包裝器，負責將它與來自機器人用戶端的觀測連接起來。
策略伺服器初始化時是空的容器，會在機器人用戶端與策略伺服器初次交握時，載入用戶端所指定的策略。
因此，啟動策略伺服器只需要指定主機位址與連接埠。如果策略伺服器與機器人用戶端在同一台機器上執行，可以使用 `localhost` 作為主機位址。

<hfoptions id="start_policy_server">
<hfoption id="Command">
```bash
python -m lerobot.async_inference.policy_server \
     --host=127.0.0.1 \
     --port=8080
```
</hfoption>
<hfoption id="API example">

<!-- prettier-ignore-start -->
```python
from lerobot.async_inference.configs import PolicyServerConfig
from lerobot.async_inference.policy_server import serve

config = PolicyServerConfig(
    host="localhost",
    port=8080,
)
serve(config)
```
<!-- prettier-ignore-end -->

</hfoption>
</hfoptions>

這會在 `localhost:8080` 上監聽來自對應 `RobotClient` 的連線；`RobotClient` 會在用戶端與伺服器第一次交握時，告知要執行哪個策略。

## 啟動機器人用戶端[[launch-the-robot-client]]

`RobotClient` 是 `Robot` 實例的包裝器，負責將它連接到（可能位於遠端的）`PolicyServer`。
`RobotClient` 會將觀測串流傳送給 `PolicyServer`，並接收在伺服器上執行推論所得到的動作區塊（我們假設伺服器的運算資源比機器人控制器更好）。

<hfoptions id="start_robot_client">
<hfoption id="Command">
```bash
python -m lerobot.async_inference.robot_client \
    --server_address=127.0.0.1:8080 \ # SERVER: 策略伺服器的主機位址與連接埠
    --robot.type=so100_follower \ # ROBOT: 你的機器人類型
    --robot.port=/dev/tty.usbmodem585A0076841 \ # ROBOT: 你的機器人連接埠
    --robot.id=follower_so100 \ # ROBOT: 你的機器人 id，用於載入校正檔
    --robot.cameras="{ laptop: {type: opencv, index_or_path: 0, width: 1920, height: 1080, fps: 30}, phone: {type: opencv, index_or_path: 0, width: 1920, height: 1080, fps: 30}}" \ # POLICY: 用於取得影格的相機，其鍵需符合策略預期的鍵
    --task="dummy" \ # POLICY: 要讓策略執行的任務（`Fold my t-shirt`）。並非所有策略都需要定義，例如 `act`
    --policy_type=your_policy_type \ # POLICY: 要執行的策略類型（smolvla、act 等）
    --pretrained_name_or_path=user/model \ # POLICY: 伺服器上要執行之檢查點的模型名稱/路徑（例如 lerobot/smolvla_base）
    --policy_device=mps \ # POLICY: 伺服器上執行策略所用的裝置
    --actions_per_chunk=50 \ # POLICY: 一次輸出的動作數量
    --chunk_size_threshold=0.5 \ # CLIENT: 在傳送新觀測至伺服器前的區塊大小閾值
    --aggregate_fn_name=weighted_average \ # CLIENT: 在重疊部分彙整動作的函式
    --debug_visualize_queue_size=True # CLIENT: 是否在執行期視覺化佇列大小
```
</hfoption>
<hfoption id="API example">

<!-- prettier-ignore-start -->
```python
import threading
from lerobot.robots.so_follower import SO100FollowerConfig
from lerobot.cameras.opencv import OpenCVCameraConfig
from lerobot.async_inference.configs import RobotClientConfig
from lerobot.async_inference.robot_client import RobotClient
from lerobot.async_inference.helpers import visualize_action_queue_size

# 1. 建立機器人實例
"""執行 `python lerobot/find_cameras.py` 以查看你的設定中可用的相機"""
# 這些相機必須與策略預期的相符
# 請查看你所使用策略在 Hub 上的 config.json
camera_cfg = {
    "top": OpenCVCameraConfig(index_or_path=0, width=640, height=480, fps=30),
    "side": OpenCVCameraConfig(index_or_path=1, width=640, height=480, fps=30)
}

robot_cfg = SO100FollowerConfig(
  port="/dev/tty.usbmodem585A0076841",
  id="follower_so100",
  cameras=camera_cfg
)

# 3. 建立用戶端設定
client_cfg = RobotClientConfig(
    robot=robot_cfg,
    server_address="localhost:8080",
    policy_device="mps",
    client_device="cpu",
    policy_type="smolvla",
    pretrained_name_or_path="<user>/smolvla_async",
    chunk_size_threshold=0.5,
    actions_per_chunk=50,  # 確保這小於策略的最大動作數
)

# 4. 建立並啟動用戶端
client = RobotClient(client_cfg)

# 5. 指定任務
task = "Don't do anything, stay still"

if client.start():
    # 啟動動作接收器執行緒
    action_receiver_thread = threading.Thread(target=client.receive_actions, daemon=True)
    action_receiver_thread.start()

    try:
        # 執行控制迴圈
        client.control_loop(task)
    except KeyboardInterrupt:
        client.stop()
        action_receiver_thread.join()
        # （可選）繪製動作佇列大小
        visualize_action_queue_size(client.action_queue_size)
```

<Tip>
  `actions_per_chunk` 與 `chunk_size_threshold` 的值不同，
  確實會導致不同的行為。
</Tip>

一方面，提高 `actions_per_chunk` 的值可以降低沒有動作可執行的機率，因為在計算新的區塊時，手上會有更多動作可用。
不過，`actions_per_chunk` 的值較大時，也可能讓動作較不精確，因為預測的時間跨度越長，誤差就會不斷累積。

另一方面，提高 `chunk_size_threshold` 的值，會讓用戶端更頻繁地將觀測送往 `PolicyServer` 推論，產生更多次更新的動作區塊，而且彼此有很大部分重疊。這會帶來很高的適應性，極端情況下會為每個觀測預測一個動作區塊，而每個區塊在新的區塊產生之前只會用掉一小部分。
這個選項也會因為請求次數多，而對推論管線造成更大的負擔。反之，`chunk_size_threshold` 的值接近 0.0 時，就會退化成同步推論的極端情況，也就是只有在目前的區塊用完時，才會送出新的觀測。

我們在 [SmolVLA 論文](https://huggingface.co/papers/2506.01844)的實驗中發現，`actions_per_chunk` 與 `chunk_size_threshold` 的預設值效果不錯，但仍建議你嘗試不同的值，找出最適合你的設定。

### 依你的設定調校非同步推論[[tuning-async-inference-for-your-setup]]

1. **謹慎選擇運算資源。** [PI0](https://huggingface.co/lerobot/pi0) 推論時會占用 14GB 記憶體，而 [SmolVLA](https://huggingface.co/lerobot/smolvla_base) 只需要約 2GB。請記得較小的策略需要的運算資源較少，並依你的使用情境找出最合適的運算資源。策略與裝置的組合（以 CPU 為主、使用 MPS，或特定 NVIDIA GPU 的 CUDA 核心數）會直接影響你可預期的平均推論延遲。
2. **依推論延遲調整 `fps`。** 伺服器產生新的動作區塊時，用戶端並沒有閒著，而是持續執行目前佇列中的動作。如果兩者的速度相差太多，用戶端的佇列可能會被清空。因此，如果佇列中經常沒有動作可用，請調低 fps。
3. **調整 `chunk_size_threshold`**。
   - 接近 `0.0` 的值會讓行為幾乎變成循序執行；接近 `1.0` 的值 → 每一步都送出觀測（需要更多頻寬，也更依賴良好的世界模型）。
   - 我們發現 0.5-0.6 左右的值效果不錯。如果你想微調這個值，可以在啟動 `RobotClient` 時將 `--debug_visualize_queue_size` 設為 `True`。這會在執行時繪製動作佇列大小的變化，你可以用它找出最適合你設定的 `chunk_size_threshold` 值。

## 結論[[conclusion]]

非同步推論是即時機器人控制的一大進展，解決了長期困擾機器人應用的推論延遲問題。透過本教學，你已經學會如何實作完整的非同步推論管線，消除閒置影格，讓機器人的行為更流暢、反應更靈敏。

**重點整理：**

- **典範轉移**：非同步推論將動作預測與執行解耦，讓機器人在新的動作區塊平行計算時，仍能持續動作
- **效能優勢**：消除同步做法本來就有的「等待推論」延遲，而策略模型越大，這一點就越重要
- **彈性的架構**：伺服器與用戶端的設計可以進行分散式運算，讓推論在遠端的強大硬體上執行，同時維持即時的機器人控制
- **可調校的參數**：成效取決於能否依你的硬體、策略與任務需求，適當設定 `actions_per_chunk` 與 `chunk_size_threshold`
- **廣泛的相容性**：適用於所有 LeRobot 支援的策略，從輕量的 ACT 模型到 SmolVLA 這類視覺語言模型

先從預設參數開始實驗，觀察動作佇列的大小，再逐步調整你的設定，在你的使用情境下達到最佳效能。
