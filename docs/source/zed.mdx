# Stereolabs ZED Cameras

Stereolabs stereo ZED cameras (ZED X, ZED X Mini, ZED X HDR, ZED 2i, ZED Mini, ...) are supported through the `ZedCamera` class, which talks to the hardware via the ZED SDK. On top of the standard camera API described in [Cameras](./cameras), it gives you metric depth (`uint16` millimetres), the camera's hardware image timestamp (`latest_hw_timestamp_ns`) for multi-camera and robot-state alignment.

The monocular **ZED X One** is driven by a different SDK API and so has its own class, `ZedOneCamera` (camera type `zed_one`) — same interface without depth, see [Monocular ZED X One](#monocular-zed-x-one).

## Install the ZED SDK

The Python API ships with the SDK, it is **not** on PyPI. Install the ZED SDK 5.4 or newer, then generate `pyzed` into the same environment as LeRobot:

```bash
python /usr/local/zed/get_python_api.py        # provides `pyzed.sl`
```

On Jetson, the `NEURAL` depth modes also need the ZED AI and TensorRT libraries on the library path:

```bash
export LD_LIBRARY_PATH=/usr/local/cuda-12/targets/aarch64-linux/lib:$LD_LIBRARY_PATH
```

> [!WARNING]
> `pyzed` 5.4 requires `numpy>=2`. If the OpenCV in your environment is a numpy-1 build, the import will clash — install matching wheels in the same virtual environment.

## Choose a resolution

`resolution` is what drives width, height and frame rate. Leave it at `"AUTO"` unless you have a reason not to: `AUTO` opens each model in its native mode, and the supported mode list differs per model.

| Camera family               | Notes                                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------ |
| USB (ZED, ZED 2i, ZED Mini) | `HD2K`, `HD1080`, `HD720`, `VGA`                                                                       |
| GMSL (ZED X, ZED X Mini)    | `HD1200`, `HD1080`, `SVGA` — **`HD720` is rejected**                                                   |
| ZED X HDR family            | **Only open at their native `1920x1536`** — `HD1080`, `HD1200` and `SVGA` are all rejected, use `AUTO` |

> [!TIP]
> Standalone, leave `fps`, `width` and `height` unset and let the camera report its own mode. Set either all three or none of them — a lone `fps` raises a `ValueError`.

> [!WARNING]
> Inside a **robot** config you must set `width`, `height` and `fps` explicitly (for example `width: 1920, height: 1200, fps: 30`), because robots publish their observation features before the cameras connect, so the shape cannot be filled in at connect time. The values must match the mode the camera actually opens, otherwise `connect()` raises rather than silently capturing at a different resolution.

## Configuration reference

`ZedCameraConfig` accepts the following fields:

| Field                      | Default    | Notes                                                                                                                                                                    |
| -------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `serial_number`            | `None`     | `None` opens the first ZED found                                                                                                                                         |
| `resolution`               | `"AUTO"`   | `AUTO` picks the model's native mode. `HD2K` / `HD1080` / `HD1200` / `SVGA` / `HD720` / `VGA` — see the per-model traps above                                            |
| `rectified`                | `True`     | `True` returns the rectified image (lens distortion removed); `False` returns the raw sensor image. `intrinsics` follows the choice. Cannot be combined with `use_depth` |
| `depth_mode`               | `"NEURAL"` | `NEURAL` / `NEURAL_PLUS` / `NEURAL_LIGHT` / `NONE` (the SDK still accepts `PERFORMANCE`, `QUALITY` and `ULTRA` but deprecates them)                                      |
| `use_rgb`                  | `True`     | Left color stream                                                                                                                                                        |
| `use_depth`                | `False`    | Depth as `(H, W, 1)` `uint16` millimetres, the unit LeRobot's depth path expects                                                                                         |
| `color_mode`               | `RGB`      | `RGB` or `BGR`                                                                                                                                                           |
| `rotation`                 | `0`        | `0` / `90` / `180` / `-90` (`Cv2Rotation`; `270` is not accepted)                                                                                                        |
| `warmup_s`                 | `1`        | Seconds of warmup grabbing before `connect()` returns                                                                                                                    |
| `fps` / `width` / `height` | `None`     | Inherited fields — set all three or none; with `resolution` set, prefer leaving all three unset                                                                          |

## Rectified or raw images

By default the backend returns the **rectified** left image: the SDK has removed lens distortion, so
straight lines in the world are straight in the image. Set `rectified: false` to receive the **raw**
sensor image instead, which is what you want when you intend to do your own undistortion, calibrate
against the raw optics, or feed a model trained on unrectified data.

```python
config = ZedCameraConfig(serial_number=12345678, rectified=False)  # replace with your camera's serial
```

`intrinsics` follows the choice: rectified output reports the rectified calibration, raw output
reports the raw one. On a ZED 2i the two differ substantially (measured `fx` 732.6 rectified versus
531.9 raw), so do not mix one with the other.

> [!WARNING]
> `rectified: false` cannot be combined with `use_depth: true` — the SDK computes depth from the
> rectified stereo pair, so a depth map would not align with the raw image. The config raises.

## Depth

With `use_depth: true`, `read_depth()` and `read_latest_depth()` return metric depth as `(H, W, 1)` `uint16` millimetres, and depth-aware robots record it into the dataset as a sibling feature (`observation.images.front_depth` next to `observation.images.front`). LeRobot stores it as a 12-bit video stream that decodes back to millimetres.

Two encoder defaults are worth knowing about, since they come from LeRobot's [depth encoder](./video_encoding_parameters#depth-streams) rather than from the ZED backend:

- The quantization range is `depth_min` 0.01 m to `depth_max` 10 m. A ZED sees much farther than that and everything beyond saturates, so raise `depth_max` through the dataset's `depth_encoder` settings if your scene is deeper. Precision is log-distributed, so it is finest close up.
- Invalid pixels (0 mm) come back as `depth_min`, not 0. The ZED marks unmatched pixels as 0 before encoding, so treat values sitting at the floor as "no return" rather than "1 cm away".

> [!WARNING]
> A script that builds its dataset features by hand must tag the depth stream with `"info": {"is_depth_map": True}`. Without that flag a single-channel stream is encoded as ordinary 8-bit video and the metric values are lost.

The backend exposes the **left** color view only, because LeRobot models one image stream per camera key rather than a stereo pair.

`read()` and `read_depth()` each wait for the _next_ grab, so calling them back to back returns two different captures. For a colour/depth pair from the same grab, use the `read_latest*` methods:

```python
from lerobot.cameras.zed import ZedCamera, ZedCameraConfig

config = ZedCameraConfig(serial_number=12345678, use_depth=True)  # replace with your camera's serial
with ZedCamera(config) as camera:
    rgb = camera.read_latest()
    depth = camera.read_latest_depth()  # same grab as `rgb`
```

## Monocular ZED X One

The ZED X One is a single-sensor camera, so the SDK drives it through a different API
(`sl.CameraOne`). It gets its own backend class and camera type:

```python
from lerobot.cameras.zed import ZedOneCamera, ZedOneCameraConfig

cam = ZedOneCamera(ZedOneCameraConfig(serial_number=12345678))  # replace with your camera's serial
cam.connect()
rgb = cam.read()  # (H, W, 3) uint8 — 1920x1200 native on the X One GS
cam.disconnect()
```

In a robot config, use `type: zed_one` (and remember the explicit width/height/fps rule):

```bash
--robot.cameras='{ side: {type: zed_one, serial_number: 12345678, width: 1920, height: 1200, fps: 30} }'
```

Everything from the stereo backend carries over — the background capture thread, `read()` /
`async_read()` / `read_latest()`, `rectified`, rotation, colour mode and the hardware timestamp — with
one exception:

> [!WARNING]
> A single sensor cannot triangulate, so there is **no depth**: `ZedOneCameraConfig` has no
> `use_depth` / `depth_mode`, and `read_depth()`, `async_read_depth()` and `read_latest_depth()`
> raise `NotImplementedError`.

`lerobot-find-cameras zed` lists monocular and stereo cameras together, each under its own `type`
(`zed` or `zed_one`). The SDK keeps the two device lists separate, so a stereo camera never shows up
as a monocular entry, and both kinds can capture concurrently in the same rig.

## Grab warnings

The SDK reports negative `ERROR_CODE`s from `grab()` as warnings. The backend logs each one once per streak (`ZedCamera(...) grab() warning: ...`) and keeps the frame, except for `CORRUPTED_FRAME` (green/purple image flagged by the SDK's validity check) and `CAMERA_REBOOTING`, which carry no usable image and are dropped: `read()` waits for the next good frame and `read_latest()` ages out. Repeated `CORRUPTED_FRAME` warnings point at cabling or driver problems, not at the backend. The SDK's own console output is silenced unless the `lerobot.cameras.zed` logger is at `DEBUG`.

## Embedded hosts (Jetson)

Guidance learned while recording with two cameras on a Jetson Orin NX:

- Keep `--display_data` **off** while recording. Live visualization on the iGPU starves the capture pipeline and produces choppy video; stream to another machine with `--display_mode=foxglove` instead.
- Two cameras at `1920x1200` push the record loop close to its budget. `SVGA` (960x600) leaves comfortable headroom and is ample for wrist views.
- Post-episode video encoding saturates the CPU. If your robot streams telemetry over the network, set `--dataset.video_encoding_batch_size` greater than 1 so encoding happens once at the end of the session instead of between episodes.

> [!WARNING]
> Reading datasets back on a Jetson may fail in `torchcodec` with `libtorchcodec_core*.so: could not load`. This is unrelated to the ZED backend: the aarch64 `torchcodec` wheel requires `torch>=2.11`, and PyPI's aarch64 torch is built against CUDA 13 while JetPack 6 ships CUDA 12.x, so the `libnvrtc.so.13` dependency is missing. Recording is unaffected — pass `video_backend="pyav"` when reading, or install NVIDIA's JetPack-specific torch build.
