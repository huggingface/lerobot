# Bimanual YAM

`bi_yam_follower` supports two standard YAM v1 arms with linear DM4310 grippers. All CAN communication uses LeRobot's `DamiaoMotorsBus`. The adapter does not require an I2RT controller or Portal server. MuJoCo computes gravity compensation from the bundled inertial model; its source attribution and MIT notice are embedded in the XML.

## Installation and CAN interfaces

```bash
uv sync --locked --extra yam
```

Each arm needs a separate classic SocketCAN channel at **1 Mbit/s**. Both arms reuse motor IDs 1–7 and feedback IDs 17–23: motors 1–3 are DM4340, and 4–7 are DM4310. Do not select CAN FD or attach both arms to the same channel.

Bring up the verified interfaces, substituting the names on your computer:

```bash
sudo ip link set can0 type can bitrate 1000000
sudo ip link set can0 up
sudo ip link set can1 type can bitrate 1000000
sudo ip link set can1 up
```

Confirm which channel belongs to each physical arm. The optional `expected_adapter_serial` field binds each arm to its USB adapter and rejects swapped Linux interface assignments. Camera names and ports are installation-specific; do not infer them from enumeration order.

## Gripper calibration

Support both arms, then use the standard calibration command with a unique robot ID:

```bash
lerobot-calibrate \
  --robot.type=bi_yam_follower \
  --robot.id=my_yam \
  --robot.left_arm.port=can0 \
  --robot.right_arm.port=can1
```

The command prompts for both grippers fully closed, then fully open. Move them gently **by hand**, release them before confirming each measurement, and stop if a mechanism resists. Calibration only requests feedback: it does not enable torque, open cameras, reset encoders, or write motor settings. Both endpoints must be stable and each stroke plausible before a new file replaces the previous calibration.

Measurements are saved in the standard robot calibration directory under the robot ID. The two gripper records store the native 16-bit MIT position counts and opening polarity. Rollout automatically loads these records when given the same `robot.id` and calibration directory. Explicit `gripper_closed_rad` / `gripper_open_rad` configuration values override saved measurements.

Policy grippers are continuous **0 = closed, 1 = open**, independently mapped for either motor polarity:

```text
policy_gripper = (motor_rad - closed_rad) / (open_rad - closed_rad)
```

Do not interpret gripper actions as percentages, binary flags, motor radians, or finger separation in meters. Recalibrate after changing a gripper or its encoder frame. Missing calibration prevents normal connection and instructs the operator to run `lerobot-calibrate`.

## Observations and actions

The exact 14-value order is:

```text
left_joint_0.pos ... left_joint_5.pos, left_gripper.pos,
right_joint_0.pos ... right_joint_5.pos, right_gripper.pos
```

Joints are **absolute radians** in the factory encoder frame. Conversion to the bus's internal degrees happens at the robot boundary. Factory joint zeros are retained; only use `joint_signs` / `joint_offsets_rad` for an explicitly verified frame conversion. End-effector actions require a separate IK pipeline. The rollout compatibility check rejects an incompatible MolmoAct2 control mode, state/action ordering, or camera configuration before connecting.

Configure cameras using ordinary LeRobot camera configs, preferably persistent `/dev/v4l/by-path/...` paths. Select RGB nodes, confirm physical camera roles, and check all streams simultaneously. For MolmoAct2 BimanualYAM, the roles are `top`, `left`, and `right`; use the checkpoint's saved processors and normalization statistics. Policy preparation and inference are covered by the [MolmoAct2 guide](molmoact2).

For continuous MolmoAct2 inference, synchronous chunk generation can delay policy updates even while the independent arm servos keep running. The existing RTC backend performs inference in a background thread and conditions new chunks on queued actions. The following rollout options sustained approximately 30 action updates per second in a read-only RTX 5090 test with three live cameras:

```bash
--inference.type=rtc \
--inference.rtc.mode=guided \
--inference.rtc.execution_horizon=20 \
--inference.queue_threshold=20 \
--fps=30
```

These are options to add to a complete `lerobot-rollout` command. Measure action availability as well as loop cadence on your installation; this timing test does not validate physical task performance. Keep the checkpoint's action representation and saved normalization. Lowering `fps` changes how quickly its action sequence is played and is not a substitute for resolving inference delays.

## Startup and control

The adapter defaults to `read_only=true`. Explicitly set `robot.read_only=false` to enable control after validating the installation. At startup, cameras must deliver frames and both arms must pass feedback, calibration, and pose checks before either is enabled. A camera first-frame timeout is retried once using a fresh connection, before opening either motor bus. A second timeout aborts startup; camera failures during control are not automatically retried. Each joint must be within `initial_tolerance_rad` (default 0.2 radians) of `initial_position_rad` (default six zeros). Grippers may start anywhere within their calibrated stroke by default. Optionally set each arm's `initial_gripper_position=1.0` to require open grippers. These are assertions, not automatic homing commands.

To start from the current joint pose, set both
`--robot.left_arm.initial_position_rad=null` and
`--robot.right_arm.initial_position_rad=null`. This disables only the fixed
startup-pose assertion. Fresh feedback, calibrated gripper range and joint limits
are still checked. With deferred activation, `/start` seeds control from the
current measured pose without a move toward zero. The rollout home target remains
the pose captured at connection, including gripper openings. An arbitrary valid
start is not necessarily a pose the policy performs well from; keep the physical
starting layout consistent for comparisons.

A separate servo loop per arm (default 200 Hz) supplies gravity compensation and bounded targets. Defaults are 0.3 rad/s joint target speed, 0.5 gripper strokes/s, and a 0.15 rad tracking-error bound. The gripper's proportional torque contribution is limited to 0.5 Nm; damping adds torque, so this is not a contact-force guarantee. `send_action` returns the accepted target; observations contain measured positions.

The gripper speed setting limits target motion, not achieved speed. With zero commanded motor velocity, its damping opposes motion: at the default `gripper_kd=0.5`, the 0.5 Nm proportional cap balances damping at roughly 1 motor rad/s, before friction or load. Increasing target speed alone does not remove that bottleneck. A lower `gripper_kd`, such as 0.1, reduces this damping without increasing the proportional torque cap, but also changes braking and settling behavior. Validate it on the installation before relying on faster motion.

After one second without a fresh policy target, each servo holds fresh measured position instead of progressing toward an old target. Missing, malformed, or faulted motor feedback stops both workers. Disconnect disables torque. Keep the arms supported and the hardware e-stop accessible; communication or power failure can prevent software stopping from working.

This is an experimental adapter. Gravity compensation uses the standard arm/gripper inertias and excludes added camera/payload mass. There is no collision avoidance. Validate control, loading, stopping behavior, and task performance on the installation before normal use. For initial rollout testing, set `return_to_initial_position=false` to avoid an unvalidated automatic return motion.

## Interactive rollout and return to startup pose

Add `--interactive=true --return_to_initial_position=true` to keep the policy and hardware connected between attempts and return before normal shutdown. The captured startup pose, including grippers, is the return target; this does not perform encoder homing. By default, motors hold their measured pose after connection, even before policy actions begin with `/start`.

To keep YAM torque disabled during the initial interactive wait, also set `--robot.defer_torque_enable=true`. Support the arms in their starting pose: this mode reads feedback but provides no powered hold or gravity compensation until `/start`. Both starting poses are rechecked on `/start`; each bus worker seeds its controller from fresh measured positions before enabling torque. `/reset` and `/stop` before the first `/start` do not command a return. After activation, `/reset` returns home and leaves holding torque on for the next run.

Gravity compensation is independent of the policy. Each arm's `gravity_factors` scales the modeled torque per joint. For example, `[0.9,0.99,0.99,1.08,0.9,0.9]` applies 90% of the default compensation profile `[1.0,1.1,1.1,1.2,1.0,1.0]`; position gains and gripper torque limits are separate settings. Reduced compensation does not guarantee a motionless arm and must be checked on the physical installation.

- `/start`: run the current instruction. `--duration` limits each run, not the session.
- `/subtask <text>`: change the instruction; with RTC it takes effect through the next generated chunk.
- `/reset`: stop policy execution, return to the startup pose, restore the original task, and wait for another `/start`.
- `/stop`: return to the startup pose, then disconnect and disable torque.
- `/help`: list available commands.

YAM returns directly through its rate-limited servo targets using motor feedback, independently of camera availability. It refreshes the return target until both arms remain within 0.03 radians and both grippers within 0.05 of their targets for 0.2 seconds. Settling allows up to `robot.return_timeout_s` (default 30 seconds); use `--robot.return_timeout_s=120` to allow up to two minutes. It finishes early when measured arrival is confirmed, and feedback faults still stop it immediately. A timeout or feedback fault reports failure instead of claiming a completed return; normal shutdown still disconnects. Clear the return path before resetting or stopping: the return is joint-space motion without obstacle avoidance, and returning the grippers to their startup opening can release a held object.

## Communication faults

Feedback errors include the CAN interface and motor name. A motor reporting `0xD` has latched a communication-loss fault. Stop rollout, support the arms, and address the transport/control interruption before resetting motor power. The adapter never automatically clears a motor fault or resumes policy execution. Saved gripper calibration is retained across power cycles.

The bus collects queued replies even if Python was briefly descheduled past the receive timeout. This does not permit cached feedback: strict reads still reject missing, malformed, or faulted replies, and a servo read exceeding `feedback_timeout_s` stops control before another command is sent. Keep the motor firmware communication watchdog enabled.

Large cyclic garbage-collection scans can also pause all Python servo threads beyond the feedback deadline. Before opening hardware, YAM collects unused objects and freezes the preloaded heap out of later cyclic scans; collection of newly allocated objects remains enabled. The freeze is process-wide, shared across connected YAM instances, and undone after the last disconnect if YAM created the freeze. An existing caller-owned freeze is extended to include the loaded model and left frozen after disconnect; those cycles remain retained until the owner unfreezes them or the process exits. Disabled collection is left unchanged. This reduces a measured source of scheduling pauses without extending the feedback deadline; it does not make Python a hard real-time controller. Stale-feedback errors report the affected interfaces and snapshot ages.

To attempt home after a transient freshness timeout, opt in with
`--robot.recover_on_feedback_timeout=true` and enable rollout returns. Once policy
control has stopped, YAM joins both servo workers and requires 0.5 seconds of fresh,
valid feedback from all 14 motors with torque disabled. Each worker then seeds its
command from a new measured pose before enabling the bounded return. Recovery is
attempted only if control was previously activated; it cannot activate a session
waiting for its first `/start`. Missing packets, motor faults, invalid positions,
or failure to stop/disable a worker prohibit reactivation. A second feedback fault
during the return aborts it; persistent communication failures cannot guarantee
home. This option does not widen the feedback deadline or automatically restart
the policy. The hardware watchdog remains enabled.
