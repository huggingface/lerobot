# Adding a Benchmark

A benchmark is a simulator that LeRobot drives in one place, the shared env core, so that every way of using it behaves the same: `lerobot-eval` (a batched env, `--env.type=<benchmark>`), rollout and recording (a sim robot, `--robot.type=sim --robot.env.type=<benchmark>`), in-process or served by `lerobot-env-server` from its own Docker image. See [Simulation: in-process or served](./simulator_server) for how it is used.

## What to add

| Component            | Location                                      | What to add                                                                                                       |
| -------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Native environments  | `src/lerobot/sims/native/<benchmark>.py`      | The `gym.Env` and a `create_<benchmark>_envs` factory: reset/step, rendering, episode limits, task descriptions   |
| Canonical adapter    | `src/lerobot/sims/adapters.py`                | Only if needed: native observations to canonical keys, HWC uint8 RGB and float32 state                            |
| Conventions          | `src/lerobot/sims/conventions.py`             | Control rate, controller (`position`, `delta`, `eef_pose`), ordered state/action names, gripper and held channels |
| Config               | `src/lerobot/envs/configs.py`                 | An `EnvConfig` subclass whose `sim_settings()` maps its options to the factory's kwargs                           |
| Server configuration | `docker/sims/configs/<benchmark>.yaml`        | The task and factory kwargs the server and CI use                                                                 |
| Simulator image      | `docker/Dockerfile.sim`                       | A `<benchmark>_native` stage: pinned native dependencies and asset revisions; the final stage adds the server     |
| CI manifest          | `benchmarks/benchmarks.yaml`                  | Name, tasks, checkpoint revision and camera `rename_map`; policy, image, config and extras default from the name  |
| Dependencies         | `pyproject.toml`                              | An optional-dependency group for in-process use                                                                   |
| Documentation        | `docs/source/<benchmark>.mdx`, `_toctree.yml` | A user-facing page                                                                                                |

Data flows the same way in-process and served:

```text
native simulator → canonical NumPy observations → session (in-process client or env server)
  → batched env or sim robot → one-time image/tensor preparation → saved policy preprocessing
  → policy → saved action postprocessing → session → native simulator
```

Put image orientation, quaternion conversion and state ordering in the canonical adapter, and control conventions in `conventions.py`, so that evaluation and rollout agree. A new benchmark needs no [environment processor](./env_processor): observations reach the policy's own processors already canonical.

## What your environment must provide

### Environment structure

The factory returns a nested dict of per-world factories, wrapped by the `env_cls` it receives:

```python
def create_mybenchmark_envs(
    task: str,
    n_envs: int,
    gym_kwargs: dict | None = None,
    env_cls: Callable | None = None,
) -> dict[str, dict[int, Any]]:
    """{suite: {task_id: env_cls([make_world] * n_envs)}} for MyBenchmark."""
```

A single-task benchmark returns `{"<task>": {0: ...}}`; a multi-task one (like LIBERO) returns `{"libero_spatial": {0: ..., 1: ..., ...}, ...}`. The env core calls each `make_world` to build its worlds, in-process or on the server, and, with `--eval.use_async_envs=true`, in a process per world. See `create_libero_envs()` and `create_metaworld_envs()` for reference.

### The gym.Env

```python
class MyBenchmarkEnv(gym.Env):
    metadata = {"render_modes": ["rgb_array"], "render_fps": <fps>}

    def __init__(self, task_suite, task_id, ...):
        super().__init__()
        self.task = <task_name_string>
        self.task_description = <natural_language_instruction>
        self._max_episode_steps = <max_steps>
        self.observation_space = spaces.Dict({...})
        self.action_space = spaces.Box(low=..., high=..., shape=(...,), dtype=np.float32)
```

| Attribute            | Type  | Why                                                  |
| -------------------- | ----- | ---------------------------------------------------- |
| `_max_episode_steps` | `int` | Ends (truncates) an episode                          |
| `task_description`   | `str` | Passed to VLA policies as a language instruction     |
| `task`               | `str` | Fallback identifier if `task_description` is not set |

`step()` reports success in `info["is_success"]`. Actions are a one-dimensional continuous `Box`.

Observations are a dict the canonical adapter understands:

| Your env outputs          | Canonical key                   | What it is                          |
| ------------------------- | ------------------------------- | ----------------------------------- |
| `"pixels"` (single array) | `observation.image`             | Single camera image, HWC uint8      |
| `"pixels"` (dict)         | `observation.images.<cam>`      | Multiple cameras, each HWC uint8    |
| `"agent_pos"`             | `observation.state`             | Proprioceptive state vector         |
| `"environment_state"`     | `observation.environment_state` | Full environment state (e.g. PushT) |

Any other array is passed as `observation.<key>`. Rename your simulator's outputs to these keys inside the `gym.Env`, or add a case to the canonical adapter.

**GPU-based simulators (e.g. MuJoCo with EGL rendering):** if your simulator allocates GPU/EGL contexts during `__init__`, defer that allocation to a `_ensure_env()` helper called on first `reset()`/`step()`, so that a world built in a worker process does not inherit stale GPU handles. See `LiberoEnv._ensure_env()` for the pattern.

### Conventions (`src/lerobot/sims/conventions.py`)

Declare the simulator's control rate, controller and ordered component names in `CONVENTIONS`, keyed by the simulator type. They name the state and action components for robots, datasets and checkpoints, and define how a sim robot holds still. `semantics` defaults to `<type>-<control>-v1`. When they depend on the simulator's options (an action mode), declare a function of the kwargs, as for RoboTwin. `robot_type` names the simulated body, recorded by a sim robot: the type the real robot records when lerobot has a class for it (`so_follower`), else a short name (`panda`, `sawyer`); left out, datasets record `sim`.

### The config (`src/lerobot/envs/configs.py`)

Register a config so users can select your benchmark with `--env.type=<name>` (and `--robot.env.type=<name>`). Its `sim_settings()` describes the simulator as a server YAML's `sim` section; the env core does the rest:

```python
@EnvConfig.register_subclass("<benchmark_name>")
@dataclass
class MyBenchmarkEnvConfig(EnvConfig):
    task: str = "<default_task>"
    fps: int = <fps>
    obs_type: str = "pixels_agent_pos"

    @property
    def gym_kwargs(self) -> dict:
        return {"obs_type": self.obs_type}

    def sim_settings(self) -> dict:
        return {"type": "<benchmark_name>", "task": self.task, "kwargs": {"gym_kwargs": self.gym_kwargs}}
```

Keep its defaults and the server YAML's in agreement: a served evaluation refuses a server that runs another environment than the command describes. Features come from the environment's description when it is created, so the config declares none.

## Checkpoint admission

`--rename_map` aliases environment camera keys to the checkpoint's trained keys, as for any robot; in CI it comes from the entry's `rename_map` in `benchmarks/benchmarks.yaml`. Checkpoint inputs must exist after renaming, and state/action dimensions must match; renaming cannot repair checkpoint metadata. RGB channel count and layout are checked at admission. Acquisition height/width may differ from training metadata; resizing belongs to policy preprocessing.

## Verification and CI

1. Check the canonical adapter against your simulator's raw outputs, especially camera orientation, state order and applied actions.
2. Compare seeded reset/step sequences in-process and served (`scripts/ci/check_sim_parity.py`). Check terminal freezing, success, episode length, rendering and resource cleanup.
3. Run torch-disabled import guards for the server code and your native module. Document simulators that need their own torch runtime, such as RoboTwin and RoboMME.
4. Run `lerobot-eval --env.type=<name> --env.task=<task> --eval.n_episodes=1 --policy.path=<checkpoint>` in-process, and with `--env.endpoint` against the server. Inspect task descriptions and rendered camera views.
5. Run the generated benchmark job on the GPU runner. Preserve the LIBERO training smoke when changing shared evaluation/training integration.

`benchmarks/benchmarks.yaml` generates the matrix through `scripts/ci/benchmark_matrix.py`; `.github/workflows/benchmark_run.yml` runs each entry. Add entries to the manifest rather than copying CI jobs. Simulator images have separate pins and content tags; BuildKit caches only persist on persistent runners.

## Dependencies (`pyproject.toml`)

Add a new optional-dependency group for in-process use:

```toml
mybenchmark = ["my-benchmark-pkg==1.2.3", "lerobot[scipy-dep]"]
```

Pinning rules:

- **Always pin** benchmark packages to exact versions for reproducibility (e.g. `metaworld==3.0.0`).
- **Add platform markers** when needed (e.g. `; sys_platform == 'linux'`).
- **Pin fragile transitive deps** if known (e.g. `gymnasium==1.1.0` for Meta-World).
- **Document constraints** in your benchmark doc page. When the dependencies conflict with LeRobot's, the served path is the supported one.

## Writing a benchmark doc page

Add the page to the "Benchmarks" section of `docs/source/_toctree.yml`. Each benchmark page should include:

- **Title and description** — 1-2 paragraphs on what the benchmark tests and why it matters.
- **Links** — paper, GitHub repo, project website (if available).
- **Overview image or GIF.**
- **Available tasks** — table of task suites with counts and brief descriptions.
- **Installation** — `pip install -e ".[<benchmark>]"`, or the server command.
- **Evaluation** — recommended `lerobot-eval` command with `n_episodes` for reproducible results.
- **Policy inputs and outputs** — observation keys with shapes, action space description.
- **Training** — example `lerobot-train` command.
- **Reproducing published results** — link to pretrained model, eval command, results table (if available).

See `docs/source/libero.mdx` and `docs/source/metaworld.mdx` for complete examples.
