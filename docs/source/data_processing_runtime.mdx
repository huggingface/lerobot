# Offline data-processing runtime

This experimental runtime is shared infrastructure for conversion and annotation. It is
developed on the FineRobotics integration branch, not yet a replacement for every public
dataset workflow.

## Conversion

Install the dataset extra, then run `lerobot-convert --config_path=convert.yaml`.
The NPY/video example source file owns acquisition, safe unpacking, metadata discovery
and raw reading. A new source replaces those methods, not the runtime. The built-in
`lerobot.data_processing.sources.lerobot:LeRobotSource` also normalizes v3 inputs,
preserving native action/state values, subtask IDs and canonical language annotations.
Pre-v3 inputs need the existing official format-upgrade recipe first. Asynchronous
clocks, depth and missing-camera policies must be handled explicitly by their source
recipe, rather than silently treated as synchronous RGB.
View-dependent native language labels require source-specific reprojection when image
geometry changes; conversion refuses to silently associate old pixel labels with new views.

Each worker writes a complete isolated episode using LeRobot's current writer and
encoding parameters. RGB becomes an aspect-ratio-preserving square (512 by default);
exact rounded scale/padding is recorded in `meta/camera_geometry.parquet`. Source IDs
and selected frame indices remain available. Native FPS is kept unless a lower FPS
is explicitly selected; upsampling never invents actions. Cameras keep their source
names; semantic view mapping and action alignment are later processing stages.

Validated parts are assembled in source-ID order without concatenating/re-encoding
videos. `meta/processing.json` records the input hash, recipe and parameters. The final
directory is published only after ordinary LeRobot loading succeeds; existing outputs
are not overwritten. An accepted run can be assembled into another release without
repeating encoding. Conversion defaults to one episode per checkpoint.

This initial vertical slice uses the existing image spool before encoding, temporary
episode archives, and a serial metadata/part assembly pass. Budget extra temporary
storage and input/output bandwidth. No 1,024-worker scaling result is claimed; replacing
the spool/assembly bottlenecks should be driven by the maintained benchmarks.

## Language annotation

`lerobot-annotate` now builds an ordered processing recipe: plan, interjections, VQA,
plan refresh, validation, and file materialization. Existing annotation flags remain;
`--runtime.workers=4 --runtime.batch_size=8` controls local execution. Use
`--runtime.mode=plan` to seal independent stages without initializing a model. Dependent
stages are planned only after their real upstream artifacts exist. A persistent
`--runtime.run_uri=/path/to/run` holds resumable work and accepted Parquet artifacts.

Original language atoms, native actions and `subtask_index` are preserved. Generated
families have ownership records in `meta/annotations/ownership/*.parquet`; reruns replace
only families they generated, leaving disabled families and unselected episodes intact.
Unknown/source-owned atoms are never inferred to be generated. Videos are unchanged.
Dataset files are prepared and validated before a recoverable local commit. Interrupted
commits roll forward before the next run. This is not an atomic snapshot for simultaneous
readers: use a separate version directory while training or reading a live dataset.

Hub inputs get a persistent writable working copy; immutable snapshot caches are not
modified. Credentials use `--vlm.api_key_env=VARIABLE`, not plaintext in stored plans.
Local services are owned by the controller, reused across stages, and closed at the end;
workers do not spawn replacement servers. Concurrency is bounded per worker/client.

A source supplies a pinned `DatasetRef` and a stable stream of `InputItem` metadata. A
module supplies its version, scope, resources and Arrow output schemas. `seal_plan` writes
bounded Parquet row groups; `run_local` runs the same module in persistent spawn workers.
Workers initialize a model once, write isolated artifacts, and commit validated batches.
Failed runs reuse valid batches. `finalize_stage` requires complete coverage and returns an
immutable accepted index. A rejected or masked item must carry a reason.

```python
from lerobot.data_processing.artifacts import ArtifactStore
from lerobot.data_processing.planner import seal_plan
from lerobot.data_processing.runtime import run_local
from lerobot.data_processing.types import DatasetRef, InputItem

store = ArtifactStore("./runs/quality")
plan = seal_plan(
    store,
    DatasetRef("./source", input_manifest_sha256),
    "lerobot.data_processing.modules.video_quality:VideoQuality",
    {"sample_every": 30},
    [InputItem("front", {"video_path": "./source/front.mp4", "expected_frames": 300})],
)
summary = run_local(store, plan, workers=1)
print(summary.accepted_path)
```

Install `lerobot[dataset]` for Arrow and filesystem dependencies. CPU stages neither import
Torch nor construct a VLM. Source adapters are responsible for verifying that their raw
inputs still match the pinned manifest; arbitrary external files are not made immutable by
writing a digest into `DatasetRef`.

## Reliability boundaries

- One controller owns a plan. Concurrent controllers for the same plan are not supported.
- Each worker has unique attempt paths. Remote publication uses manifest-last writes and
  checksum validation, not atomic remote directory renames.
- Checkpoints pack a batch of results; work completed inside an uncommitted batch can repeat.
- An incomplete or corrupt output is recomputed. Repaired accepted indexes receive new
  content-addressed paths so downstream stages can invalidate their inputs.
- Item identities and seeds exclude worker count and shard packing. Module code must bump
  its declared version when behavior changes; pin the code environment externally.
- CPU determinism is module-specific. Seeds alone cannot promise bitwise GPU/VLM equality.
- Local spawn workers can share local/shared storage. An in-memory filesystem is only useful
  for single-process testing, not distributed workers.

`patch_table` replaces declared columns at explicit frame identities. It preserves other
rows, columns and source metadata, rejects duplicate/unknown identities, and does not
interpret missing patches as deletion. `materialize_patch` writes a separate file, never
overwriting an input dataset or immutable Hub cache. Family-aware language merging and
complete dataset publication are subsequent integration steps.

## FineRobotics implementation sequence

1. Contracts, local workers, checkpoints, safe dense patches and CPU quality module.
2. Existing annotation migration, canonical language ownership and compatibility.
3. Conversion CLI, raw source recipes, encoding and deterministic dataset assembly.
4. Slurm CPU/GPU launchers, dependency handling and worker entry point.
5. HF Jobs, serialized run packages, persistent outputs and guarded publication.
6. Extension examples, reducers, metrics, failure tests and scaling benchmarks.

Cluster acceptance and measured throughput require actual cluster resources. Generated
scripts and local tests do not establish 1,024-worker or 500–1,000× realtime performance.
