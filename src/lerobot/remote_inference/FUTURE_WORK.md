**Recommended bounded engineering work before the freeze:**

- Prepare H2's controlled one-off delay method and prove it works without hardware first. Keep the session healthy, preserve original deadlines, and expose recovery versus expiry in logs. Prefer a test-only utility or documented procedure over a production feature flag.
- Bring N2 router/security compatibility forward: it needs a router binary, not a robot. Use a small nonphysical transport interruption/congestion probe to identify any concrete N3 gap before the physical run. Do not change DROP/BLOCK policy speculatively.
- Inspect D5's strategy-only failure exit status and unhealthy-reset operational behavior with bounded reproductions. Fix a confirmed, in-scope reporting/exit defect before hardware; broader hardware teardown or process-supervision redesign stays outside this PR.
- Inspect D2's capability-error wording during C1 and improve only demonstrated ambiguity. Keep D4 control-budget changes deferred unless a concrete failure establishes a need; shortening a timeout behind valid serialized language work is an observable behavior change requiring an explicit design.

The bounded engineering recommendations above were approved and implemented/inspected in this pass; evidence is recorded in implementation progress. Do **not** pull buffered VQA motion, new robot support, additional policy adapters, GPU optimization or shared-client serving into the pre-hardware batch just because they are on the roadmap.

**Suggested order:** inspect bounded runtime issues and test coverage → implement agreed fixes/consolidation → write C4 and simplify C1/C2 → update C5/C6 and audit scope → run relevant software checks and hosted CI → freeze the behavior → H1–H4 plus the selected interaction smoke check. Subsequent documentation-only updates do not by themselves require another hardware round.

“Final validation” here means final validation of the agreed PR scope. Real language remains an explicitly unvalidated feature until L1 is run; router robot operation, new checkpoints and hosted deployments remain separate follow-up experiments unless deliberately included in the coming round. If the available setup cannot induce the intended condition, mark the physical check pending; do not describe an ordinary no-starvation run as a pass. The launcher adds no production tuning knobs.

Keep these semantics explicit when interpreting H1–H4:

- `--inference.action_starvation_grace_s=1.0` is the current default; zero selects immediate exhaustion fault. It is separate from server absent-client cleanup and planned language/startup deadlines.
- Grace covers draining old work, ordered invalidation and fresh inference. It never renews an existing operation deadline or makes stale/invalid actions eligible.
- Unsupported local robots retain ordinary RTC but receive no starvation grace. Remote operation still requires supported position-hold semantics and explicit configuration.
- Planned language pauses, operator pauses, recording pauses and starvation share a motor operation, but have different budgets and resumption authority. Language still pauses immediately.
- A latched server loss cannot recover in the same session. Accepted actions can drain before bounded waiting and terminal shutdown.

Add only one short interaction smoke check to this round if convenient: change instruction during inference, then exercise recording save/resumption on a setup that uses it. Confirm obsolete task results do not execute, recording retains correct task labels, and blocking saves pause/resume correctly. Software coverage exists; physical evidence for these reviewed paths remains distinct. No inference-event sidecars or extra dataset artifacts are expected.

## Stage 4: remote hosting, with Spaces as the preferred follow-up

After the router check, try a private remote connection or an explicitly secured public route as available. Then prioritize **one dedicated GPU Space serving one client** over concurrent shared-model work.

```text
Robot client -- outbound authenticated/encrypted Zenoh --> reachable router
GPU Space    -- outbound authenticated/encrypted Zenoh --> same router
```

1. **Transport feasibility first:** recheck current Spaces networking restrictions and prove real outbound Zenoh request/reply and persistent presence from the actual Space. A web port or port 443 alone does not establish compatibility. No hardware is needed for this step.
2. **Only after feasibility:** package one known-good policy server, model warmup/readiness and secrets. Keep the router separately hosted and secured. If connectivity fails, evaluate an explicitly supported gateway/tunnel or another host before expanding implementation scope.
3. **One physical task:** measure full turnaround variability/playback margin and task performance, then verify interruption/clean shutdown and a new session after restart. Assess JPEG only if bandwidth warrants it.

**Acceptance:** useful operation within existing freshness/deadline bounds, with trustworthy ownership/readiness and local motor/shutdown authority. “Anytime/anywhere” is conditional on server readiness, network quality and available ownership. Record startup/sleep and cost implications when selecting the deployment; no cloud resource or public exposure is authorized by this document alone.
