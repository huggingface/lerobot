You inspect frames from ONE camera stream of a robot-manipulation dataset, shown in
chronological order. Use ALL frames together, never a single frame.

Return ONE JSON object with three INDEPENDENT judgments, made in this order:
1. usable (quality); 2. mount_type; 3. view_label.
Never use a later judgment as evidence for an earlier one.

{task_context}1. QUALITY (usable)

Default usable=true. A view is USABLE if a meaningful fraction of frames shows the
robot manipulation scene — the robot, its gripper/arm, the work surface, or the
manipulated objects — clearly enough to be recognizable. It need NOT frame the task
perfectly or be ideal for learning, but it must actually be AIMED AT the scene.

Set usable=false (with a short "blur_reason") ONLY when ALL / NEARLY ALL frames fail:
  - blur so extreme the frame is unintelligible (not mere soft focus / motion blur);
  - severe over/under-exposure, corruption, a frozen feed, a test pattern, a logo,
    or a "no signal" / placeholder / blank image;
  - a TACTILE / touch-sensor readout (GelSight/DIGIT contact image, gel pad,
    force/pressure heatmap) -> reason "tactile sensor, not a camera view";
  - a DEPTH / disparity map (smooth grayscale or false-colour distance map) ->
    reason "depth map, not an RGB camera view";
  - the lens is blocked so no useful scene is visible in any frame;
  - IRRELEVANT / MISAIMED: the camera is pointed AWAY from the scene the WHOLE
    episode — every frame shows only unrelated surroundings (a ceiling, a plain
    wall, the floor, a random corner of the room) and NO robot, gripper, work
    surface, or manipulated object is visible in ANY frame -> reason "camera not
    aimed at the workspace". (A close-up of the work surface, an object, or the
    gripper still counts as the scene — do NOT flag those.)

Transient problems are FINE: some blurry frames, a temporary blank wall, a brief
obstruction, or the robot's own arm/gripper partly blocking the view -> usable —
as long as OTHER frames do show the robot/workspace. Only flag when the scene is
NEVER visible across the whole stream.

WRIST / CLOSE-UP BLUR SLACK: a wrist or extreme close-up (gripper in foreground,
lens inches from the surface) is often soft, washed-out, low-contrast, or
motion-blurred — this is NORMAL and stays USABLE. Flag it only when it is a uniform
featureless field with NO discernible object, gripper, edge, or surface at all.

HUMANS (these are teleoperated recordings): mark UNUSABLE only when a human is
PROMINENTLY present as an operator/bystander — a person filling much of the frame or
reaching over the working area, a hand/arm persistently in the workspace, or a human
HAND GRIPPING a second "leader" arm (it looks like the robot, but a hand holding an
arm means the operator is in frame). A partial or background human not interacting
is FINE. EXCEPTION: if the task itself involves a person (handshake, someone handing
the robot an object — see TASK CONTEXT) or the human is a task PARTICIPANT, keep
usable. The robot's own arm is table/base-mounted, not hand-held.

2. MOUNT TYPE (fixed / robot_mounted / unknown)

Judge whether the VIEWPOINT is attached to the robot, from the STATIC ENVIRONMENT
(table edges, walls, shelves, fixtures, the background scene) — NOT from how large
or prominent the robot/gripper is.

PRIMARY TEST — track the static BACKGROUND across frames:
  - If concrete static landmarks / a background SCENE (desk, wall, mat, furniture,
    table edges, monitor, containers) stay REGISTERED in roughly the same place and
    perspective -> FIXED. This holds EVEN when the arm or gripper looms LARGE in the
    foreground or hovers nearly still there — the arm is just moving through / toward
    a stationary camera. A prominent, close, or still gripper does NOT by itself make
    a wrist.
  - If those static landmarks globally TRANSLATE / ROTATE / RESCALE, or the whole
    scene re-frames, correlated with robot motion -> robot_mounted.

GRIPPER FALLBACK — use ONLY when the background is BLANK / uninformative (a green
screen, plain wall, or empty tabletop with no trackable texture, so drift cannot be
judged). Then, if the CAMERA'S OWN gripper is anchored in the near foreground —
belonging to the arm the camera rides on, emerging from the near edge, showing only
its forward-facing END connected to your viewpoint, pinned at constant size and
position across frames -> robot_mounted (wrist). Do NOT use this fallback when a
concrete static background scene is present — there the background decides above.

NOT a wrist, even with a gripper in view:
  - you look AT a SEPARATE, whole arm as an external limb (joints/servos/links seen
    from the OUTSIDE) over a real scene -> fixed (e.g. a side camera watching an arm
    pour);
  - the gripper/arm changes SIZE or POSITION across frames (small/far, then
    large/close as it reaches/pours/retracts) -> a separate arm before a stationary
    camera -> fixed;
  - a big arm swinging in and out of a stationary scene -> fixed.

If neither test resolves -> unknown (do not invent motion).

3. VIEW LABEL — use ONLY this closed vocabulary:
  {vocabulary}

Reason about physical geometry, not the image orientation (it may be rolled or
mirrored). Classify from the locked mount_type:

If robot_mounted -> "wrist" (NEVER top/bottom/side).
  Assign left_wrist / right_wrist ONLY from HAND ANATOMY: on a multi-fingered hand,
  read palm-vs-back and the THUMB side (a left and a right hand are mirror images).
  Fall back to plain "wrist" for a 2-jaw gripper (no thumb) or if unreadable. NEVER
  infer handedness from image side, the gripper's pointing direction, or mirroring.

If fixed -> top / bottom / side (NEVER wrist).

  TOP vs SIDE — the deciding question: is the camera ABOVE the workspace looking
  DOWN onto it (the workspace laid out BELOW the lens, you see the tops of things /
  into boxes) -> "top"; or at the workspace's OWN level (near table/eye height)
  looking ACROSS it (objects edge-on, arms standing up) -> "side". LEAN TOP: an
  elevated downward camera is "top" even at a strong diagonal, with perspective, a
  wall behind, or visible object fronts — none of that demotes it, and it need not
  be near-nadir. WHEN IN DOUBT, choose TOP. Reserve "side" for a clearly across,
  table-level / perimeter view.

  BOTTOM: camera below the workspace looking up.

  SIDE DIRECTION (optional — plain "side" is a valid, confident answer). The
  directional labels say where the CAMERA physically sits relative to the robot.
  First find the robot's FRONT (its working direction — where the objects and active
  workspace are) vs BACK (motor backs, mounts, cabling; objects are stronger
  evidence):
    - front_side: objects between robot and camera, arm reaching TOWARD you;
      rear_side: workspace beyond the robot / motor-backs toward you, arm reaching
      AWAY.
    - left / right — from robot geometry, using body position AND reach TOGETHER
      (never the image side alone): robot body/base toward image RIGHT + arm reaching
      LEFT -> left_side; body toward image LEFT + reaching RIGHT -> right_side. (A
      camera on the robot's LEFT sees the body pushed to the RIGHT/far edge with the
      workspace on the left — do not invert this.) If the base is out of frame, the
      geometry is ambiguous, or the image may be mirrored -> plain "side".
  Commit to a direction when body + reach are clearly readable; otherwise "side"
  (you may list a plausible-but-unproven direction in candidates, but do not promote
  it to view_label).

  base_image_side / workspace_image_side: report WHICH IMAGE SIDE (left / right /
  center) the robot's base and the active workspace sit on. This is PLAIN
  LOCALIZATION — just report what you see; do NOT compute left/right from it (done
  downstream). Say "left" or "right" only when the thing is clearly toward that side
  of the image; use "center" when it is roughly centered, in the FOREGROUND between
  the robot and the camera (a front/rear-facing view), or you cannot tell. For
  top/wrist views "center" for both is fine.

If unknown -> view_label "unknown" unless the category is independently clear.

Consistency: fixed pairs with top / bottom / side / front_side / rear_side /
left_side / right_side; robot_mounted with wrist / left_wrist / right_wrist; unknown
with unknown. A FIXED camera is NEVER wrist; a ROBOT_MOUNTED camera is NEVER
top/bottom/side. {combo_rule}Do not invent labels outside the vocabulary.
